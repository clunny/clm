description: Turn an intent into one CLM spec branch and land it. Use when the user wants to add or change behaviour, record a design decision, or reshape the specs in a repository with specs/SPEC.md.

# Propose a change

Turn the user's intent into **one** spec branch, and see it through to `main` with `clm land` (`land-locally`). A spec branch either needs review or lands on checks (`yes-no-review`): when the first line `clm gate` prints is `spec review`, it lands only after the human's `clm approve`; when it is `spec`, it lands on checks, and nothing is reviewed after it lands. A branch needs review when it edits `ARCHITECTURE.md`, `CAPABILITIES.md` or `docs/allowed_signers`, changes `clm.toml`'s `approval`, or adds or edits a change that declares `human_burdens`. Every human review costs time, so put all of this piece of design work (decisions, deltas and backlog edits) in it.

1. Read `ARCHITECTURE.md` and the repo's `CLAUDE.md`, then run `clm status` and `clm backlog` to see the current state. Run `clm proposals` and leave out every item it names: another session holds it (`propose-claims`). When the user names no intent, suggest only the remaining `idea` items, highest priority first, as `clm backlog` lists them (`priority-caps`), and point the user at `/clm:triage` for the `bug`, `question`, `human-task`, `deferred` and `workaround` items, saying so when no `idea` item is left (`triage-owns-backlog-work`); an item of any kind the user names is still taken as the intent. If the intent comes from backlog items, read them, then claim each with `clm claim backlog/<slug>`. When a claim is refused, tell the user what holds the item and stop on that item: never work around the refusal. Right after claiming, cut the spec branch, `<id>` being `<YYYYMMDD-slug>`, in a worktree of its own (`session-worktrees`): run `git worktree add .claude/worktrees/<id> -b spec/<id> origin/main`, change into `.claude/worktrees/<id>` and do all later work there. Other sessions on this clone share the checkout you started in, so never switch the checkout you started in onto another branch. When you started in one of the skills' own worktrees, add yours under the clone's main checkout, the first path `git worktree list` prints, with `git worktree add <main>/.claude/worktrees/<id> -b spec/<id> origin/main`, so it is never nested in that worktree. The one exception is a session whose checkout it started in already lies under `.claude/worktrees/` (`git rev-parse --show-toplevel`, run before you cut anything, says so; a worktree this step adds doesn't count, and neither does one the skills add, named by a change ID, `<YYYYMMDD>-<slug>`, `archive` or `defects`, whoever started there), where Claude Code isolates a subagent's session and refuses every git command aimed at another worktree: there, cut the branch in the checkout you have with `git switch -c spec/<id> origin/main` and do all later work there, since that worktree is this session's own and no other session's `HEAD` moves with it. Such a session removes no worktree, since the one it is in belongs to whoever made it: once the branch has landed, it switches its checkout off the branch with `git switch --detach origin/main`, before `clm wrap-up`. On `spec/<id>`, in its worktree or the isolated checkout, write `changes/<id>/change.md` with `from` or `resolves` naming the items and `status: proposed`, commit it and push the branch, so the spec work holds the items before the claim's expiry runs out, with or without autosync. Never rename the change ID after that; if you must, delete the old `spec/<id>` and `autosync/spec/<id>` on `origin`, which would otherwise hold the items. When you resume a `spec/<id>` that already exists, change into `.claude/worktrees/<id>` when it exists, and otherwise add it for the existing branch with `git worktree add .claude/worktrees/<id> spec/<id>` (no `-b`). A session isolated under `.claude/worktrees/` switches to it with `git switch spec/<id>` instead, when no other worktree holds the branch; when one does, say so and stop, since you can neither enter that worktree nor check the branch out twice. Write scratch files, such as the pull request body, under `.clm/`, which git ignores. A claimed item that design finds already fixed, by an earlier change or by code that has landed, stays in `resolves`: delete its `backlog/<slug>.md` on the spec branch and name in `## Intent` what fixed it, so the change retires the item without claiming a fix it doesn't make.
2. Brainstorm the design (`design-brainstorming`): run `clm superpowers brainstorming` and follow the skill at the path it prints on stdout. The skill's own first step decides whether the intent needs the conversation: a request that already fixes what to build goes straight on. When it explores the project, use `clm context <component>` for the components the intent touches. Map its outputs onto CLM's:
   - its design doc becomes the `change.md` body, with its approaches under `## Approaches`. Don't write or commit the doc on its own: it is written in step 4;
   - significant choices become `docs/decisions/` files (step 6);
   - its approval of the doc is the user's agreement in this conversation, before you write any delta;
   - skip its own spec or builder review: the change gets one builder check, `propose`'s, before the pull request.

   Never write under `docs/superpowers/`. Never hand over to `writing-plans` either: carry on with the steps below instead. Read only the skill's text: don't invoke the installed `superpowers:brainstorming` skill or turn the superpowers plugin on, so its hooks don't run. If `clm superpowers` fails, for example because the installed `clm` predates the command or the fetch fails offline, tell the user and carry on without brainstorming.

   When brainstorming finds that the intent is a `kind: bug` backlog item whose fix changes nothing under `specs/`, `changes/`, `docs/`, `ARCHITECTURE.md`, `CAPABILITIES.md` or `CLAUDE.md` (such as a wrong test, or code that falls short of requirements it already has), whose code lies in one of the item's `components`, and whose behaviour a requirement or scenario already states, offer the user a code branch instead of a spec branch, as **Code fixes** below says; on a no, carry on with the spec branch.
   **Recommend the right design** (`recommend-the-right-design`). Before you recommend an answer, a fix or a design, or offer choices for one, such as the approaches while brainstorming, read the specs and the code it concerns: `clm context <component>` for its components, and the files under their `paths` it names or touches. Read them before anything is shown, not after the human pushes back. Treat the fix the item itself suggests, or the first one that comes to mind, as one option among the approaches, never as the answer by default, and recommend the design that is correct and maintainable over the long term, saying why it beats the most convenient one. Recommend a cheaper or smaller option only with the reason it is also the right one.

3. Find the components it touches: `clm context <component>` shows a component with its ancestors and dependencies. Then run `clm proposals --component <component> [--component <component>]...` for them, with `--component` once per component. When it prints a `proposed` or `claimed` line, show the user those lines and ask whether to carry on, fold the work into the other change, or wait: overlap never stops you by itself, the user decides. A `main` line is a change already applied on `main`: its deltas are in `specs/`, the base your deltas are written against, and nothing can be folded into it or waited for, so ask nothing about it.
4. On the branch `spec/<id>` from step 1, in its worktree (when no item was claimed, cut it now as step 1 says, with `git worktree add`, or with `git switch -c` in an isolated session), write `changes/<YYYYMMDD-slug>/change.md` with the intent, `status: proposed`, `human_burdens` when it has any, `from` or `resolves` when they apply, and `priority`: the highest `priority` among the items in its `from` and `resolves`, left out when all of them are `P5` (`priority-orders-nodes`). A change declares no order against other changes: the queue builds component by component, and the only ordering a change carries is its `priority` (`node-reconciliation`). Its body starts with `## Intent`, a few sentences on what the change does and why, then the problem, `## Approaches`, the outcome and the constraints.

   List under `human_burdens` in its frontmatter, one short line each, what the change spends of the human's money or time, or can't undo: a paid service, a step only the human can take, an outward-facing or irreversible effect. Leave it out when there is none. A `human-task` backlog item the change adds is a burden: a spec branch that adds one and declares no burden is blocked (`gate/undeclared-burden`). A burden makes the branch need review.
5. Write one `deltas/<component>.md` per component, with ADDED, MODIFIED or REMOVED requirements, Contract or Design. Take each MODIFIED element's base from `clm hashes <component>`. Every requirement needs at least one scenario, and requirement IDs are kebab-case slugs, never numbers. Once `CAPABILITIES.md` or `ARCHITECTURE.md` holds an entry, every rule must serve one: give each component you add, and each component you add a rule to that has none, a `serves` list in its frontmatter naming the entries its rules serve, and a rule whose purpose differs from its component's a `#### Serves` block (`- <id>` lines, among its scenarios) that replaces the component's list for it (a MODIFIED rule that leaves its block out keeps the one it has); `clm check` fails a rule that serves nothing (`check/untraced`). Before any layer holds an entry, write neither: an ID must name an entry that exists.
   When the change splits a component or carves a part out of one (`slim-components`, `nested-splits`), make the carved-out part a child of the component it came from, at `specs/<component>/<part>/SPEC.md` with ID `<component>.<part>`. Keep the product's ID on the half that stays: the one other components already name, or the one that is the product rather than a part of it. Move each requirement unchanged: REMOVED from the parent's delta and ADDED, word for word, to the child's. The child's delta has `create: true` with its frontmatter, Contract and Design; the parent's has `MODIFIED Frontmatter` (its `paths` shrink, so every component's `paths` stay disjoint, and its `depends_on` may gain the child) and a `MODIFIED Contract` and `Design` that hand the carved-out part over. Split only along architectural seams (parts that change for different reasons, have different dependencies, are already separate packages or have their own contract), never to satisfy a size budget alone. Cut so that imports run one way (`splits-import-one-way`): the child below the parent, or what both halves share in a layer of its own below both. Inside one crate or package that means a carved-out part using the crate's other modules goes into a crate or package of its own. Check the cut before writing a delta: write a component map of the component's halves to a file, listing every file each will own and `outside: ["**"]` for the rest of the code, run `clm survey --components <file>`, and change the cut until it exits 0. `clm guide shaping-the-graph` says how.
   When a delta modifies or removes a requirement, delete each `workaround` backlog item whose `requirement` names it, or, when the workaround still applies to the new text, re-record the item's `requirement` at the version `clm hashes <component>` prints after `clm apply` (step 7), since the model rejects a flag at an old version; and delete the `reconsider-<component>-<slug>` question the change answers.
   When the change alters what a person can do with the product, or what must always hold of it, edit `CAPABILITIES.md` or `ARCHITECTURE.md` directly in the branch, not through a delta: add, reword or remove the `### Capability: <slug>` or `### Constraint: <slug>` entry, the latter in `ARCHITECTURE.md`'s `## Constraints` section (format in `clm guide spec-format`). Such an edit always needs review. Each architectural constraint you add or reword holds an `#### Enforced by` block naming the rules that enforce it (for a property of every file, the whole-tree check that reads them all; for a choke point, the one path plus each blocked bypass), or an `#### Untested` block saying why no program can check it, or both for an entry that is part mechanism and part judgement (`human-layer-proof`); a test never cites an architectural constraint, which is current when every rule its block names is current, and `clm check` fails an entry with neither block (`check/unenforced`). A capability is proven by a test of the component `capability` at the project's public boundary, deterministic, with what lies beyond the boundary (a model, the network) stubbed; until the project has that component, its root component builds those tests.
6. Record each significant choice as `docs/decisions/<name>.md`. Add, edit or delete backlog items the change affects: work it defers goes to `backlog/<slug>.md`.
7. Run `clm check` until it passes. When it reports `check/priority-caps`, ask the user which holder to demote, never choosing one yourself: priority is the human's call. Then `clm apply <change>`, as the last step, re-record at the new versions `clm hashes <component>` prints the `workaround` items step 5 kept, and run `clm check` again.
8. Commit, then run `clm rebase` until its last line is `rebase ok`, reading its outcome from that line, never from its exit code: `rebase incomplete` leaves something for you to resolve, and `rebase failed` means git itself failed, so run it once more and, if it fails again, stop and tell the user what it printed. It rebases the branch onto `origin/main` and regenerates `specs/` from your applied deltas, and it prints what it leaves for you: resolve conflicted files by hand and `git add` them, rebase stale deltas on `clm hashes`, fix check failures, commit, and run it again. Then:
   - Run `clm gate --base origin/main`. Its first line is `spec review` when the branch needs review and `spec` when it lands on checks. A branch that needs review also reports `gate/approval` until the human approves it; that is expected, so leave it, and never remove a burden to make the branch land on checks. When it reports `gate/undeclared-burden`, declare a burden in `human_burdens` for the `human-task` item it names, run `clm check`, commit, and run it again.
9. Run a builder check (`blocked-by-backlog`). Launch a fresh subagent with the `Agent` tool (general-purpose, `model: "sonnet"`, `model-per-launch`), giving it only the change ID and the path of this checkout, not this conversation. Ask it to work in that checkout, to read `changes/<id>/`, `clm context <component>` for each component the change touches and the decisions it names, as the person who will build the change, and to list the questions it would need answered first. Then:
   - settle what the repo or this conversation already answers by writing the answer into the change;
   - facts only a human knows, and steps only a human can take (creating accounts, DNS records or secrets), go into the change as backlog items at the repo root, `backlog/<slug>.md`, of kind `question` or `human-task`, with `origin` the change and `blocks` naming the requirements that can't be built before they are settled (`requirement-blocks`);
   - a requirement that can't be built until another component's pending requirement is built gets a `#### Needs` block among its scenarios in its component's delta, one line `- <component>/<slug>` per requirement it waits on (`requirement-needs`), not a backlog item: the queue holds it back until those are current. When the change has no delta for that component, add a MODIFIED one with its base from `clm hashes <component>`. The change is `applied` by now, so `clm apply` refuses it: the edited deltas reach `specs/` when `clm rebase` re-applies them, as below;
   - a requirement that removes or renames part of a component's Contract that another component's code uses is such a requirement (`contract-removal-needs`): it needs the requirements that move each such component off the old contract, and a removal written only as `REMOVED Requirements` can't carry them, so state it as an added or modified requirement, or split it per `expand-contract`. Ask the subagent to search the code of the other components for uses of each part of a Contract the change removes or renames;
   - when the removal can't carry that `#### Needs` (the removing component is required and the component that must move is optional, or the removed text is a whole requirement), the contract step goes in a second change on the same branch, left `proposed`, and the branch also adds a `kind: deferred` backlog item for it (`contract-step-deferred`): its `components` are the contract change's components and its body names the contract change and each requirement it waits on with the version it must be current at. The contract change's `resolves` doesn't name the item, so `clm triage` shows it until the human judges it due;
   - a Contract or Design edit alone builds nothing (`dependency-work-is-a-requirement`): ask the subagent to name the work a requirement relies on from another component that no requirement of that component states, then add that component's requirement to the change, which makes the component pending, and name it in the relying requirement's `#### Needs`;
   - ask the subagent, for each requirement the change adds or modifies, which requirements not yet current it relies on, of any component, among the change's own and those `clm pending` lists, answering `none` for a requirement that relies on none (`builder-check-asks-order`), so a missing order shows as a named pair rather than a question the subagent may not think to ask. A requirement relying on a pending requirement of its own component that has a `#### Needs` block carries that block's needs too, since a need may not name its own component and the build's order within the component can't wait on another component's work;
   - list the rest under `## Open questions` in the pull request body (step 10).

   If you changed anything, run `clm check`, commit, and repeat step 8: `clm rebase` until its last line is `rebase ok`, then `clm gate --base origin/main`, declaring a burden for each `human-task` item the check added. The builder check advises and never gates.

   A change whose deltas add, modify and remove no requirement, such as one that edits only a Design, a Contract, decisions or the backlog, has nothing to build, so it is archived in its own spec branch (`archive-in-spec-pr`). After the builder check, the last `clm rebase` and `clm gate`, as the last commit before opening the pull request, set its `status: done`, run `clm archive <id>`, delete each `backlog/<slug>.md` its `resolves` names, since no `impl/*` sync will archive it, and run `clm check` again, so the change lands on `main` already archived. `clm rebase` still counts it as the change the branch adds once it is archived (`sync/reapply`): it keeps `main`'s side of a conflict under `specs/` and re-applies the archived change's deltas, so `specs/` is never yours to merge.
10. Before opening the pull request, review the session for CLM defects neither reported nor fixed (`defect-reports`): anything CLM itself (its CLI, gate rules, plugin, skills or method) would have to change so it doesn't happen again, not your own mistakes that CLM caught or you fixed. Report each with `clm defect --title <title> [--component <component>]...`, naming with `--component` the component a fix would lie in, the report on stdin, describing only the process, never the project's files, code, specs or output, unless the session-start rule has it folded into the branch. Run `clm proposals --component <component> [--component <component>]...` again for the change's components, and when it prints a `proposed` or `claimed` line ask the user as in step 3. Write the pull request body to a file under `.clm/` and push with `git push --force-with-lease`, since step 8's `clm rebase` rebased the branch onto `origin/main` and a plain push is refused, then open the branch's pull request with `clm pr open spec/<id> --title <title> --body-file <file>`; correct its body later with `clm pr body <file>`. The body has `## Intent`, `## Decisions` (each new or changed decision, by name, with its title), `## Open questions` and `## CLM defects`, listing every defect of this session (or `None`), each fixed one with its fix. Say whether the branch waits for the reviewer's `clm approve` (`spec review`), naming its `human_burdens`, or lands on checks (`spec`).
11. Land by the first line of your last `clm gate` run (`land-locally`). For `spec`, run `clm land spec/<id>` at once. For `spec review`, ask for the approval first (step 12), and on a yes run `clm land spec/<id>`. Go by what `clm land` prints:
    - `landed <sha> ...`: the change is on `main`; go to step 13;
    - `gate/up-to-date`, or a conflict with `main`: run `clm rebase`, resolve what it reports as in step 8, push with `git push --force-with-lease`, and land again. An approval holds only while the diff's fingerprint is unchanged: if `clm land` reports `gate/approval` after the sync, ask again;
    - a failing check: fix it, commit, push, and land again. For a branch that needs review, if the fix changed the diff's fingerprint, `clm land` then reports `gate/approval`: ask again (step 12).
12. For a branch that needs review, ask the human for their approval in this conversation (`approve-in-session`): show the pull request's link and the change's `## Intent`, its `human_burdens`, `## Decisions` and `## Open questions`, and ask whether they approve its intent. On a yes, run `clm approve spec/<id>`; the guard asks the human to confirm that command, and their confirmation is the approval. Then land it (step 11). On a no, discuss what to change, edit the change, re-apply it with `clm rebase`, push with `git push --force-with-lease`, and ask again.
13. When the branch has landed and `clm defect` writes to the backlog (the session-start rule says so), first **fix reported defects**, before `clm wrap-up` and the summary: fix each small defect this session reported whose item is on `origin/main`, one at a time and one round only, as the code fixes below do, with `clm claim <component> --fix backlog/<slug>`, in this branch's worktree switched with `git switch --detach origin/main`, never in the checkout the session started in, unless the session is isolated under `.claude/worktrees/`, where that checkout is the branch's own. Fold a defect you meet during such a fix when it lies in that fix's component, and leave it filed otherwise. When a claim is refused or a fix turns out large, leave the item filed, release a claim you took by deleting its branch on `origin` and, after `git switch --detach origin/main`, the local branch with `git branch -D`, and name the item in the summary. The fix branch's pull request lists the defect as fixed; the landed pull request that reported it isn't edited.

    Then, with the branch landed: a session isolated under `.claude/worktrees/` (step 1) switches its checkout off the branch with `git switch --detach origin/main` and removes nothing; otherwise, change back to the directory you started in and remove the branch's worktree with `git worktree remove .claude/worktrees/<id>`; when that refuses, tell the user the path and leave it, never forcing it. A worktree whose branch hasn't landed, such as a change waiting for approval, stays with its branch for the session that picks the work up. Then run `clm wrap-up` (`checkpoint-before-done`), which deletes the landed branch. It removes landed work and reports what isn't safe on `origin`; fix what it reports and run it again. Then end with a summary: what landed, what is still open and who it waits on, and the backlog items you added. Once the checkpoint exits 0, add a line saying everything is saved, the session can be ended or cleared, and `/clm:build` in a new session builds the change. If the checkpoint can't pass for a reason you can't fix, say what and why instead of that line.

Never push `main` by any means but `clm land`. Run `clm approve` only after the human says yes in this conversation, and only through the guard's confirmation: never route around the guard or ask another tool to do it. Only a human approves a spec change (`humans-review-intent`).

## Elaborating an idea

An idea may be elaborated over several sessions in its own backlog item (`elaborate-ideas-on-main`). This section is outside the numbered steps.

- **Start.** When the user wants to elaborate an `idea` item, first look for an unlanded branch of it on `origin` with `git ls-remote origin 'refs/heads/spec/*-idea-<slug>'` and resume that one when there is one, in a worktree of its own. Otherwise claim the item with `clm claim backlog/<slug>`, stop when the claim is refused as for a change, and cut `spec/<YYYYMMDD>-idea-<slug>` from `origin/main` in a worktree of its own. A new idea is cut the same way without a claim, its item written with `title`, `kind: idea` and `components` in its frontmatter.
- **Elaborate.** The branch holds no `change.md` and no delta. Keep in the item's body the sections `## Intent`, `## Settled` (each choice made, with its reason), `## Approaches` (the options still open) and `## Open questions` (what the next session takes up), rewriting them as the brainstorm settles things and starting from the item's `## Open questions` when it has them. Commit and push as you go, never landing at every pause.
- **Land once.** At the end of the session, or when the user asks for a checkpoint, run `clm rebase` until its last line is `rebase ok`, push, and land the branch with `clm land`, going by the first line of `clm gate --base origin/main` (`spec`, or `code` for a branch that only adds a new item, both landing on checks). On `landed <sha>` release the claim you took and the branch's autosync snapshot, deleting `propose/<slug>` and `autosync/spec/<YYYYMMDD>-idea-<slug>` on `origin`, each with its own `git push origin --delete <ref>`, since nothing else deletes them while the item stays in the backlog, and then run `clm wrap-up`. Work after a land in the same session goes on a branch cut afresh from `origin/main`. A session that runs past the claim's expiry claims the item again with `clm claim backlog/<slug>` once the claim has lapsed.
- **Propose.** Once the user agrees to the whole design, propose the change as any other, with `from: backlog/<slug>`, its `change.md` seeded from the item's sections and the item deleted on the spec branch.

## Code fixes

When the user says yes to a code branch for a bug (step 2), and that bug is the only item the intent comes from, fix it on one code branch instead of a spec branch (`code-fix-resolves-bug`).

A bug takes this route only when a requirement or scenario as written already states the behaviour the fix restores, and the fix's test cites that requirement. When none does, the fix starts with a spec branch that adds the requirement or scenario, and the code fix follows on `impl/<component>` citing it, built once that change lands (`code-fix-needs-a-written-rule`): keep the spec branch from step 1 and carry on from step 3, as for a fix that needs a spec change below. A fix no requirement states is code that serves nothing written, which the next rewrite, slimming or `no-dead-code` pass can remove unseen.

The code branch:
- In the checkout holding `spec/<id>` from step 1, its worktree or the isolated checkout, switch off the spec branch onto `origin/main` with `git switch --detach origin/main`, then delete the `spec/<id>` branch you pushed in step 1, locally and on `origin`, with `autosync/spec/<id>` on `origin`, so no change names the item.
- Claim the component whose code the fix changes with `clm claim <component> --fix backlog/<slug>` (`orchestrator/claim-fix`), run in that worktree, which it switches to the `impl/<component>` branch it prints; work there. A test file lies in the components its `req:` markers cite as well as in the component whose `paths` hold it (`fixes-count-where-cited`), so a fix to a component's test kept under another component's `paths` claims the component the test cites; when the fix's files belong to several of the bug's components, claim any one of them, since one claim carries the fix.
- Fix the bug test first: a test that fails on the bug, then the fix that makes it pass.
- Delete `backlog/<slug>.md` in a commit whose trailer block, the message's last paragraph beside `Co-Authored-By`, holds `Resolves: backlog/<slug>`, which lets the gate pass the deletion in a code land (`gate/backlog-additions`).
- Run the repository's checks and reviews as `CLAUDE.md` asks, then `clm rebase` until its last line is `rebase ok`; `clm check` must pass and `clm gate --base origin/main` must print `code`.
- Review the session for CLM defects as in step 10, push with `git push --force-with-lease`, since `clm rebase` rebased the branch, open the pull request with `clm pr open impl/<component> --title <title> --body-file <file>`, whose body has `## CLM defects`, and land it with `clm land impl/<component>`, handling what it prints as in step 11, with no review to ask for. When it has landed, finish with step 13, saying in the summary that the fix landed and nothing is left to build.

A fix whose code spans more than one component, that touches none of the bug's `components`, or that needs a spec change stays a spec branch; so does one whose component's claim is refused: tell the user why and carry on from step 3.

## Contributing back from a fork

When `clm contribution parent` names a parent, this clone is a fork, so ask the user once, before cutting the branch in step 1, whether this work goes back to the parent or the fork is their own project, which carries on as any other. For work going back, bring the fork's `main` up to the parent's first with `clm contribution sync`, then do steps 1 to 8 as written, branching from the updated `origin/main`. Run neither `clm land` nor `clm approve`: the parent's maintainer decides what lands, and a land in the fork would only move the fork's own `main`. Push the branch and open its pull request on the parent with `clm contribution open spec/<id> --title <title> --body-file <file>`, the body written as step 10 says, and leave "Allow edits by maintainers" on, so the maintainer can rebase it. End by telling the user that the parent's maintainer reviews it and nothing more is needed unless they ask for changes. `clm guide contributions` says what a maintainer accepts and why.
