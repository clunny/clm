# Upgrade the project

Bring the project up to date with the `clm` it runs, one migration at a time (`upgrades-carry-migrations`). Never push `main` by any means but `clm land`. Run `clm approve` only after the human says yes in this conversation, and only through the guard's confirmation.

1. Run `clm upgrade`. When it prints `up to date`, say so and stop.
2. Cut the branch `upgrade/<YYYYMMDD>` from `origin/main` in a worktree of its own (`session-worktrees`): run `git worktree add .claude/worktrees/upgrade-<YYYYMMDD> -b upgrade/<YYYYMMDD> origin/main`, change into it and work only there. Never switch the checkout you started in onto another branch.
3. Run `clm upgrade --apply`. It takes the mechanical migrations and prints a `note <id>` line for each advised edit the project owns.
4. For each `note <id>`, read the note with `clm upgrade --note <id>`, show the human the edit it proposes beside the file's current text, and make the edit on their yes. On their no, run `clm upgrade --decline <id>`. An edit to `ARCHITECTURE.md` or `CAPABILITIES.md` is one the human then approves again with `clm approve`. A note that says it edits no file, such as the one telling a project its tests must now overlap (`upgrade/migration-tests-overlap`), asks for no edit: show the human the note, offer to do what it advises (such as looking through the check script and tests for fixed ports, paths and shared servers and recording each as a `bug` backlog item on the notes branch) and do it on their yes, and run no `clm upgrade --decline` for it, since `clm upgrade --apply`'s stamp has already taken it (`stamp-taken-notes`).
   For the note on `.claude/settings.json` (`upgrade/migration-unattended-allow-rules`), never edit that file yourself, since it holds the human's settings and is a protected path (`unattended-steps-run-clm`): show the human the rules `clm init --check-permissions` prints in the upgrade's worktree, ask them to add those they want to `.claude/settings.json` there by hand, and run `clm upgrade --decline` for the migration when they want none. When the root component's `paths` don't list `.claude/settings.json` and git doesn't track it yet, as in a project set up before `clm init` seeded the rules, put the file's addition to the root's `paths` on the notes branch, as a change of its own as `/clm:propose` makes one (`changes/<id>/` with a delta for the root's frontmatter, applied), landing it as that branch lands, and commit the settings file only after that, on a third branch `upgrade/<YYYYMMDD>-settings` cut from the new `origin/main` and landed as the code branch is, since `.claude/settings.json` is a code path and `clm check` reports a tracked file that no component's `paths` hold. A project whose root already lists the file takes the human's settings edit on the first, code, branch.
   When `clm upgrade --apply` prints `applied` for the migration "Slow tests can run after the land: offer [verify]" (`upgrade/migration-offer-verify`), which appended the commented `[verify]` section to `clm.toml`, ask the human the questions `/clm:init` asks about slow tests (`init-skill-asks-verify`): whether the project has tests too slow to run on every land and, on a yes, the command, where they run (`local`, `pipeline` or `import`) and the triggers, recommending `change-done`. On a yes, replace the commented section with those settings on the notes branch, keep those tests out of `[land] check`, and for `pipeline` and `import` say what the host's pipeline must run, naming `clm guide ci-and-deployment`. On a no, leave the section commented.
5. When `clm upgrade` still lists a `required` migration after `--apply`, or a migration fails, report it with `clm defect --component upgrade`, tell the human that `skip_migrations` in this clone's `clm.local.toml` lets this clone run meanwhile, never setting it without their yes, and stop: land nothing, so `upgraded` never records a project that still has a required migration pending.
6. Run `clm check`.
7. Land in two branches, since mechanical migrations are code and a note's edit is spec, which `clm gate` refuses together as `mixed`. First commit the changes outside spec paths on `upgrade/<YYYYMMDD>`, when there are any, leaving the rest uncommitted. Run `clm gate --base origin/main` and land the branch by its first line, as `propose` lands a branch: `code` lands on checks; push with `clm branch push`, open the pull request with `clm pr open` and run `clm land`. Go by what `clm land` prints; `gate/up-to-date` or a conflict means `clm rebase` until its last line is `rebase ok`.
8. Then add a second worktree from the new `origin/main`, `git worktree add .claude/worktrees/upgrade-<YYYYMMDD>-notes -b upgrade/<YYYYMMDD>-notes origin/main`, make the notes' edits and `clm.toml`'s `upgraded` and `declined_migrations` lines there, run `clm check`, commit and land it the same way. When `clm gate --base origin/main` prints `spec review`, ask for the human's `clm approve` first and run `clm land` on their yes.
9. Delete each pushed branch after it lands with `clm branch delete`, and remove its worktree.
