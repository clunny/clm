description: Build the approved specs (not compile) by draining the work queue with clm run, component by component and in parallel, until clm next is empty. Use when the user wants approved specs built; /clm:build runs the unattended builds, it does not compile.
---

# Build approved changes

Build every ready component, in parallel, each in a background subagent of this session in its own worktree that lands its own branch with `clm land`, and archive the changes that complete (`builds-in-subagents`, `land-locally`).

Before the first build, tell the human once that builds run under this session's permission mode: in manual mode they pause for the human's answers, while auto or bypass mode lets them run alone. Never refuse a mode. A build that writes a protected path, such as `.claude/settings.json`, is built like the rest: Claude Code asks the human before the write.

Once, before the first build you launch (`unattended-permissions-check`), run `clm init --check-permissions`. When it exits 1, tell the human that in auto mode Claude Code may deny the unattended steps those rules allow, show the rules it printed, say that they belong in `permissions.allow` in `.claude/settings.json` (or `.claude/settings.local.json` for this clone alone), and go on launching, never refusing to. When it exits 0, go on. When it exits with any other code, as a `clm` without the option does, tell the human the check couldn't run and go on launching. Never write either file yourself.

What needs the human is in the loop's queue, which `clm view queue` and the CLM panel's Queue tab show until it is resolved: point the human at it rather than keep a question, a stop or a condition only in the chat, and when the human asks what is waiting on them, answer from `clm view queue`.

Run `clm agent-harness` before your first launch (`skills-follow-agent-harness`): it says what this session's agent harness can do. Where `isolated-worktrees` is `no`, add each build's worktree yourself with `git worktree add .claude/worktrees/agent-<component> origin/main` and tell the build, before the launcher `clm run` printed, to work in that directory, so `clm run --finish` and `clm wrap-up` tidy it as they tidy a subagent's `agent-*` worktree. Where `subagents` is `no`, build the components one at a time in this session itself, each in such a worktree. Where `model-choice` is `no`, launch with this session's own model and pass its name as `--review-model`.

Take the queue's state from `clm next`, which fetches `origin` and reads `origin/main`, never from `clm status`, `clm view` or the state the session-start hook printed: those describe this checkout as of its last fetch, which may be an old commit. When they disagree, `clm next` is right, and their checkout line says why (`views-name-their-commit`). Never pull, merge or sync this session's own checkout to bring them up to date: it may hold the human's work in progress. Learn what a build has done from its branch on `origin`, `origin/impl/<component>`, which the build pushes at each sync point, and from `clm wrap-up`, never from a command aimed at the build's worktree, such as `git -C <worktree>`, which Claude Code's worktree isolation refuses.

1. Draft the bugs first, then run `clm next` (`build-drafts-bugs`). Running `/clm:build` is already a yes to unattended work, so you draft the bug groups yourself, as `/clm:triage` drafts a picked `group` line. In each round, before launching builds, run `clm triage`. For each `group` line it prints whose items no draft of this session has taken, in `clm triage`'s order and while a place is free, run `clm draft <slug>...` with the line's items and, only when it exits 0, pass its stdout, unchanged, as the prompt to the Agent tool as a background `general-purpose` subagent with `isolation: "worktree"` and `model` set to the session's own model, the alias of the one your system prompt names (such as `opus`), since a draft designs (`model-per-launch`); when `clm draft` exits 3, launch nothing more for drafts that round. Draft only `group` lines: never pass `--answers`, or a `human`, `idea`, `deferred` or `workaround` line, to `clm draft`, since those need the human and stay `/clm:triage`'s. An item a draft of this session took is not drafted again in this session, even when a draft that left it released its claim and `clm triage` prints it again. Drafts go before builds in a round, since a bug's spec fix can make its component pending, which the same drain then builds. Handle a draft's return by its closing line, as `/clm:triage` does: a draft whose subagent's result ends with a `waiting: <command>` line, or that Claude Code marks as still running background work of its own, hasn't returned unless that line is `landed <sha>` or `proposed <id> review` (`background-work-stopped`); otherwise run `clm draft --finish <id>`, and read `landed <sha>` as landed, `proposed <id> review` as a change left on its branch for review, which joins the list to fold at the end, and `stopped: <reason>` as a stop you tell the user and never retry. Keep each `left <slug>: <reason>` line for the summary. A bug filed while the session watches is drafted at the next drain. Then run `clm next`. It prints the ready components, one per line, most urgent first: the unclaimed components with a pending requirement that no `#### Needs` and no blocking backlog item holds back (`needs-alone-order`, `component-reconciliation`). A component's `depends_on` does not order builds, so never wait for, or explain the queue by, a component's dependencies being built. It prints at most as many as the clone has free build places (`build-places`), so launch builds only for the components the latest `clm next` printed, never for a component you remember from an earlier one. A `clm next` that prints nothing and writes a `no free build place` line to stderr (`orchestrator/next`) means the places are full, not that the queue is empty: treat it as no free place, as for `clm run` exiting 3 below, and never tell the human nothing is left to build.
2. Build each component it prints: run `clm run <component> --review-model <alias>`, and only when it exits 0, pass its stdout, unchanged, as the prompt to the Agent tool as a background `general-purpose` subagent with `isolation: "worktree"` and `model: "sonnet"`, one per component, all in parallel; `<alias>` is the alias of the session's own model, the one your system prompt names (such as `opus`), on which the build's final review runs (`model-per-launch`). `clm run <component>` claims the component, or picks up its unfinished build, and prints the prompt for a build that switches to `impl/<component>`, builds the component's pending requirements highest priority first, test-first, syncs at each step, reviews the work, opens the branch's pull request and lands it with `clm land`. When `clm run` exits 3, the clone has no free place, which another session's builds or drafts on this clone can cause: launch nothing for that component, and wait for one of your own builds to return. When no place is free, whichever of the two said so (`clm run` exiting 3 or `clm next`'s `no free build place` line), and none of your own builds is running, tell the human the cap is reached and by how many places, naming the `max_builds` setting in `clm.local.toml`, and that other sessions' builds or drafts on this clone may hold the places, then run step 5 as at any drain, its summary saying the cap is reached in place of an empty queue, so the wrap-up runs and the offer to watch (step 6, whose `clm next --wait` waits for a place to free as it waits for work) follows. When it exits 1 or 2, tell the user what it printed and launch nothing for that component. Never do a component's work in your own context.
3. When a subagent returns, landed or stopped, first run `clm run --finish <component>` in this checkout (after the `TaskStop` rule below, for a landed build still marked as running), before retrying or launching anything else for that component, but not for a build you resume instead (`resume-sound-builds`, below), such as one a usage or rate limit cut off: it frees the build's place and, once the branch has landed, removes the build's worktree, so disk stays bounded by the cap. Pass each `left <path>: ...` line that `clm run --finish` prints to the human as it stands, a worktree it couldn't remove, and go on, leaving the directory, and any command that line names, to them. Then read its closing line: `landed <sha>` means the component's branch is on `main`. `clm next` may list the component again at once: its spec may have moved, or the build may have stopped at its budget with work left pending, and either is just the next build. `stopped: <reason>`: tell the user the reason. A build whose subagent's result ends with a `waiting: <command>` line, or that Claude Code marks as still running background work of its own, hasn't returned, whatever its last line says, a `stopped:` line included, unless that line is `landed <sha>` (`background-work-stopped`): it is waiting for a command it started, such as its own `clm land`, and finishing it would free its place and remove its worktree while that command runs. This rule comes before the rule for a subagent that ends without a closing line. For such a build, don't run `clm run --finish <component>`, don't tell the human it stopped and don't build the component again; count it as one of your own builds still running, for the cap and for when `clm next` is due again. Handle the subagent's next result, which arrives once that command has ended, as the build's return. The exception is a `landed <sha>` line: its land has ended, so a build that returns it while Claude Code still marks it as running background work of its own has returned, and what still runs is a leftover task the build failed to stop, against `background-work-stopped`. Before you run `clm run --finish <component>` for it, stop that subagent with `TaskStop`, by the task ID its notifications carry, loading the tool with `ToolSearch` first when it is deferred, so the leftover task neither runs on in the worktree the finish removes nor wakes this session later. When `TaskStop` fails because the subagent has already ended, go on. Then read the build's `landed <sha>` line as for any landed build. When a build's subagent returns `stopped: <reason>`, or a usage or rate limit error from the API in place of a closing line of its own, first judge by why it stopped whether to resume that same subagent or build the component again (`resume-sound-builds`), a rule that comes before the rule for a subagent that ends without a closing line and before the retry below. Resume a build whose work is sound and whose stop came from outside the work, such as a usage or rate limit, a full disk, a network outage, or a tool or host failure that has passed. Resume a build stopped by a usage or rate limit or a full disk each time that cause stops it and clears, and never build it again for it: the limit's reset or the human's word that the disk is freed bounds each resume. Resume at most once for the same reason a build whose stop could lie in the work itself, such as a check or test that keeps failing, or that you resume at once, a network outage or a tool or host failure that had already passed when it stopped, since such a cause that keeps coming back may be the work's; its second such stop is the retry's first. Build again, with the retry below, a build that went wrong in its approach or ran out of context. Neither resume nor build again one that stopped blocked on a backlog item or a spec change. When the same outside cause stops builds again, tell the human it recurred and act on what brings it back where you can, such as parallel builds and their land checks filling the disk or reaching a limit: resume the builds you stopped one at a time and launch no new build until they have returned. For a build you resume, don't run `clm run --finish <component>`, and count it as one of your own builds still running, for the cap and for when `clm next` is due again. Tell the human why it stopped and, when only they can clear the cause (such as freeing disk), what to clear. Resume it once the cause has cleared: after the limit has reset, on your first turn after the human says they cleared it (such as their next message), or at once for a failure that has already passed. Resume it with `SendMessage`, loading the tool with `ToolSearch` first when it is deferred, telling it why it stopped, that the cause has cleared, to carry on where it was in its own worktree, and to run again any review or check subagent of its own that the stop killed, since that one will never report back. Handle the resumed build like any other when it returns. When `SendMessage` returns an error or the subagent no longer exists, count it as a stop, run `clm run --finish <component>` and build the component again with the retry below, and never retry the resume itself. A subagent that ends without a closing line of its own, neither `landed <sha>` nor `stopped: <reason>` (for example out of context, or after an earlier result that ended with `waiting: <command>`), and isn't one the `waiting:` rule or the resume rule above holds back, is judged by what `clm run --finish <component>` printed for it, which you run for that build as for any other return, never by reading `origin` with a `git` command of your own (`unclosed-build-reads-finish`): when that output holds the line `landed impl/<component>`, the build landed, so tell the human that it landed without its closing line, don't count it as a stop, don't build it again for that, and, as after any landed build that returns, run `clm next` again. Otherwise it keeps its claim and what it pushed: tell the user; it counts as a stop, retried as follows. A build that stopped without landing and isn't one you resume above, unless it stopped blocked on a backlog item or a spec change, is built again the same way, with `clm run <component> --review-model <alias>` and a new subagent, but launched with `model` set to the session's own model in place of `"sonnet"`, until it lands or stops twice in a row for the same reason, then tell the user. The new build resumes on the component's branch, starts with `clm rebase` and lands it (`versioned-markers`); a spec that moved under the work is what its `clm rebase` reports as `spec changed`, and it handles it.
4. After each build or draft returns and is finished, run `clm next` again and build what it prints, from step 1. Repeat until `clm next` prints nothing, with no `no free build place` line on stderr, `clm triage` prints no `group` line whose items no draft of this session has taken, and none of your builds or drafts is left (that line is the cap in step 2, not a drained queue): a landed component may only free the requirements whose `#### Needs` name its requirements.

5. At the end, once every build and draft has returned, first fold the changes your own drafts left for review, and only those, when the list isn't empty, as `/clm:triage`'s fold and approval steps do: run `clm draft --fold <id>...` with their IDs in the order of the `group` lines they came from, pass its stdout, unchanged, as the prompt to one background `general-purpose` subagent with `isolation: "worktree"` and `model: "sonnet"`, and on its `proposed <batch> review <url>` ask the human once, in this conversation (`approve-in-session`), whether they approve the intent of every folded change, showing the link and each change's `## Intent`, `## Decisions` and `## Open questions`. On a yes, run `clm approve spec/<batch>`, which the guard has them confirm, then `clm land spec/<batch>`, and `clm draft --finish <id>` for each folded draft once it has landed; never approve or land a change a draft left for review otherwise. Left one by one, those changes would go stale against each other as each landed. You ask nothing mid-drain, and only when a draft needed review (`humans-review-intent`). A bug the builds reported is a `kind: bug` item like the rest, so it is drafted by the next round and has no step of its own here.

   Then, once every land is done, run `clm verify --due --event work-done` and show the human its `verify` line; a `verify failed` line is a slow test that broke on `main`, which the next triage takes in (`verify-after-land`); whatever it exits, go on to the wrap-up.

   Then run `clm wrap-up` (`checkpoint-before-done`). It removes landed work and reports what isn't safe on `origin`; fix what it reports and run it again. Pass each `left <path>: ...` line `clm wrap-up` prints to the human as it stands, a build's worktree it couldn't remove, which doesn't make the wrap-up incomplete, and leave the directory, and any command the line names, to them. When it prints `complete <id>` lines, archive those changes on one code branch you land, `impl/archive/<id>`, `<id>` the first change it lists `complete`, cut from `origin/main` in a worktree of its own (`archive-branches`, `session-worktrees`; a session isolated under `.claude/worktrees/` cuts it in its own checkout instead, with `git switch -c impl/archive/<id> origin/main`, removes no worktree, and switches the checkout off the branch with `git switch --detach origin/main` once it has landed, or its push was refused, before `git branch -D` and before `clm wrap-up`), where `clm rebase` archives every complete change and deletes the items they resolve (`archive-on-sync`), and land it with `clm land`. First remove a leftover `.claude/worktrees/archive` whose branch has landed, with `git worktree remove .claude/worktrees/archive`; when another session's `impl/archive/<id>` is still unlanded on `origin`, leave archiving to that branch, whose `clm rebase` archives every complete change, and say so. Otherwise:
   - unless isolated (above), run `git worktree add .claude/worktrees/archive -b impl/archive/<id> origin/main` and change into `.claude/worktrees/archive`;
   - run `clm rebase` until its last line is `rebase ok`, and push the branch with `clm branch push`. When the push is refused because `impl/archive/<id>` already exists on `origin`, another session is archiving the same changes: change back, remove the worktree, delete your local branch with `git branch -D`, since its archive commits are merged nowhere, and leave the archive to that session;
   - open its pull request with `clm pr open impl/archive/<id> --title <title> --body-file <file>`, writing the body under `.clm/`, and land it with `clm land impl/archive/<id>`;
   - once it has landed, change back to the directory you started in and remove the worktree with `git worktree remove .claude/worktrees/archive`; when that refuses, say so and leave it, never forcing it. Then run `clm wrap-up` again, and after the archive branch has landed run `clm triage` again: when it prints a `group` line whose items no draft of this session has taken, go back to step 1.

   The branch name has a `/` after `impl/`, which no component ID has, so the queue never reads it as a claim.

   Whether or not there was anything to archive, end with a summary: what landed, what is still open and who it waits on, the `question` and `human-task` backlog items that block requirements, with the requirements they block (take them from `clm pending --at origin/main`, run after `clm next` has fetched, and not from `clm pending` without `--at`, which describes this checkout), so the human knows what's waiting on them, each `workaround` item and each `reconsider-<component>-<slug>` question the builds filed, pointing at `/clm:health` for the whole picture, and any spec branches waiting for approval. Once the checkpoint exits 0, add a line saying everything is saved and the session can be ended or cleared. If it can't pass for a reason you can't fix, say what and why instead of that line.

6. **Watch for new work** (`next-wait`). Once step 5 has ended with its summary, `clm next` prints nothing (or only the `no free build place` line, a full cap) and none of your builds is left, offer the human once per session to watch for new work. On a yes, run `clm next --wait` as a background Bash command (`run_in_background`), which wakes the session when it exits. When it exits 0, start again at step 1, taking the queue from a fresh `clm next` and not repeating the notice given before the first build. When it exits non-zero, tell the human what it printed and stop watching. The watch stays on for the rest of the session, so after each later drain you run step 5 again, its summary saying the session is watching and that the human can say to stop, and run `clm next --wait` again without asking, answer the human's messages meanwhile and keep watching. When the human says to stop, stop the background command (`TaskStop`) and run nothing more. The watch is no setting and does not outlive the session.

When you resolve what `clm rebase` leaves you yourself, do it the way the builds do: a `spec changed` report by reading it and `clm pending <component>`, and adapting the work; conflicted files by hand (then `git add` them); stale deltas by rebasing them on `clm hashes`; check failures by fixing them. When `clm land` reports `gate/up-to-date` or a conflict, run `clm rebase`, resolve, push with `clm branch push` and land again; on a check failure, fix, push with `clm branch push` and land again. Never touch a worktree a build is still working in: `clm run --finish <component>` removes a build's worktree.

Before opening any pull request yourself, review the session for CLM defects neither reported nor fixed (`defect-reports`): anything CLM itself (its CLI, gate rules, plugin, skills or method) would have to change so it doesn't happen again, not your own mistakes that CLM caught or you fixed. Report each with `clm defect --title <title> [--component <component>]...`, naming with `--component` the component a fix would lie in, the report on stdin, describing only the process, never the project's files, code, specs or output, unless the session-start rule has it folded into the branch, and list every defect of the session under `## CLM defects` in the pull request body, each fixed one with its fix. Each build lists its own under `## CLM defects` in its pull request body.

Stop and tell the user when a component keeps stopping after its retries, or a component is blocked on a spec change or a backlog item, and end with step 5's summary. When the human tells you to give up a component's build for good, release its claim by deleting `impl/<component>` on `origin` with `clm branch delete`.

Never push `main` by any means but `clm land`. Run `clm approve` only after the human says yes in this conversation, and only through the guard's confirmation: never route around the guard or ask another tool to do it. Only a human approves a spec change (`humans-review-intent`).
