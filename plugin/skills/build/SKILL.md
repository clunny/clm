description: Build the approved specs (not compile) by draining the work queue with clm run, component by component and in parallel, until clm next is empty. Use when the user wants approved specs built; /clm:build runs the unattended builds, it does not compile.

# Build approved changes

Build every ready component, in parallel, each in a background subagent of this session in its own worktree that lands its own branch with `clm land`, and archive the changes that complete (`builds-in-subagents`, `land-locally`).

Before the first build, tell the human once that builds run under this session's permission mode: in manual mode they pause for the human's answers, while auto or bypass mode lets them run alone. Never refuse a mode. A build that writes a protected path, such as `.claude/settings.json`, is built like the rest: Claude Code asks the human before the write.

Once, before the first build you launch (`unattended-permissions-check`), run `clm init --check-permissions`. When it exits 1, tell the human that in auto mode Claude Code may deny the unattended steps those rules allow, show the rules it printed, say that they belong in `permissions.allow` in `.claude/settings.json` (or `.claude/settings.local.json` for this clone alone), and go on launching, never refusing to. When it exits 0, go on. When it exits with any other code, as a `clm` without the option does, tell the human the check couldn't run and go on launching. Never write either file yourself.

Take the queue's state from `clm next`, which fetches `origin` and reads `origin/main`, never from `clm status`, `clm view` or the state the session-start hook printed: those describe this checkout as of its last fetch, which may be an old commit. When they disagree, `clm next` is right, and their checkout line says why (`views-name-their-commit`). Never pull, merge or sync this session's own checkout to bring them up to date: it may hold the human's work in progress. Learn what a build has done from its branch on `origin`, `origin/impl/<component>`, which the build pushes at each sync point, and from `clm wrap-up`, never from a command aimed at the build's worktree, such as `git -C <worktree>`, which Claude Code's worktree isolation refuses.

1. Run `clm next`. It prints the ready components, one per line, most urgent first: the unclaimed components with a pending requirement that no `#### Needs` and no blocking backlog item holds back (`needs-alone-order`, `component-reconciliation`). A component's `depends_on` does not order builds, so never wait for, or explain the queue by, a component's dependencies being built. It prints at most as many as the clone has free build places (`build-places`), so launch builds only for the components the latest `clm next` printed, never for a component you remember from an earlier one.
2. Build each component it prints: run `clm run <component> --review-model <alias>`, and only when it exits 0, pass its stdout, unchanged, as the prompt to the Agent tool as a background `general-purpose` subagent with `isolation: "worktree"` and `model: "sonnet"`, one per component, all in parallel; `<alias>` is the alias of the session's own model, the one your system prompt names (such as `opus`), on which the build's final review runs (`model-per-launch`). `clm run <component>` claims the component, or picks up its unfinished build, and prints the prompt for a build that switches to `impl/<component>`, builds the component's pending requirements highest priority first, test-first, syncs at each step, reviews the work, opens the branch's pull request and lands it with `clm land`. When `clm run` exits 3, the clone has no free place, which another session's builds or drafts on this clone can cause: launch nothing for that component, and wait for one of your own builds to return. When no place is free and none of your own builds is running, tell the human the cap is reached and by how many places, naming the `max_builds` setting in `clm.local.toml`, and stop. When it exits 1 or 2, tell the user what it printed and launch nothing for that component. Never do a component's work in your own context.
3. When a subagent returns, landed or stopped, first run `clm run --finish <component>` in this checkout (after the `TaskStop` rule below, for a landed build still marked as running), before retrying or launching anything else for that component, but not for a build you resume instead (`resume-sound-builds`, below), such as one a usage or rate limit cut off: it frees the build's place and, once the branch has landed, removes the build's worktree, so disk stays bounded by the cap. Pass each `left <path>: ...` line that `clm run --finish` prints to the human as it stands, a worktree it couldn't remove, and go on, leaving the directory, and any command that line names, to them. Then read its closing line: `landed <sha>` means the component's branch is on `main`. `clm next` may list the component again at once: its spec may have moved, or the build may have stopped at its budget with work left pending, and either is just the next build. `stopped: <reason>`: tell the user the reason. A build whose subagent's result ends with a `waiting: <command>` line, or that Claude Code marks as still running background work of its own, hasn't returned, whatever its last line says, a `stopped:` line included, unless that line is `landed <sha>` (`background-work-stopped`): it is waiting for a command it started, such as its own `clm land`, and finishing it would free its place and remove its worktree while that command runs. This rule comes before the rule for a subagent that ends without a closing line. For such a build, don't run `clm run --finish <component>`, don't tell the human it stopped and don't build the component again; count it as one of your own builds still running, for the cap and for when `clm next` is due again. Handle the subagent's next result, which arrives once that command has ended, as the build's return. The exception is a `landed <sha>` line: its land has ended, so a build that returns it while Claude Code still marks it as running background work of its own has returned, and what still runs is a leftover task the build failed to stop, against `background-work-stopped`. Before you run `clm run --finish <component>` for it, stop that subagent with `TaskStop`, by the task ID its notifications carry, loading the tool with `ToolSearch` first when it is deferred, so the leftover task neither runs on in the worktree the finish removes nor wakes this session later. When `TaskStop` fails because the subagent has already ended, go on. Then read the build's `landed <sha>` line as for any landed build. When a build's subagent returns `stopped: <reason>`, or a usage or rate limit error from the API in place of a closing line of its own, first judge by why it stopped whether to resume that same subagent or build the component again (`resume-sound-builds`), a rule that comes before the rule for a subagent that ends without a closing line and before the retry below. Resume a build whose work is sound and whose stop came from outside the work, such as a usage or rate limit, a full disk, a network outage, or a tool or host failure that has passed. Build again, with the retry below, a build that went wrong in its approach, ran out of context, or stopped for the same reason it was already resumed for: a build is resumed at most once for the same reason, and its second such stop is the retry's first. Neither resume nor build again one that stopped blocked on a backlog item or a spec change. For a build you resume, don't run `clm run --finish <component>`, and count it as one of your own builds still running, for the cap and for when `clm next` is due again. Tell the human why it stopped and, when only they can clear the cause (such as freeing disk), what to clear. Resume it once the cause has cleared: after the limit has reset, on your first turn after the human says they cleared it (such as their next message), or at once for a failure that has already passed. Resume it with `SendMessage`, loading the tool with `ToolSearch` first when it is deferred, telling it why it stopped, that the cause has cleared, to carry on where it was in its own worktree, and to run again any review or check subagent of its own that the stop killed, since that one will never report back. Handle the resumed build like any other when it returns. When `SendMessage` returns an error or the subagent no longer exists, count it as a stop, run `clm run --finish <component>` and build the component again with the retry below, and never retry the resume itself. A subagent that ends without a closing line of its own, neither `landed <sha>` nor `stopped: <reason>` (for example out of context, or after an earlier result that ended with `waiting: <command>`), and isn't one the `waiting:` rule or the resume rule above holds back, is judged by what `clm run --finish <component>` printed for it, which you run for that build as for any other return, never by reading `origin` with a `git` command of your own (`unclosed-build-reads-finish`): when that output holds the line `landed impl/<component>`, the build landed, so tell the human that it landed without its closing line, don't count it as a stop, don't build it again for that, and, as after any landed build that returns, run `clm next` again. Otherwise it keeps its claim and what it pushed: tell the user; it counts as a stop, retried as follows. A build that stopped without landing and isn't one you resume above, unless it stopped blocked on a backlog item or a spec change, is built again the same way, with `clm run <component> --review-model <alias>` and a new subagent, but launched with `model` set to the session's own model in place of `"sonnet"`, until it lands or stops twice in a row for the same reason, then tell the user. The new build resumes on the component's branch, starts with `clm rebase` and lands it (`versioned-markers`); a spec that moved under the work is what its `clm rebase` reports as `spec changed`, and it handles it.
4. After each build returns and is finished, run `clm next` again and build what it prints, from step 2. Repeat until `clm next` prints nothing and no build is left: a landed component may only free the requirements whose `#### Needs` name its requirements.

5. At the end, once every build has returned, and when `clm defect` writes to the backlog (the session-start rule says so), first **fix reported defects**, before `clm wrap-up` and the summary: fix each small defect this session or its builds reported (their closing messages and pull requests list them under `## CLM defects`) whose item is on `origin/main`, one at a time and one round only, as `propose`'s code fixes do, with `clm claim <component> --fix backlog/<slug>`, in a worktree of your own added with `git worktree add --detach .claude/worktrees/defects origin/main` (first removing a leftover `.claude/worktrees/defects` as you remove the archive's below; when that refuses, say so and fix nothing), never in the checkout the session started in, unless the session is isolated under `.claude/worktrees/` (`session-worktrees`; `git rev-parse --show-toplevel` says so, as in `propose`'s step 1), where you make the fixes in the checkout you have instead: switch it with `git switch --detach origin/main` before each `clm claim <component> --fix backlog/<slug>`, add and remove no worktree, and once each fix has landed, or its claim or push is refused, switch it off the branch with `git switch --detach origin/main`, before deleting a refused branch with `git branch -D` and before `clm wrap-up`. Fold a defect you meet during such a fix when it lies in that fix's component, and leave it filed otherwise. When a claim is refused or a fix turns out large, leave the item filed, release a claim you took by deleting its branch on `origin` with `clm branch delete` and, after `git switch --detach origin/main`, the local branch with `git branch -D`, and name the item in the summary. When the fixes are done, change back and remove that worktree as you remove the archive's below (an isolated session has no worktree to remove). The fix branch's pull request lists the defect as fixed; the landed pull request that reported it isn't edited.

   Then, once every land is done, run `clm verify --due --event work-done` and show the human its `verify` line; a `verify failed` line is a slow test that broke on `main`, which the next triage takes in (`verify-after-land`); whatever it exits, go on to the wrap-up.

   Then run `clm wrap-up` (`checkpoint-before-done`). It removes landed work and reports what isn't safe on `origin`; fix what it reports and run it again. Pass each `left <path>: ...` line `clm wrap-up` prints to the human as it stands, a build's worktree it couldn't remove, which doesn't make the wrap-up incomplete, and leave the directory, and any command the line names, to them. When it prints `complete <id>` lines, archive those changes on one code branch you land, `impl/archive/<id>`, `<id>` the first change it lists `complete`, cut from `origin/main` in a worktree of its own (`archive-branches`, `session-worktrees`; a session isolated under `.claude/worktrees/` cuts it in its own checkout instead, with `git switch -c impl/archive/<id> origin/main`, removes no worktree, and switches the checkout off the branch with `git switch --detach origin/main` once it has landed, or its push was refused, before `git branch -D` and before `clm wrap-up`), where `clm rebase` archives every complete change and deletes the items they resolve (`archive-on-sync`), and land it with `clm land`. First remove a leftover `.claude/worktrees/archive` whose branch has landed, with `git worktree remove .claude/worktrees/archive`; when another session's `impl/archive/<id>` is still unlanded on `origin`, leave archiving to that branch, whose `clm rebase` archives every complete change, and say so. Otherwise:
   - unless isolated (above), run `git worktree add .claude/worktrees/archive -b impl/archive/<id> origin/main` and change into `.claude/worktrees/archive`;
   - run `clm rebase` until its last line is `rebase ok`, and push the branch with `clm branch push`. When the push is refused because `impl/archive/<id>` already exists on `origin`, another session is archiving the same changes: change back, remove the worktree, delete your local branch with `git branch -D`, since its archive commits are merged nowhere, and leave the archive to that session;
   - open its pull request with `clm pr open impl/archive/<id> --title <title> --body-file <file>`, writing the body under `.clm/`, and land it with `clm land impl/archive/<id>`;
   - once it has landed, change back to the directory you started in and remove the worktree with `git worktree remove .claude/worktrees/archive`; when that refuses, say so and leave it, never forcing it. Then run `clm wrap-up` again.

   The branch name has a `/` after `impl/`, which no component ID has, so the queue never reads it as a claim.

   Whether or not there was anything to archive, end with a summary: what landed, what is still open and who it waits on, the `question` and `human-task` backlog items that block requirements, with the requirements they block (take them from `clm pending --at origin/main`, run after `clm next` has fetched, and not from `clm pending` without `--at`, which describes this checkout), so the human knows what's waiting on them, each `workaround` item and each `reconsider-<component>-<slug>` question the builds filed, pointing at `/clm:health` for the whole picture, and any spec branches waiting for approval. Once the checkpoint exits 0, add a line saying everything is saved and the session can be ended or cleared. If it can't pass for a reason you can't fix, say what and why instead of that line.

6. **Watch for new work** (`next-wait`). Once step 5 has ended with its summary, `clm next` prints nothing and none of your builds is left, offer the human once per session to watch for new work. On a yes, run `clm next --wait` as a background Bash command (`run_in_background`), which wakes the session when it exits. When it exits 0, start again at step 1, taking the queue from a fresh `clm next` and not repeating the notice given before the first build. When it exits non-zero, tell the human what it printed and stop watching. The watch stays on for the rest of the session, so after each later drain you run step 5 again, its summary saying the session is watching and that the human can say to stop, and run `clm next --wait` again without asking, answer the human's messages meanwhile and keep watching. When the human says to stop, stop the background command (`TaskStop`) and run nothing more. The watch is no setting and does not outlive the session.

When you resolve what `clm rebase` leaves you yourself, do it the way the builds do: a `spec changed` report by reading it and `clm pending <component>`, and adapting the work; conflicted files by hand (then `git add` them); stale deltas by rebasing them on `clm hashes`; check failures by fixing them. When `clm land` reports `gate/up-to-date` or a conflict, run `clm rebase`, resolve, push with `clm branch push` and land again; on a check failure, fix, push with `clm branch push` and land again. Never touch a worktree a build is still working in: `clm run --finish <component>` removes a build's worktree.

Before opening any pull request yourself, review the session for CLM defects neither reported nor fixed (`defect-reports`): anything CLM itself (its CLI, gate rules, plugin, skills or method) would have to change so it doesn't happen again, not your own mistakes that CLM caught or you fixed. Report each with `clm defect --title <title> [--component <component>]...`, naming with `--component` the component a fix would lie in, the report on stdin, describing only the process, never the project's files, code, specs or output, unless the session-start rule has it folded into the branch, and list every defect of the session under `## CLM defects` in the pull request body, each fixed one with its fix. Each build lists its own under `## CLM defects` in its pull request body.

Stop and tell the user when a component keeps stopping after its retries, or a component is blocked on a spec change or a backlog item, and end with step 5's summary.

Never push `main` by any means but `clm land`. Run `clm approve` only after the human says yes in this conversation, and only through the guard's confirmation: never route around the guard or ask another tool to do it. Only a human approves a spec change (`humans-review-intent`).
