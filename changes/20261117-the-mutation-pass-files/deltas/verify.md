## MODIFIED Design
**Settings** (`settings-from-main`). `clm verify` verifies `origin/main`, so it reads how to verify it from `origin/main`: the commit it checks out is the one whose settings it follows. It first loads the root's own settings for `host` alone, which names the host adapter, fetches `origin` (every host has one: `none-keeps-its-own-remote`), and then loads the settings again with `config`'s `load_committed`, the repository layer being the text of `origin/main:<prefix>clm.toml` (none when `origin/main` or the file is missing) and its source `origin/main:clm.toml`. `[verify]`, `[affected] all` and `[land] target_cap_gb`, the cap on verify's build place (`verify-build-cap`), come from those; the clone's `clm.local.toml` still sets either for this clone, as everywhere (`local-settings`), since it belongs to the clone and is never behind. Whether `[verify]` is set is decided only after the fetch, so a project with no `[verify]` pays one fetch per call; a fetch that fails is exit 2 as for any other call. The sessions that run `clm verify --due --event work-done` at their end run it in their own checkout, which they leave as it is and which may be far behind `main`: reading the checkout's file there skipped every run with `verify off` once `[verify]` had landed after the checkout was made. `host` stays the root's, as `land` keeps it (`land-policy-from-base`): it is needed before there is anything fetched to read, and names the tooling, not the policy. This is the decision `verify-settings-from-main`.

**Since when.** The *last verified commit* is the newest commit on `origin/main`'s first-parent chain that a `verified` record names, whatever its result; the *last green commit* the newest that one with `passed: true` names. The *unverified lands* are the first-parent commits of `origin/main` after the last verified commit, up to its head, or all of them when no record exists. A run's tests are selected by `check.affected`'s library call with the last green commit as its base, as `clm affected --base <last green commit>` selects them (`graph-test-selection`), written to a file and handed to the check as `CLM_SELECTION` as `[land] check` gets it, so a run covers everything changed since the tests last passed, the lands of an earlier red run included; with no green record there is no selection and every test runs.

**Triggers** (`verify-due`). Read from `[verify] triggers` and `[verify] every` over the unverified lands: `change-done` when one of them adds a `changes/archive/<id>/change.md` (`git diff --diff-filter=A` against its first parent); `queue-drained` when every requirement `check.coverage`'s `pending` returns for `origin/main`'s head, checked out into the verify tree, is blocked, its `blocked_by` or its `waits_on` holding something, so also when it returns none (computed only when `queue-drained` is among the triggers): a blocked requirement waits on a human's answer or on other work, which no build is about to do, and one of a component under a live claim is still pending and unblocked in `origin/main` until its build lands, so the trigger reads no claim and waits for that land. A spec graph with violations leaves the queue unknown, and the trigger doesn't hold; `work-done` when the caller passed `--event work-done`; `every.lands` when there are at least that many; `every.days` when the oldest of them was committed at least that many days ago. A red last record makes any unverified land a trigger (`red-again`), since a fix may have landed. No unverified land means nothing is due, whatever else holds.

**The run** (`verify-run`). It checks `origin/main`'s head out into `<home>/.clm/verify-tree` as `land` keeps its land tree (`fixed-land-tree`), `<home>` found as `land` finds it, and runs `[verify] check` there through `land`'s shared check runner (`land/shared-check-runner`), so under the clone's check lock, `<home>/.clm/check.lock`, like every other check of the clone (`check-runs-one-at-a-time`): CLM can't know what a project's tests share, so a slow run and a land's check never overlap. A land on the same clone waits while a slow run's check runs; triggers make that rare, and a project that can't accept the wait runs its slow tests in `pipeline` mode or from another clone. Each bisect probe takes the lock afresh, so lands can go between probes. **Build place** (`verify-build-dir`, `verify-build-cap`). Every run of `[verify] check`, a bisect probe's included, gets `CLM_LAND_DIR` set to `<home>/.clm/verify-build`, as a land's check gets `.clm/land` (`land/land-dir-env`): a place that lasts from run to run outside the verify tree, so a check script that points its toolchain there for lands (`init/starter-check-land-dir`) does so for verify too, with incremental compilation off. Build output kept inside the verify tree, which keeps what git ignores from run to run, grew without bound: 27 GB on one clone, 15 GB of it incremental data no run between whole commits reuses. Verify sets no toolchain's variables itself. After each run of the check, still holding the verify tree's lock (`verify.lock`), so no other verify run is building there, it applies `land`'s cap to that place through `land/shared-target-cap`, named `.clm/verify-build` and capped at `[land] target_cap_gb` from the settings it follows (`settings-from-main`), printing its line on stderr as the check's other notes go; a warning from the cap never changes the run's record or exit status. Cargo prunes no unit no run builds again, so the cap trades one cold run for a bounded place, as the land's does. Its output goes to stderr and to `<home>/.clm/verify-logs/<sha>.log`, which a passing run removes and a failing one keeps. `local` and `pipeline` differ only in where the project calls it: `pipeline` is a host pipeline running `clm verify --due` on each push to `main`, with `CLM_WRITER` naming it and the right to push `clm/ledger/*`. A run killed before it records leaves its trigger due. **Output** (`verify-run`). Once the check has exited, nothing `clm verify` writes can lose its result. Every write to stderr before the record (the verify tree's waiting line, a failed selection's `clm affected failed` note, the check runner's waiting line and log warning, and each bisect probe's output and lines) ignores a failure, as the runner's copy of the check's output already does, and nothing goes to stdout before it: the outcome line and the notes are printed only after the record is appended, so a stdout whose reader has gone (`clm/closed-stdout`), or a stream on a full disk, ends the command with the verdict already in the ledger. A failed write before the check exits ends nothing either, since ending then would leave the check running unwatched in the verify tree. The check's output is still copied to stderr, so a person watching a run sees it progress; the log holds it whole. `clm verify --commit <sha>` for a commit other than the head takes the last verified commit before it as its `since` and checks that commit out.

**Import** (`verify-import`). `host`'s `runs` for `[verify] workflow` (`host/list-runs`), each with its head commit, whether it completed and its conclusion. A completed run whose conclusion is `success` or `failure` on an unverified land is a result; the newest such run's commit is the one recorded, covering the unverified lands up to it, `passed` from its conclusion and `run` its URL. Any other conclusion (cancelled, skipped) is no result. With none, `verify pending <head>`, exit 4.

**Culprits and components** (`verify-bisect`). A red result over one unverified land names that land as the culprit. Over several, `local` and `pipeline` runs bisect at once: a search of the first-parent lands between the last green commit (exclusive) and the red one, each probe running the same selection in the verify tree, the first red land being the culprit; `import` records `culprit: null` and leaves the search to `clm verify --bisect <sha>` on a developer's machine, which appends a fresh red record for the same commit with what the search found. **Untestable lands.** A probe whose `[verify] check` exits 125, 126 or 127 could not test its land: 126 and 127 are `sh`'s own codes for a command it found but could not run and one it could not find, as on a commit older than the project's slow-test script, and 125 is the code `git bisect run` already gives a script for "this commit can't be tested", so a project's script can say so without CLM inventing a convention (`reuse-first`). Such a land is set aside, neither green nor red. The search keeps a range of lands `lo..hi`, `hi` the red one (at first the red commit itself) and every land before `lo` in the range known green; it probes the land in `lo..hi` (`hi` excluded) not set aside that is nearest `lo + (hi - lo) / 2` (rounded down), the later of two equally near, moving `lo` past a green probe and `hi` to a red one, until no such land is left. When `lo` is `hi`, that land is the culprit. Otherwise every land from `lo` to `hi` but the last was set aside and any of them may hold the break, so the culprit is unknown, and stderr says, after the outcome line, `culprit unknown: [verify] check could not run on <n> lands, <short lo> to <short hi-1>, before the first red one, <short hi>`. The search assumes, as `git bisect` does, that a land after a red one stays red; to conclude it is unknown it must probe every land it set aside, each a checkout and a check that ends at once. The record's components are those whose `paths` hold a file the culprit's first-parent diff changes, or, with no culprit, a file any of the lands that may hold it change: those from `lo` to `hi` when the search left it unknown, and in `import` mode, which searches nothing, the covered lands. A land with no first parent (the repository's first commit) diffs against the empty tree. When no component's `paths` hold such a file (a land that changed only doc-only paths), the root component.

**What it stops.** A red record is a report: `clm intake` lists it for triage (`orchestrator.triage/intake-verify-failures`) and `clm land` warns a branch touching its components. Once the human takes it in as a `kind: bug` item with `verify_failures`, `clm land` holds code lands on the item's components until a branch whose commit carries `Resolves: backlog/<slug>` for it lands, letting through meanwhile a branch that resolves another item holding the same component (`land/verify-stop`). A host's run never holds a land by itself (`land-locally`).

**The mutation pass** (`mutation-pass`, `mutation-after-land`). A marker says which test claims a requirement, and the land's check says the test passed; neither says the test would fail if the code were wrong. Mutation says that, and it is slow, so it runs here, after the land. CLM names no tool: the project's `[verify] mutate` command gets a plan and writes verdicts, as `[land] check` gets a selection, and it is unset unless the project sets it. A requirement is *due* when one of its citing tests was added, or changed in more than its markers, since the last pass, so a requirement that was only re-cited isn't judged: its tests are the ones an earlier pass saw, or none did, and a sample of mutants drawn from a whole component can't judge it either, since on 2026-11-14 seventeen mutants of `clm-coverage` were noticed by the tests of seven of its ten requirements often and by those of three almost never, all ten sound. The plan therefore hands the command the code the lands changed first, and a limit of 20 further mutants from the rest of the component, a constant (`yagni`). Of both, the command tries only mutants of lines the requirement's tests run (`ci/mutate-script`), since a mutant of code they never reach is one no citing test could notice: on 2026-11-16 the first 20 mutants of `clm-config` were `Display` impls and getters that the tests of `config/unreferenced-detector`, whose rule is data in `clm.toml`, never run, and the pass would have filed those sound tests as unproven. A requirement whose tests run lines of its code but none a mutant changes, as when its rule is data, is not judged; one whose tests run none of its code, as an empty test, still reads as unproven, unless a file holding one of its citing tests carries a `clm:reads` marker (`check.affected`). Such a test reads the repository's own files, and the rule it proves can be data there that no `code` line holds and no mutation tool changes: `clm/doc-readers-marked`'s rule is the markers themselves, in test files of half a dozen crates, and its tests run `clm-affected`'s `readers`, none of the root's code, so the pass filed those sound tests as unproven twice, on 2026-11-16 and 2026-11-17, each time a build's look and a land of no code, and would again whenever they change. The plan names each such marker's glob on a `reads` line, so the command can tell a test that reads data from an empty one, and leaves the requirement not judged (`ci/mutate-script`). An empty test in a file that carries a marker escapes so; the marker is a declaration a reviewer reads, and a file that reads nothing has no reason to carry one. Tests that predate the pass are never judged (`backlog/tests-written-before-the-mutation-pass-were-never-judged`). The pass runs after the `verified` record is appended and the outcome line printed, and outside the check lock, so it can lose no verdict and hold no land; it keeps the verify tree's lock, so two passes never share the tree, and it gets slots of its own, from one past the build places up to `mutate_jobs` of them, one for each requirement it judges at once, since its tests overlap lands' checks and builds' (`check-runs-one-at-a-time` covers the runs that share slot 0, which this one doesn't). It judges up to `mutate_jobs` requirements at once, cut down to one per 2 GiB of available memory, since each concurrent build of a crate's tests takes one to two gigabytes and the build loop often runs builds beside a verify. A requirement an item named is not judged again when the item goes: the build that mended its test changed the test, which makes it due, and the build that found the test sound and deleted the item has settled it. A pass keeps what it reached however it ends: the command writes each verdict as it is reached, and when it fails, reaches `mutate_minutes`, or is stopped, `clm verify` records the verdicts written and names the due requirements it didn't reach under `left`, which the next pass judges first, with the diff from where they were first due (2026-11-16: four passes that each recorded nothing had restarted a day's requirements from the first, and a pass of 219 requirements ran over two hours with no limit). A pass killed with `clm verify` itself, by `SIGKILL`, still records nothing, and the next pass starts from the same commit. The crate's call takes the path it reads available memory from, the length of a minute and of the grace before `SIGKILL`, and a stop request, which `clm` passes as `/proc/meminfo`, 60 and 10 seconds and a flag its signal handler sets (`verify-command`), so its tests pass a file, short lengths and a set flag; a stop or the limit can end the command before `coverage.sh` runs, which leaves `[health] lcov` as the last whole pass wrote it.

**Filing** (`files-unproven`). Verify pushes nothing to `main`, so a verdict reaches the tree as a backlog item, landed through `clm land` like any branch: adding a new item lands on checks. What is still to file is found each time from the ledger and from `main`'s history, not remembered: an item is named after the commit of the record that found it, so a filing that failed is made by the next `clm verify --due` on a clone in `local` mode, and an item a build has resolved is not filed twice. A pipeline has the right to push only the ledger, so `pipeline` mode records and leaves the filing to such a clone.

## MODIFIED Requirements

### Requirement: mutation-pass <!-- base: 1dea303f672e0680 -->
When the settings it follows (`settings-from-main`) set `[verify] mutate`, a `clm verify --due` or `clm verify --commit` in `local` or `pipeline` mode whose check passed SHALL, after appending the `verified` record and printing the outcome line, and holding the verify tree's lock but not `.clm/check.lock`, run the mutation pass on the commit `C` it verified. With `P` the commit the newest `mutated` record on `C`'s first-parent chain names, or, when there is none, the first parent of the oldest commit of the unbroken run of commits ending at `C` on that chain whose `clm.toml` sets `[verify] mutate`, which is the last commit before the project switched the pass on, a requirement is *due*; a commit sets it when its `clm.toml` parses as TOML and holds a non-empty string there, and any other commit ends the run when, between the trees of `P` and `C`, a test citing it at its current version in `C` (`check.coverage/test-spans`, groups left out) was added, or its lines changed in more than their markers; with no `P`, as when the chain's first commit already sets `mutate`, every requirement a test of `C` cites at its current version is due. A requirement under `left` in the newest `mutated` record on that chain, `C` included and the newest by `at` among a commit's records, is due as well when a test of `C` cites it at its current version; its `diff` runs from the `since` of the oldest record of the unbroken run of newest records whose `left` names it, so a requirement carried over keeps the change that made it due. So a pass that ends before it judges a requirement loses nothing: the next one judges it, and a pass that records nothing starts from the same commit. For the due requirements it SHALL write a plan file holding, for each, first those under that `left` in the list's order and then the others in ID order, the line `requirement <id>`, then one line `code <path>` for each file its component owns in `C`, then `diff <path>` naming a file that holds `git diff <P> <C>` over those files when that is not empty, then one line `test <file>`, a tab and the test's name for each test citing it in `C`, then one line `reads <glob>` for each distinct glob, in sorted order, of the `clm:reads` markers in `C`'s text of the files holding those tests, as `check.affected`'s `reads_in` reads them, then `limit 20`. It SHALL run the command through `sh -c` in the verify tree, with `CLM_MUTATE` naming the plan, `CLM_MUTATE_RESULT` naming an empty file, `CLM_SLOT` set to one more than the clone's `max_builds`, a number that, with the `mutate_jobs` less one numbers after it, no build place and no check holds, so the tests it runs may overlap any other run (`tests-run-concurrently`), `CLM_MUTATE_JOBS` set to the whole number of 2 GiB (2097152 kB) in the `MemAvailable` line of the memory file its call is given, at least 1 and at most `[verify] mutate_jobs`, or to 1 when `mutate_jobs` is unset or that file or line can't be read, and `CLM_LAND_DIR` and the `[env]` variables as the check gets them, its output copied to stderr, in a process group of its own. With `[verify] mutate_minutes` set, when the command has run that many of its call's minutes it SHALL send `SIGTERM` to that group, and `SIGKILL` when the command hasn't ended after its call's grace, and print `mutation: stopped at its limit of <m> minutes` on stderr; when its call's stop request is set while the command runs, it SHALL end the command the same way and print `mutation: stopped` on stderr. However the command ends, it SHALL then read from the result file the lines that end in a newline, one per requirement, the last for a requirement holding: `<id> killed`, the tests failed for at least one mutant; `<id> survived <n>`, `<n>` mutants were tried and the tests passed for every one; or `<id> not-judged`; a line of `survived 0` is not judged, a line that doesn't parse is ignored, and a due requirement with no line is left. It SHALL then append one `mutated` record naming `C`, `P` as `since`, the killed and not-judged IDs, the survived ones as `unproven` entries at their versions in `C`, and the left ones under `left` in the plan's order (`ledger/mutated-record`), and print `mutation: <k> killed, <u> unproven, <n> not judged` on stderr, followed by `, <l> left` when any is left. With nothing due it SHALL run no command and append the record with empty lists. When the command exits non-zero without being ended so, it SHALL print `mutation: <command> failed with status <n>` on stderr before the record's line, and still append the record, so the verdicts it reached are kept and the rest are left. The pass SHALL NOT change the outcome line, anything on stdout or the exit status, and SHALL NOT run when the check failed, in `import` mode, for a result answered from the ledger, for a bisect, or with `mutate` unset.

#### Scenario: a new test that notices
- GIVEN `mutate` set to a fake that copies its plan and writes `a/x killed`, a passing check, a `mutated` record for the last verified commit, and one land since that added `tests/x.rs` with a test `proves_x` citing `a/x` and changed `src/a.rs`, both `a`'s
- WHEN `clm verify --due` runs
- THEN the plan holds `requirement a/x`, `code src/a.rs`, `code tests/x.rs`, a `diff` line whose file names `src/a.rs`, `test tests/x.rs` with `proves_x` and `limit 20`; the ledger gains a `mutated` record with `a/x` under `killed`; stdout is the one line `verify passed <sha> 1 lands`; and it exits 0

#### Scenario: a test that notices nothing
- GIVEN the same with a fake that writes `a/x survived 12`
- WHEN `clm verify --due` runs
- THEN the `mutated` record holds `a/x@<version>` under `unproven`, stderr holds `mutation: 0 killed, 1 unproven, 0 not judged`, and it still prints `verify passed` and exits 0

#### Scenario: the first pass fails, and the next loses nothing
- GIVEN no `mutated` record, a land `S` that set `mutate`, a land `L` after it that added a test citing `a/x` and changed `a`'s code, a `mutate` command that writes nothing and exits 3, and `clm verify --due` run once at `L`, which records a `mutated` record for `L` whose `since` is the first parent of `S` and whose `left` holds `a/x`
- WHEN a further land adds a test citing `a/y`, the command is replaced by one that copies its plan, and `clm verify --due` runs again
- THEN the plan holds the block for `a/x`, whose `diff` file holds `L`'s change to `a`'s code, and then the one for `a/y`, and the new `mutated` record's `since` is `L`

#### Scenario: a test that reads the repository's files
- GIVEN the land of the first scenario, with `tests/x.rs` also holding the markers `clm:reads specs/**` and `clm:reads ARCHITECTURE.md`, and another file of `a`'s holding `clm:reads docs/**` but no test citing `a/x`
- WHEN `clm verify --due` runs with a fake that copies its plan
- THEN the block for `a/x` holds `reads ARCHITECTURE.md` and then `reads specs/**`, after its `test` line and before `limit 20`, and no `reads docs/**`

#### Scenario: the pass switched on from the first commit
- GIVEN no `mutated` record and a chain whose first commit sets `mutate` and holds a test citing `a/x` at its current version
- WHEN `clm verify --due` runs with a passing check
- THEN the plan holds a block for `a/x`, with no `diff` line

#### Scenario: only re-cited
- GIVEN a land since the last pass that changed only the version in the marker of the test citing `a/x`
- WHEN `clm verify --due` runs
- THEN the command isn't run, and the `mutated` record's lists are empty

#### Scenario: an item resolved with its test unchanged
- GIVEN a backlog item naming `a/x` under `unproven` at the last pass's commit, deleted by a land since, with the tests unchanged
- WHEN `clm verify --due` runs
- THEN the command isn't run for `a/x`, so a build that found the test sound settles it in one look

#### Scenario: its own slot
- GIVEN `max_builds` 4 and a fake `mutate` that records `CLM_SLOT`
- WHEN the pass runs it
- THEN it recorded `5`

#### Scenario: the command fails part-way
- GIVEN `a/x`, `a/y` and `a/z` due, and a `mutate` command that writes `a/x killed` and exits 3
- WHEN `clm verify --due` runs with a passing check
- THEN the `mutated` record holds `a/x` under `killed` and `a/y` and `a/z` under `left`, stderr names the command and status 3 and then holds `mutation: 1 killed, 0 unproven, 0 not judged, 2 left`, and it prints `verify passed` and exits 0

#### Scenario: a line cut short
- GIVEN `a/x` and `a/y` due, and a `mutate` command that writes `a/x killed`, a newline and `a/y survived 1` with no newline, and exits 3
- WHEN `clm verify --due` runs
- THEN the record holds `a/x` under `killed` and `a/y` under `left`

#### Scenario: the time limit
- GIVEN `mutate_minutes = 1`, a call whose minute is one second and whose grace is one second, `a/x` and `a/y` due, and a `mutate` command that writes `a/x killed`, starts a child that sleeps, and then ignores `SIGTERM` and sleeps
- WHEN the pass runs
- THEN within a few seconds the command and its child no longer run, the record holds `a/x` under `killed` and `a/y` under `left`, stderr holds `mutation: stopped at its limit of 1 minutes`, and the outcome is unchanged

#### Scenario: a stop request
- GIVEN `a/x` and `a/y` due, and a `mutate` command that writes `a/x killed` and then waits until a file appears
- WHEN the call's stop request is set once the line is written
- THEN the command no longer runs, the record holds `a/x` under `killed` and `a/y` under `left`, and stderr holds `mutation: stopped`

#### Scenario: what is left goes first
- GIVEN the newest `mutated` record's `left` holding `a/z`, and a land since that added a test citing `a/a`
- WHEN `clm verify --due` runs with a fake that copies its plan
- THEN the plan's block for `a/z` comes before the one for `a/a`

#### Scenario: jobs follow memory
- GIVEN `mutate_jobs = 6` and a fake `mutate` that records `CLM_MUTATE_JOBS`
- WHEN the pass runs with a memory file whose `MemAvailable` reads 5242880 kB, then one whose reads 41943040 kB, then one with no such line, then with `mutate_jobs` unset
- THEN it recorded `2`, then `6`, then `1`, then `1`

#### Scenario: unset
- GIVEN a `[verify]` with no `mutate`
- WHEN `clm verify --due` runs with a passing check
- THEN no `mutated` record is appended and stderr holds no `mutation:` line

#### Scenario: a red check
- GIVEN `mutate` set and a check that fails
- WHEN `clm verify --due` runs
- THEN the command isn't run

#### Scenario: lands don't wait
- GIVEN a `mutate` command that waits for a file to appear
- WHEN `clm verify --due` is in its pass and a land of the clone runs its check
- THEN the land's check starts before the file appears
