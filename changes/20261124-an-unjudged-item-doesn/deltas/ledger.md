## MODIFIED Contract
The records that say what was approved, checked and landed, as facts in git that any clone can replay (`per-writer-ledgers`). Each writer appends to its own branch, `clm/ledger/<person>/<clone>`, so appends never race, and the state is the fold over the union of every ledger branch on `origin` and this clone's own. Crate `clm-ledger` offers, as library calls, `env` being the environment as a lookup, which `config` and git's config are read with:
- `writer(root, env)`: this clone's identity, creating it on first use.
- `append(root, entry, env)`: commit the entry to the writer's branch and push it, returning `Appended { record, pushed }`. An `entry` (`Entry`) is a record's `Body`, given a fresh `id`, the writer and the time, or a `Signed` record `sign` returned. `append_all(root, entries, env)`: several entries in one commit and one push, returning one `Appended` per entry.
- `fold(root)`: the state, a `Fold` holding `records` (every record once, by `at` and then `id`), `approvals` by fingerprint, `checks` by code key, `lands` by commit, `subscriptions` (the live push subscriptions by `id`, each with its `writer`, `at`, `endpoint`, `p256dh` and `auth`), `proposals` (the open web proposals by `id`), `answers` (the open answers by item), `comments` and `change_requests` by branch (`web-proposals-as-ledger-records`, `web-review-feedback-as-ledger-records`), `efforts` (the effort records by `id`), `decisions` (the capability decisions by capability), `verifications` and `mutations` (the slow-test results and the mutation passes by commit, newest first), `lines` (each record's JSON object as read, by `id`) and `warnings` (each line or ledger it skipped). `fold_records(sources)`: the same fold over `(ledger, records.jsonl text)` pairs already read, which the build with default features off offers too.
- On a `Fold`: `cleared(request)` (whether a `changes_requested` record is cleared at its fingerprint, the one rule `land.approval` and `web.worker` hold by: `request-cleared`) and, in the default build, `cleared_at(root, rev, request)` (the same rule, counting in a repository signed at `rev` only an approval whose signature checks: `request-cleared`), in every build `carries_sig(id)` and `cleared_by_sig(request)` (whether a record's line as read carries a non-empty `sig`, and `cleared` counting only an approval whose line does, for a caller that can check no signature: `cleared-by-a-signed-line`), `timed_lands(n)` (the last `n` timed lands as `TimedLand { commit, at, check_seconds, steps, recheck, recheck_files }`, each step a `TimedStep { name, seconds, selected_by }`: `landed-times`, `landed-recheck`) and `unresolved_reds(chain)` (the red `verified` results nothing has since cleared: `verified-record`).
- `effort_id(session, branch)` (an `effort` record's `id`), `code_key(root, rev)` (a commit's tree with the doc-only paths left out, hashed), `code_key_with(root, rev, path, from)` (`rev`'s code key with `path`'s entry as it is in `from`, which `land` reads to count a `clm.toml` whose settings are unchanged as checked), `doc_only(path)` (whether `code_key` leaves a path out, which `check.affected` reads so its selection and the code key agree), `legacy_doc_only(path)` (the doc-only list as it was when the `landed` records without a `code_key` were written: `legacy-doc-only`), `person(writer)` (the person part of a `<person>/<clone>` writer), `change_ids(paths)` (the live change IDs a branch's added or modified paths name, sorted, which an `approved` record's `change` and a `landed` record's `changes` are named by: `change-ids`), `rfc3339(secs, millis)` and `unix_time(text)` (a record's `at` written, and an RFC 3339 time read: `record-times`) and `slug(name)` (a name slugged as `writer` slugs git's `user.name`, which `land.approval` and `verify` slug commit authors with: `person-slug`).
- `verify(root, tip, since, review)`: the audit `clm ledger verify` makes, of `tip`'s first-parent chain, returning its findings, each a `Finding { rule, commit, message }`. `on_main(root)`: those findings for `main` as violations, for `clm check` to report. `compact(root, env)`: what `clm ledger compact` does, returning `Compacted { removed, warnings }`. `show(fold)`: the lines `clm ledger show` prints.
- For signed repositories (`signed-ledger-records`): `signed(root, rev)` (whether `rev`'s tree holds `docs/allowed_signers`), `sign(root, body, namespace, env)` (the body as a record with its `id`, `writer` and `at` filled in, signed with the person's key, as `Signed { record, sig }`, whose `line()` is the JSON object `append` writes), `signed_by(root, rev, line, namespace)` (whether a record's line as read, a JSON object such as `Fold::lines` holds, has a `sig` that is a valid signature by a key `rev`'s `docs/allowed_signers` lists for the line's writer's person) and `signed_message(line)` (the bytes a signature is over).

A call that fails returns `Error`: `Git` (`clm-git`'s error), `Config` (`config`'s), `Io`, `Writer` (the writer identity can't be made, or a signed record is another writer's), `Signing` (a record can't be signed or a signature checked: `record-signing`, `signature-check`; `land.approval` reads its text) or `Settings` (a committed `clm.toml` the audit reads doesn't parse). The record types are `Record { id, writer, at, body }`, `body` a `Body` with one variant per kind below, holding the kind's fields under their names in the line, but for `Body::Landed`'s `kind`, written `land_kind`; and `LandKind`, `Basis { head, base }`, `Recheck`, `TimedStep`, `Usage { input, output, cache_read, cache_write }`, `Rating`, `Decision` and `VerifyMode`, the values their fields hold. `Body::kind()` gives a body's kind as `kind` holds it; `Usage::work()` gives `input` + `output` + `cache_write`, saturating rather than overflowing; and `Rating::as_str()` and `Decision::as_str()` give the value as the line writes it. `Body::mutated(...)`, `Body::with_left(left)`, `Body::with_failed(failed)` and `Body::with_ended(ended)` build a `mutated` body without naming the variant's fields (`mutated-constructor`, `mutated-record`). `Body::approved(fingerprint, branch, change)` builds an `approved` body without naming the variant's fields (`approved-constructor`). `Body::landed(commit, branch, kind, review, fingerprint)` builds a `landed` body without naming the variant's fields, with no code key, changes, check time, steps or recheck, and `with_code_key`, `with_changes`, `with_check_seconds`, `with_steps`, `with_recheck` and `with_recheck_files` set those on it (`landed-constructor`). `clm ledger compact` prunes the caller's own superseded records, `clm ledger verify` audits `main` against the records, approvals and signatures included, and `clm ledger show` prints the fold. Each prints a warning on standard error as `warning: <text>`, and a failure as `clm ledger: <why>` with exit 2; `clm ledger verify` exits 1 when it finds anything, and otherwise each exits 0 (`commands-in-crate`). Changing a record kind or a field name is a change to this Contract: `land`, `gate`, `view`, `web.worker` and the skills all read them.

Record kinds:
- `approved`: `fingerprint`, `branch`, `change` (a change ID, or null), `clears` (the `id`s of the `changes_requested` records the approval clears, an empty list when it clears none). `Body::with_clears(clears)` gives an `approved` body the list given, and `Body::approved(...)` alone leaves `clears` out. A record without `clears` was written by an older `clm` or Worker, or by a caller that names no requests, and clears by time; `clm approve` (`land.approval/approve`) and `web.worker`'s approve (`web.worker.review/approve`) name their requests once each is built (`request-cleared`). A human's approval of a diff (`approve-pins-the-review`).
- `checked`: `code_key`, `command`, and optionally `basis` (`head` and `base`: the code keys of a branch's head and of `main` whose checks it was composed from: `composed-check`). A tree whose code key passed the check command and `clm check`, written by `clm land` for its merged tree or by `clm land --check-only` for a clean, committed `HEAD` that contains `origin/main` (`land/check-only`, `worktree-check-counts`), or whose code key `code_key_with` maps, its `clm.toml` settings unchanged, to one that did, the land having run that tree's `clm check` and the tests that read `clm.toml` (`land/settings-unchanged-is-checked`). A record with `basis` is a *composed* check: `clm land` writes one for a merged tree it checked only where the branch and `main` overlap (`land/overlap-recheck`), and `clm ledger verify` audits that `checked` records name both of its keys.
- `landed`: `commit`, `branch`, `land_kind` (`spec` or `code`), `light` (true for a land of a branch the gate reads as `light`, `gate/light`, whose `land_kind` is then `code`; absent otherwise, as on every record written before it, which reads as false; `Body::with_light(light)` sets it on a body `Body::landed` built, which starts false), `review` (whether the land needed a human's review, `gate/needs-review`; false for code), `fingerprint`, `code_key` (the code key the land's `checked` record names: the landed commit's, or, for a land checked together with others (`land/batched-lands`), that of the commit their check ran on), `recheck` (how the land checked its merged tree: `checked`, its code key already checked; `none`, the overlap selected nothing; `overlap`, the overlap ran; `selected`, the branch's own selection ran; absent on older records: `landed-recheck`), `recheck_files` (with `overlap` or `selected`, the number of `file` lines the check ran, or null when it ran every test), `changes` (the live change IDs a spec land added or modified), and, when the land ran `[land] check`, `check_seconds` (the command's wall-clock time in whole seconds, rounded down) and `steps` (each step it marked, in order, as `{name, seconds, selected_by}`, `selected_by` the paths its `::clm-selected::` lines named: `land/step-times`), which `Fold::timed_lands(n)` reads back (`landed-times`). A `checked` record stays a fact about a code key and carries no times (`graph-test-selection`, `land-times-on-the-landed-record`). Older records lack `code_key` (`landed-record-names-its-code-key`). Records from before review was yes or no (`yes-no-review`) have `tier` instead of `review`: `HARD` reads as `review: true`, anything else as `false`.
- `subscribed`: `endpoint`, `p256dh`, `auth`. A browser's Web Push subscription for this repo, which `web.worker` notifies (`push-subscriptions-in-ledger`).
- `unsubscribed`: `subscription` (the `id` of a `subscribed` record). That subscription's end.
- `proposed`: `slug`, `title`, `body`, and the components at `/nodes`. A backlog item proposed from the web app, which `clm rebase` files as `backlog/<slug>.md` on the next `impl/*` branch (`web-proposals-as-ledger-records`).
- `withdrawn`: `proposal` (the `id` of a `proposed` record). That proposal's withdrawal by its proposer.
- `answered`: `item` (a backlog item's slug) and `answer`. A person's answer from the web app to a `question` item that lists it in `choices`, or `done` for a `human-task` item, which `clm triage` prints under the item (`web-answers-as-ledger-records`).
- `commented`: `branch`, `fingerprint`, `target` (always present: a requirement ID `<component>/<slug>`, or null for the change as a whole), `text`. A reviewer's comment on a spec branch's diff, made in the web app (`web-review-feedback-as-ledger-records`).
- `changes_requested`: `branch`, `fingerprint`, `text`. A reviewer's request, made in the web app, that the branch change before it lands; `clm land` holds the branch while its fingerprint is the one named (`land`).
- `effort`: `branch`, `session`, `models` (a map from a model's name to its `input`, `output`, `cache_read` and `cache_write` token counts), `active_seconds`. The work one Claude Code session spent on one branch, as `clm effort record` read it from this machine's transcripts (`effort`). Its `id` is `effort_id(session, branch)`, not random, so a later record of the same session and branch supersedes the earlier one (`effort-accounted`).
- `decided`: `capability` (the ID of the entry decided on, `capability/<slug>` or `architecture/<slug>`; the key keeps its name for both, so earlier records and earlier `clm`s read alike), `value` (`high`, `medium` or `low`), `decision` (`keep`, `cut`, `redesign` or `accept`), `settles` (the slugs of the workaround items it settles). A human's review decision on a capability or an architectural constraint (`review-capability-cost`, `docs/decisions/architecture-review.md`).
- `verified`: `commit` (a commit of `main`), `passed` (true or false), `since` (the last commit a `verified` record named before it, or null), `lands` (the first-parent commits of `main` it covers, oldest first), `culprit` (the land that broke it, or null), `components` (the components a red result holds, empty when it passed), `mode` (`local`, `pipeline` or `import`), `run` (the host pipeline run's URL, or null). The result of running a project's slow tests after the land on that commit (`verify-after-land`).
- `mutated`: `commit` (a commit of `main`), `since` (the commit the pass started from, or null), `killed` and `not_judged` (requirement IDs), `unproven` (entries `<component>/<slug>@<version>`), `left` (requirement IDs the pass didn't reach; absent in older records, read as empty), `failed` (an object from each requirement ID among `left` whose block's tool failed to the text the command gave, possibly empty; absent in older records, read as empty) and `ended` (how the command ended when it didn't exit 0: `stopped`, `limit <m>`, `status <n>` or `signal <n>`; absent or null when it exited 0 or didn't run). What a mutation pass found on that commit (`mutation-after-land`).

Every record also has `id` (random 128-bit hex, except an `effort` record's, which is `effort_id(session, branch)`), `kind` (one of the fourteen above), `writer` (`<person>/<clone>`) and `at` (the time it was written, in UTC, always as `YYYY-MM-DDTHH:MM:SS.mmmZ`, as `clm` and `web.worker` write it, so two records' times order as strings: the fold sorts by `at` so, and `cleared` compares a request's with that of an approval that has no `clears`, for `land` and `web.worker` alike). A signed record also has `sig`: an `approved` record signed under the namespace `clm-approve`, or a `landed` record under `clm-land`; the other kinds never have it, and a record without it is unsigned. A record is one flat JSON object, so no record field shares a name with these five: the land's kind is `land_kind`, not `kind`.

`clm-ledger` offers `clm ledger` as a call, `ledger_command(args, root, env, out, err)` (`commands-in-crate`, `commands-live-in-their-crates`): it takes the command's arguments as the command line gives them, the repository root, the environment as a lookup and a stream each for standard output and standard error, and returns the exit status. Its arguments are `LedgerArgs`, which `crates/clm`'s parser reads, holding the subcommand as a `Ledger` (`Compact`, `Verify` or `Show`), and whose `root()` is the `--root` the subcommand was given. `crates/clm` routes the command to it and adds nothing to what it writes.

## MODIFIED Requirements

### Requirement: mutated-record <!-- base: 9b20d6a5c4661ef1 -->
The fold, `fold` and `fold_records` alike, SHALL parse `mutated` records and hold them by `commit`, the newest by `at` first, skipping with a warning a line whose `commit` or `since` holds anything but a full 40-hex lowercase commit ID (or null for `since`), whose `killed` or `not_judged` isn't a list of requirement IDs, or whose `unproven` isn't a list of `<component>/<slug>@<version>` entries with 8 lower-case hex digits, or whose `left` is present and isn't a list of requirement IDs, or whose `failed` is present and isn't an object from requirement IDs to strings or names an ID its `left` doesn't, or whose `ended` is present and is neither null nor a string; a record with no `left` or no `failed` holds it empty, and one with no `ended` holds none, so records written before the fields read as they did. `Body::mutated` (`mutated-constructor`) SHALL set `left` and `failed` empty and `ended` to none; `Body::with_left(self, left: Vec<String>) -> Body` SHALL return a `mutated` body with that list as its `left`, `Body::with_failed(self, failed: BTreeMap<String, String>) -> Body` one with that map as its `failed`, and `Body::with_ended(self, ended: String) -> Body` one with that text as its `ended`, each returning any other body unchanged, so a caller that built its body through the constructor sets `left`, `failed` and `ended` without naming the variant's fields. `append` SHALL write it like any record, unsigned in every repository, since it holds no land. `clm ledger show` SHALL print it as `mutated <commit> <k> killed <u> unproven <n> not judged <writer> <at>`, with ` <l> left` after `not judged` when `left` isn't empty. `clm ledger compact` SHALL keep the caller's newest `mutated` record for each commit and every one that holds an `unproven` entry, and drop the others.

#### Scenario: folded and shown
- GIVEN a `mutated` record for commit `c` with one `killed`, one `unproven` and no `not_judged`
- WHEN the fold reads it and `clm ledger show` runs
- THEN the fold holds it under `c`, and the line is `mutated <c> 1 killed 1 unproven 0 not judged <writer> <at>`

#### Scenario: bad entry
- GIVEN a `mutated` line whose `unproven` holds `a/x` with no version
- WHEN the fold reads it
- THEN it skips the line with a warning naming it

#### Scenario: what a pass left
- GIVEN a `mutated` record for commit `c` with one `killed` and `left` holding `a/y` and `a/z`
- WHEN the fold reads it and `clm ledger show` runs
- THEN the fold holds `a/y` and `a/z` as its `left`, and the line is `mutated <c> 1 killed 0 unproven 0 not judged 2 left <writer> <at>`

#### Scenario: an older record
- GIVEN a `mutated` line with no `left` key
- WHEN the fold reads it
- THEN it holds the record with an empty `left`

#### Scenario: a bad left
- GIVEN a `mutated` line whose `left` is the string `a/y`
- WHEN the fold reads it
- THEN it skips the line with a warning naming it

#### Scenario: left set through the constructor
- GIVEN `Body::mutated` called with a commit and one `killed` ID, and `Body::with_left` called on what it returns with `a/y`
- WHEN the body is appended and the fold reads it
- THEN the fold holds the record with `a/y` as its `left`, and a body from `Body::mutated` alone holds an empty `left`

#### Scenario: why a pass left them
- GIVEN `Body::mutated` called with a commit and no IDs, and, on what it returns, `Body::with_left` with `a/y` and `a/z`, `Body::with_failed` with `a/y` mapped to `StrykerJS ran no test` and `Body::with_ended` with `status 1`
- WHEN the body is appended and the fold reads it
- THEN the fold holds the record with `a/y` and `a/z` as its `left`, `a/y` alone under `failed` with that text and `ended` `status 1`, and a body from `Body::mutated` alone holds an empty `failed` and no `ended`

#### Scenario: an older record's reasons
- GIVEN a `mutated` line with no `failed` and no `ended` key
- WHEN the fold reads it
- THEN it holds the record with an empty `failed` and no `ended`

#### Scenario: a bad failed
- GIVEN a `mutated` line whose `failed` is the list `["a/y"]`, one whose `failed` maps `a/q` to a text while its `left` holds only `a/y`, and one whose `ended` is the number 1
- WHEN the fold reads them
- THEN it skips each line with a warning naming it
