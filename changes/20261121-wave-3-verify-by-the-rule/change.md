## Intent

Wave 3 of phase 5 of `backlog/a-passing-check-proves-less-than-the-spec-claims`, its branch C of three: `verify` and `ci` are each brought, in one pass and one delta, to the rule for a requirement (`requirements-state-what-the-contract-shows`), with small deltas of the root (`clm`), `ledger`, `config` and `context` that follow from them. Branch A (`20261121-wave-3-land-by-the-rule`) holds `gate`, `land` and `land.approval`, and branch B (`20261121-wave-3-host-by-the-rule`) holds `host`, `sync` and `sync.regenerate`; no clause moves to or from either. The wave is for a spec that is true and proven, not a smaller one.

## Problem

Read against the rule and the code on 2026-11-21, by one reader per component, then by one drafter per component that checked each entry against the code, then by one builder check per component whose first question of every clause was whether the code does it as worded:

- **Both Contracts were wrong or incomplete.** `verify`'s listed four command lines as what the crate offers, where the crate offers a library call (`verify_with`, its `Request`, `Outcome`, `Error` and `Call`) and the command is the root's; it left out `--root`, and its list of refusals left out four the code returns (a `--bisect` of a commit no red record names, a revision that names no commit, a commit whose `[env]` can't be used, and the host's run list failing in `import` mode). `ci`'s gave a dependant nothing of the scripts' interface, though `land` reads the check script's step markers and `verify` writes the plan the mutation script reads.
- **Clauses the code shows had no requirement**: the order in which `verify`'s triggers are tried and the line when none holds, a tree that must be remade, a selection that can't be made, a record kept local, a land between two bisect probes, a CLM root below the top of its repository, the mutation pass's standard call and the lines it reads that aren't verdicts; and of `ci`, a missing selection file, a deleted crate, the panel validation's empty standard input, a mutation script given a bad environment or interrupted part-way, and a failure before the check script's first phase.
- **`config`'s Design said `[verify] check` is the whole suite with no selection.** `clm verify` hands its check the selection `clm affected` makes since the last green commit whenever a green record exists, and this repository's check script reads it.
- **Two scenarios of `ci` were wrong against the scripts.** `web-checks`' "every check" said the script runs `cargo test`, and `no-model-steps`' "the pin changes" said `cargo test -p clm-run`; the script runs the Rust tests through nextest, as `nextest-runner` states and the existing test already asserts.
- **Two requirements of `context` state what no code uses**: `bundle_from`, which no crate outside `clm-context` calls, and a build for WebAssembly, which no WebAssembly crate links. The plan item named both for this wave, to go with `ci`, which builds the crate for WebAssembly in every land check.
- **Bugs on `main`, each mended by its component's build:**
  - `verify`: a commit whose `[env]` can't be used refuses the whole `clm verify` when it is a bisect probe or the last green commit, not only when it is the commit verified. A land that breaks `[env]` followed by one that mends it makes a red run on the head bisect onto the broken land and refuse after the head's check failed, so the red result is never recorded; every later verify does the same while that land lies in the range, since the green commit can't move. The message naming a commit's `clm.toml` leaves out the CLM root's place in its repository, which the file read from `origin/main` includes. A mutation command ended by a signal is reported as `failed with status a signal`. A conversion from `clm-git`'s `Failure` is dead code, and two doc comments contradict the Contract.
  - `ci`: a release locks the migrations it ships whether or not their requirements are built (`backlog/a-release-locks-a-migration-whose-requirement-is-still-pending`), which the human has held the release on since wave 2. The check script builds `clm-context` for WebAssembly, which nothing needs.
  - `context`: its WebAssembly gates and the public `bundle_from` go with the two requirements.
- **`backlog/reconsider-clm-verify-command`** carries the human's answer of 2026-11-17: the window in which `clm verify` holds a stop signal is from its `verify passed ` line until `clm-verify`'s call returns, the mutation pass and its filing together. The root's code already does that; `backlog/workaround-clm-verify-command-1` and `backlog/clm-verify-can-t-tell-its-caller-when-the-mutation-pass-runs` are the same question from the workaround flag and from `verify`'s side.

## Outcome

- Each of `verify` and `ci` has one delta: Contract and Design made right against the code, requirements reworded to what someone outside the component observes, the unstated clauses stated with one scenario each, and the cuts below.
- Where the code falls short of a requirement's plain meaning the requirement keeps its meaning, gains a scenario for the failing case, and its build mends the code.
- `verify/verify-env`: only a table `config` refuses makes a commit's `[env]` unusable, and only for the commit whose check runs as the verification does it refuse. A probe whose table can't be used is untestable and runs nothing; a green or red commit whose table can't be used counts as differing, so every test runs. A git failure reading the table ends the run as `settings-from-main` says.
- `verify/mutation-pass` states its standard call's values (the memory file, the minute and the grace, which leave `clm/verify-command`) and the line for a command ended by a signal: `mutation: <command> was ended by signal <n>`, followed by ` (<name>)` for the 27 standard and XSI signals of POSIX.1-2017 it lists.
- `verify/settings-from-main` and `verify-due` name the file as `origin/main:<prefix>clm.toml`, `<prefix>` the CLM root's place in its repository, with the scenario "a CLM root below the top".
- `clm/verify-command` states the stop window as the human's answer gives it, and names `verify/files-unproven` within it.
- `ci/release-records-upgrade-corpus`: before it builds the corpus, locks or pushes anything, the release runs `clm pending upgrade` and then `clm pending init`, both whatever the first gave, and refuses when either prints a line on standard output or exits non-zero. A run that exits non-zero is reported only by its status, as `release: clm pending <component> exited <status>`, whatever it printed (so the violations of specs that don't load are not repeated); a run that exits 0 is reported by its lines, under `release: requirements of upgrade or init are pending:`; both on standard error, `upgrade`'s first, then exit 1. The cost: a release waits for every pending requirement of `upgrade` and `init`, not only a migration's, since nothing maps a migration to its requirement; the other design, a lock that leaves out a pending migration, is `upgrade`'s code and was not taken.
- `ci`'s text scans of its own scripts and workflows are restated as runs of the scripts with recording stand-ins and parses of the two workflows, each run well under a second.
- `ci/web-checks` no longer names a WebAssembly build of `clm-context`; `context`'s Contract and Design say the crate is built for the native targets alone.
- `requirements-state-what-the-contract-shows` gains a paragraph, "What wave 3 settled": what a workflow does is a requirement, proven by reading the workflow file, since only the host runs it; and `ci/early-access-form` stays by name until the web's wave. The human agrees it by approving this branch.
- `config`'s Design says what `[verify] check` is: the land's check script, given the tests `clm affected` selects since the last green commit, or every test with no green commit or a changed `[env]`, and names `backlog/no-check-runs-a-test-the-selection-misses` for the test that selection misses.
- `ledger/mutated-record` and `clm/readme-front-page` each lose one `#### Needs` line, naming a requirement this change removes; neither changes otherwise.
- `backlog/every-test-runs-in-the-land-check-the-browser-suites-included` records the two requirements of `ci` proven only against stand-ins, and what a part of the check only `[verify]` runs would give them.

## Constraints

- A build changes only its own component's files (`own-files-at-the-gate`). No build of this branch needs a file outside its component, and no prerequisite outside the wave is needed.
- `ci/npm-installs-bounded`, its Design paragraph **Bounded npm installs** and change `20261115-a-stalled-npm-install` are untouched: the requirement is not in the delta, and the paragraph is copied into the new Design byte for byte.
- Order, each carried by a `#### Needs`: `ledger` before `verify`, since `verify/mutation-pass` and `verify/files-unproven` need `ledger/mutated-record`, whose version moves; the root after `verify`, since `clm/verify-command` needs six of `verify`'s requirements this change modifies; `ci`'s `mutate-script` after `verify`. Built as `ledger`, then `verify`, then the root and `ci`, no component is built twice: the root and `ci` each hold a requirement that is ready at once beside one that waits on `verify`, so either claimed before `verify` lands is built again. `context` may be built at any time: without its WebAssembly gates `clm-context` still builds for WebAssembly. Branch A also carries a `ledger` delta; one `ledger` build after both branches land covers both.
- `verify`'s build also waits on branch A, through its `#### Needs`: `verify/verify-run` and `verify/verify-bisect` need `land/shared-check-runner`, `verify/verify-build-cap` needs `land/shared-target-cap`, and `verify/verify-import` and `verify/verify-commit` need `host/list-runs`, each of which branch A modifies. This branch lands in any order with A and B; once A has landed, `verify`'s build, and the root's and `ci`'s after it, wait for `land`'s and `host`'s builds.
- `verify`'s requirements name `land/check-log`, `land/shared-check-runner`, `land/shared-target-cap` and `land/overlap-recheck`, `host/list-runs` and `check.affected/affected-readers`, all modified on branch A; that branch keeps each name and its meaning. `host/list-runs` keeps "newest first", which `verify-import` relies on.
- `crates/clm-context/tests/carried.rs` keeps its `clm:reads ARCHITECTURE.md` marker, since the root's test of `clm/doc-readers-marked` names the file and `context`'s build can't edit it.
- The release workflow's push to `main` stays the one named exception to `land-locally`: `ci/no-workflow-pushes-main` says so.
- `verify` and `ci` were over the spec budget before this change and each grows, as "Settled on 2026-11-20" in the plan item expects of every wave. No seam is proposed here.

## Narrowings the human reads

- `verify/files-unproven`: it files at the end of a `clm verify --due` in `local` mode with `mutate` set, now only without `--dry-run` and unless the verification ended in a refusal or an error, as the code does; what is to file is derived from the ledger each time, so the next call files it. Widened at the same time: `unproven: not filed: <reason>` covers any step of the filing, not only the push or the land, and `--import` and `--bisect` are named among the forms that file nothing.
- `verify/verify-import`: `culprit` is the land for a failing run that covers one land, and null otherwise, where it said the land when the run covers one; a passing result has no culprit.
- `verify/settings-from-main` and the last sentence of `verify-due`: the file is `origin/main:<prefix>clm.toml`, where they said `origin/main:clm.toml`. At a repository's top, the case of every existing scenario, nothing changes.
- `ci/no-workflow-pushes-main`: the statement keeps its meaning, that no workflow pushes anything to `main`, by any means, but the release's merge of its version bump. What the land check fails on is now stated as the `git push` forms it reads (a refspec naming `main`, `--all`, `--mirror`). A push by other means, such as `gh api` moving a ref or a refspec held in a variable, is still forbidden, and no program catches it, as before.
- `ci/coverage-script`: "No other file of this repository SHALL run it or `cargo llvm-cov` but `mutate.sh`" becomes "No command `ci-check.sh` runs, nor any workflow step, SHALL be it or `cargo llvm-cov`". A doc or a test file naming it was never meant; a run sees only the branches a full run with stand-ins takes.
- `ci/mutate-script`: "neither `ci-check.sh` nor `clm.toml`'s `[land] check`" becomes "no command `ci-check.sh` runs, nor any workflow step".
- `ci/nextest-runner` "no plain cargo test": from a scan of every file under `.github/` to a parse of the two workflows, each script proven by its own run; a script nothing runs is no longer read.
- `ci/tests-time-bounded` "the bound": from a scan of `.github/` to the recorded calls of the four scripts' runs and a parse of the workflows; a branch a full run with stand-ins doesn't take isn't seen, and none of them runs nextest.
- `ci/detector-tools` "check script installs the tools" and "every detector's tool": a run shows the commands a full run makes, not every line the script holds.
- `ci/web-checks`: with `every_wasm_build_stands_alone` gone, nothing checks that each WebAssembly build stands on its own line.
- `ci/no-model-steps`: the check that `ci-check.sh` holds no word naming `clm` goes; the run records any call of `clm`, on the selections the tests run.
- `ci/land-dir`: drops "once `clm land` stops setting the cargo variables itself", a condition nobody can observe.
- `ci/node24-actions`: "every `uses:` line in `.github/workflows/`" becomes "every action the release and site workflows run", the same set while `release` holds the directory to those two.
- `ci/test-tools` "in the release": loses "no other job names `test-tools.sh` or `nextest`", the cut above.
- `context`'s Contract no longer offers `bundle_from` or a WebAssembly build.
