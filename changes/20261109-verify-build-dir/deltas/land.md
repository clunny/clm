## MODIFIED Contract
Landing a branch on `main`, on the machine that runs the command (`land-locally`). `clm land [<branch>]` runs the gate against `origin/main`, merges the branch in a scratch tree, runs the project's check command, handing it the tests the change can break as `clm affected` selects them (`CLM_SELECTION`, `graph-test-selection`), and `clm check` on the result unless the ledger says that code was already checked, records what it did in the ledger, and pushes the merge commit to `main` without force, retrying when `main` moved. It is the only thing in CLM that pushes `main`. What it keeps in a clone, the land tree, the shared target `.clm/land`, its lock, the check lock `.clm/check.lock`, the two locks' queues and failing checks' logs, is under the `.clm/` of the main worktree's CLM root, which `clm init` has the repository ignore, so a land leaves nothing untracked whatever the project's language (`land-places-ignored`). It prints `landed <sha> <kind>`, `<kind>` being `code`, `spec` or `spec review` as the gate's first line gives it, and exits 0; it exits 1 with the reason when it pushed nothing, and 2 on a git failure. Whether the branch is approved or held by a request for changes, and the signing of approvals and lands, are `land.approval`'s, as is `clm approve`, which `clm-land` re-exports. There is no after-merge review: a land that needs review lands only once approved (`yes-no-review`). `clm reconnect` pushes `main` and the local ledgers to an `origin` that `main` fast-forwards, as when a repository with `host = "none"` is moved onto a real remote or one landed with no remote by an older `clm` gets one. `clm land --check-only` runs the same check command, with every test (no `CLM_SELECTION`), and `clm check` on the current working tree, so a session learns the land check's verdict through a command that names no path (`land-check-command`). It lands nothing; when both pass on a clean working tree whose committed `HEAD` contains `origin/main`, it appends a `checked` record for `HEAD`'s code key, so a land whose merged tree is that tree, `main` not having moved, runs no check of its own (`worktree-check-counts`). The check command of a land, and of a `--check-only` run outside a build place, waits for any other such check of the same clone to end first (`check-runs-one-at-a-time`), so either can take as long as the checks queued before it; the waiting runs take their turns in the order they began to wait, except that a land carrying `P1` work goes first, a land whose code is already checked and runs only the tests that read what it changed goes next, and the rest go by priority (`lock-queue`, `ordered-lock-queue`); a `--check-only` run in a build place waits for none, its tests kept apart from other runs' by its slot (`tests-run-concurrently`). Both run it with `CLM_SLOT` set to the slot of the build place that names the branch checked, as `orchestrator`'s `place_slot` gives it, or 0, so the project's tests key their ports and paths apart from those of the tests other builds run at the same time (`build-slots`, `tests-run-concurrently`). While `origin/main`'s backlog holds a `kind: bug` item with `verify_failures`, a slow test the human took in as broken after the land, `clm land` refuses a code land that changes a file of one of the item's components, unless the branch's commit resolves that item; it warns, and lands, a branch touching the components of a red `verified` result no item has taken in yet (`verify-stop`, `verify-after-land`). A host's run never holds a land by itself (`land-locally`). `clm-land` also offers the runner it runs `[land] check` through, under the clone's check lock, for `verify` to run `[verify] check` the same way (`shared-check-runner`), and the cap it applies to `.clm/land`, for `verify` to bound its own build place the same way (`shared-target-cap`). When a land runs the check command it times the command and each step the check marks, and keeps the times, with the files that selected each step, on the `landed` record it appends (`step-times`); `--check-only` times nothing. After the push of such a land it prints the check's time against `[land] check_target_seconds` and, over it, its costliest steps, the chain that selected each and how recent lands fared, so an agent can judge whether the selection reaches too far or a suite belongs after the land (`check-time-report`); it files nothing, and the report never changes the land's outcome.

## ADDED Requirements
### Requirement: shared-target-cap
`clm-land` SHALL offer as a library call the cap that `land-target-cap` applies to `.clm/land`: it takes a directory, the name to print for it and a cap in gigabytes (10^9 bytes each), sums the lengths of the regular files under the directory, following no symbolic link, and when the sum is greater than the cap removes the directory and returns the line `cleared <name> (<n> GB, cap <cap> GB)`, `<n>` the sum in whole gigabytes rounded down. A directory that doesn't exist SHALL return nothing and remove nothing; when any entry can't be read the measure fails, nothing is removed, and it SHALL return a warning naming the path, as it SHALL when the removal fails. `clm land` SHALL apply `land-target-cap` through this call, naming the directory `.clm/land`, so its behaviour is unchanged.

#### Scenario: over the cap
- GIVEN a directory holding a sparse file of 2,000,000,000 bytes and a symbolic link to a directory outside it holding another such file
- WHEN the call runs on it with the name `.clm/x` and a cap of 1
- THEN it returns `cleared .clm/x (2 GB, cap 1 GB)`, the directory doesn't exist, and the file the link pointed to still does

#### Scenario: under the cap
- GIVEN a directory holding a file of 10 bytes
- WHEN the call runs on it with a cap of 1
- THEN it returns nothing and the file is still there

#### Scenario: no directory
- GIVEN a path where nothing exists
- WHEN the call runs on it
- THEN it returns nothing

#### Scenario: land unchanged
- GIVEN a `clm.toml` with `[land]`, a `check` that creates a sparse file of 2,000,000,000 bytes in `CLM_LAND_DIR`, and `target_cap_gb = 1`, and a branch `impl/a`
- WHEN `clm land impl/a` runs
- THEN stderr holds `cleared .clm/land (2 GB, cap 1 GB)`, as `land-target-cap` says
