## Problem

Read against the rule and the code on 2026-11-21, by one reader and one drafter per component, then by one builder check per component and a second round over the corrections:

- **Eleven routes onto `main`, and the rules read a branch's name.** The plan item counted eight; there are eleven: a spec branch that needs review, one that lands on checks, a queued build, a fix under `clm claim --fix`, a small code change with no claim, a docs-only branch, test plumbing under a trailer, a rename branch, an archive branch, an outside contribution and the release's push. Whether a branch is held to one component's files was read from its name: only a branch named `impl/<component>` was judged, so a small change or a fix on any other name could change any component's files, and since 2026-11-14 three of the sixteen code branches landed under other names did. The gate, which says it reads no branch name, read one to choose its advice for a `mixed` branch. `clm land` deleted only `impl/*`, `spec/*` and `propose/*` branches; refused a local `impl/*` or `spec/*` branch `origin` doesn't hold while landing any other name from the clone; and exempted every `spec/*` branch from the deleted-tests check, whatever it deleted.
- **What reads `code` though it holds no code.** A branch that only adds backlog items, an archive move such as `impl/archive/<id>`, and an empty diff all read `code`.
- **A scenario and its test can't land together.** A scenario added to an existing requirement costs a spec branch, then a build, with the requirement pending between them.
- **The order of one person's approval and request for changes is decided by two clocks.** A request is cleared by an approval of the requester's person whose `at` is later. Written from two machines, a request made after an approval is read as cleared when the approving machine's clock runs ahead, and the branch lands with the request open.
- **Every Contract was wrong or incomplete.** `gate`'s didn't describe `evaluate_at` or the outcome `land`, `ledger` and `host` read from it, nor its exit 2; `land`'s left out `land`, `check_only`, `reconnect`, `run_check` and the command calls, and offered an `approve` nothing calls; `land.approval`'s listed four `Repo` methods nothing outside the crate calls and left out the head rule both commands share; `host`'s stated no exit for the branch commands; `check.affected`'s offered `why`, `overlap` and `affected_between`, which nothing outside its crate calls.
- **Clauses the code shows had no requirement**, in every component of the branch: the lines each command prints and when, the help each crate's own command call writes, the head `clm land` lands, the waiting lines, the lock and queue failures, the paths a host reads a body file from, what the gate does with odd list lines and odd `resolves` entries.
- **Bugs on `main`, each mended by its component's build:**
  - `host`: the leased delete `clm land` calls refuses no name, so it would delete `main` or a `clm/` branch given a lease at its tip; it reads a branch as moved when `origin` holds another ref ending in its name; a delete `origin` refuses exits 2 where the same refusal of a push exits 1; two branches such as `spec/a-b` and `spec-a/b` keep their unopened bodies in one file; a relative body file is read from the process's directory when the root holds none, and on Azure always from it; Azure's cut note goes to the process's standard error, missing the command's own stream; an Azure pull request listed without its ID reads as no pull request; a `gh` answer that isn't a list reads as an empty list; the title of a pull request runs into the next paragraph past a line of spaces; the defaults are drawn from `changes/<id>/change.md` by the branch's name.
  - `gate`: a file added under an archived change's existing directory passes, though nothing may be added to history; a backlog-only, archive-only or empty branch reads `code`; a `mixed` line's advice depends on the branch's name.
  - `land`: a refusal drops every warning collected before it, and one warning prints `clm land:` twice; an append that fails after the push says nothing of the land `main` now holds; a lock or queue failure prints an OS error with no path, and a queue file that can't be read reads as empty; a ticket another OS user owns holds every later run's turn; the deleted-tests check reads every blob of the diff; the verify stop matches `paths` where `owner` gives the file's component; a spec branch that archives its own change releases no claim; `--help` through the crate's call prints a code comment.
  - `land.approval`: `clm approve`'s offline message tells the human to push and land; its warnings are never written; an approval that didn't reach `origin` says nothing; its fetch doesn't prune, so a branch `origin` deleted still reads as on `origin`; `--help` prints a code comment.
- **Backlog items this resolves**: `backlog/the-worker-says-no-review-for-an-exemption-the-gate-sends-to-review` (already built, as a shared call `widened_exemptions` both the gate and the Worker use rather than a fold into `needs_review_of`; deleted here); `backlog/the-land-reads-every-blob-to-find-deleted-tests`; `backlog/a-request-for-changes-made-after-an-approval-is-read-as-cleared-when-the-approver-s-clock-runs-ahead`; `backlog/reconsider-host-branch-push` and `backlog/workaround-host-branch-push-1`, whose answer of 2026-11-17 asked `host`'s Design to name the `ls-remote` check and its window, which it now does, `host/branch-push` unchanged.

## Outcome

The routes onto `main`, once `gate`'s, `land`'s and `host`'s builds have landed:

- **Spec.** A branch with no code file reads `spec`, a program deciding whether it needs review: a backlog-only branch, an archive move and an empty diff included, which need nothing. Docs-only edits, archive branches, rename branches and outside contributions are this route. No rule changes rank: `code` and `spec` with no review are alike in what they need.
- **Code for one component.** Every code branch, whatever its name, changes one component's files, plus the root's wiring, files no component owns and a capability test that component serves and the branch only modifies. The gate reads the component from the files (`gate/own-files`) and blocks a code branch no one component accounts for, naming each such file and its owner, once the root sets `wiring`, as this repository's does. A fix, a small change and test plumbing are this one route. A file outside the CLM root is no component's, and the gate admits it.
- **Light.** Spec and code together are refused (`mixed`), except a branch the gate reads as `light` (`gate/light`): its spec part is one change it applies and archives `done` in the branch, whose deltas only add scenarios to existing requirements of one component, with no statement, Contract, Design or frontmatter change but the component's `status`, no requirement added or removed, no cut, no burden, no rename, nothing needing review; every code file is that component's by the code route's rule, whether or not the root sets `wiring`; and at its head every requirement it added a scenario to is current, each marker citing it at its new version and at least one. A light branch needs no approval, lands on checks, and leaves nothing live. `clm land` prints `landed <sha> light` and records the land as a code land with `light` true (`ledger/landed-record-fields`). The gate's rules version becomes 7.
- **Every landed branch is deleted.** `clm land` deletes from `origin` any branch it lands that `origin` holds, leased on `origin`'s tip as the land's fetch read it, through `host`'s delete, which refuses `main` and `clm/*` before any git call (`host/branch-delete-call`). The head a land takes reads no name (`land.approval/branch-head`): the local branch when `origin` doesn't hold the branch or when `origin`'s tip is the local branch or an ancestor of it, and `origin`'s tip when there is no local branch; a local branch behind `origin`'s copy or diverged from it is refused, with advice for each case. Nothing is deleted for a branch `origin` doesn't hold.
- **Names are claims.** A branch named `impl/<component>` lands only as that component's work: `clm land` refuses it when the files give another component, as today (`land/build-holds-own-files`, by `foreign_files`). A branch named `spec/<id>` lands only when the gate reads `spec`, which also keeps an outside contribution, landed as `spec/<id>`, from landing code on checks as a light branch. No rule rests on a name alone: the gate reads none, and `clm land` judges deleted tests on every branch but a replayed rename, frees a build's `target/` after a code or light land of any name, and releases the claims of any land that adds a change, live or archived.
- **The release's push** of its version bump stays the one thing other than `clm land` that pushes `main`, as `land-locally` names it.
- **Approval order.** An `approved` record names the requests for changes it clears, in a field `clears`. A request is cleared by an approval of the requester's person for its fingerprint that names it, whatever either record's time (`ledger/request-cleared`). An approval with no `clears` field clears by time as today: one written by an older `clm` or Worker, before this change, or built with `Body::approved`, which goes on leaving the field out, so no open request starts holding again on upgrade and no approval clears nothing in the time between `ledger`'s build and its writers' builds. `Body::with_clears` writes the field, an empty list included, and a record with the field clears by name alone; `clm approve` and the web app's approve move to it in their own builds. In a repository signed at the land's base only an approval whose signature checks clears a request. `clm approve` names every request of the approver's person at that fingerprint the fold holds after its fetch; the web app's approve names those in the person's web ledger.
- **The old calls go.** `land.approval` offers the head and the hold check in their new forms (`Repo::branch_head`, `Repo::held` with the signed base) beside the old ones until `clm land` calls the new; `land.approval/old-calls-gone` then removes the old, which keeps this change live until that second build of `land.approval`.
- **What an older `clm` reads.** A light land's record parses as a code land, its signature verifying, since the unknown key is ignored; `clm ledger verify --review` says it can't rate the land (its `Gate-Rules: 7` is above the older `RULES`) and reports nothing else; `clm check` without `--review` reports nothing. An older `clm land` refuses a branch its newer gate reads `light`. An older `clm` reads an approval that has `clears` as one without it, clearing by time, so an older `clm land` keeps the clock fault for approvals a newer `clm` writes.
- Every Contract lists what its crate offers and what its callers read; every clause the code shows is stated with one scenario; each crate's command call states the help it writes, the description as the binary prints it.
