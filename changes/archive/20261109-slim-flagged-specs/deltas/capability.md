## MODIFIED Contract
The capability layer's tests (`human-layer-proof`): its requirements are the entries of `CAPABILITIES.md` (`model/reserved-ids`), and it builds those its bundle lists under `# Capabilities served` (`context`). Each test is black-box: it uses only what a person or client can touch at the product's public boundary and checks only what they can see, and it cites its capability as `req:capability/<slug>@<version>`.

## MODIFIED Design
**The boundary.** For CLM the boundary is the `clm` binary (`CARGO_BIN_EXE_clm`), run in a temporary git repository whose `origin` is a bare repository beside it, so proposing, claiming, approving and landing push and fetch as they do for a person; and `clm hook`, given the hook event Claude Code would send on standard input, for `guard-sessions`. A capability that needs GitHub runs with a fake `gh` on `PATH` that records its arguments and answers from fixture files; `git-host`'s bare-server scenario runs with no host at all. The web app's and the panel's capabilities have boundaries of their own, below.

A scenario that starts with a skill (`/clm:propose`, `/clm:triage`, `/clm:build`) is tested from the commands the skill runs, in the order it runs them, with no Claude session. A model, the network and any paid service lie beyond the boundary and are stubbed, so every test is deterministic.

**Where the tests live.** One file per capability, `crates/clm/tests/capability/<slug>.rs` with `-` as `_`, each a module of the one integration-test target `crates/clm/tests/capability/main.rs`, which holds only the `mod` lines and the shared harness (the temporary repository, its bare remote, the fakes). The target lives in `crates/clm` because only there does cargo give a test the binary's path; the root's `paths` leave the directory to this component. The tests import no crate's code: they run the binary. The capabilities a person reaches through a browser or a pane live in two npm packages of this component's own (`capability-browser-packages`), not in `web/` or `plugin-panel/`, whose component owns every file under them (`check/paths-disjoint`): `capabilities/web/`, one Playwright spec per capability, `<slug>.spec.ts`, and `capabilities/panel/`, one vitest file per capability. Neither imports a file of `web/`, `plugin-panel/` or `crates/` by a literal path, mocks included (`capability` can't depend on the optional `web`, `optional-nodes`); each keeps its fixtures and fakes in the package, installs with `ignore-scripts` (`unattended-commands`), and pins its test tools to the versions `web/` resolves, so one Chromium revision is cached for both. Neither runs `tsc`: Playwright and vitest strip types, and the code under test is type-checked by its own component.

**The web app** (`capabilities/web/`). The boundary is a phone-sized Chromium page on the built app as it is deployed, the browser app and the Worker run by Miniflare, with the site at `/` and the app at `/app/` as the zone's routes serve them (`public-site`, `site-worker-of-its-own`). GitHub lies beyond the boundary: Miniflare's outbound hook answers every request the Worker makes from a fake GitHub of the package's own, backed by a real git repository, and a request it doesn't answer fails the test, naming the method and path. Sign-in runs the Worker's own flow, with only GitHub's side faked. Each scenario uses its own owner and repository name, since the Worker's caches outlive a test. Umami lies beyond the boundary too: its script is routed to a fake that records the tag and each `window.umami.track` call, and a request to any other outside host fails the test.

**The panel** (`capabilities/panel/`). The boundary is the panel's plugin directory, `plugin-panel/`, reached only through `plugin-panel/hooks/hooks.json` as Claude Code loads it: the package's fake engine imports each module its `modules` names and calls its default export, so the package adds no import edge to `plugin.panel` (`check/undeclared-imports`). The fake runs real processes, so the pane runs the real `clm` and `git`, the binary the package builds first on `PATH`.

**Order.** A capability is built after the rules that serve it, and that order is the queue's (`check.coverage/pending-report`, `orchestrator.run/capability-waits-for-changed-rule`), not a `#### Needs`, which an entry can't hold, nor a dependency, so this required component doesn't depend on the optional `web` (`serving-rules-order-capabilities`, `optional-nodes`).

**A rule that changes what a test sees.** The build of another component's requirement that changes what a capability test observes updates that test's expectations, and the steps that reach them, in its own branch, keeping its citation and every check the entry's scenarios state, since this component holds no requirement that could carry the move. A requirement under which an entry as written doesn't hold is a change to the entry, in `CAPABILITIES.md` (`path-ownership`, `capability-tests-follow-rules`, `requirement-blocks`).

**Selection.** `capabilities/web/` and `capabilities/panel/` are not among this component's dependencies (`web` can't be, `optional-nodes`), so `ci-check.sh` runs them itself (`ci/selected-tests`, `ci/web-checks`).
