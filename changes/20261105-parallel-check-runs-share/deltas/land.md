## MODIFIED Contract

Landing a branch on `main`, on the machine that runs the command (`land-locally`). `clm land [<branch>]` runs the gate against `origin/main`, merges the branch in a scratch tree, runs the project's check command, handing it the tests the change can break as `clm affected` selects them (`CLM_SELECTION`, `graph-test-selection`), and `clm check` on the result unless the ledger says that code was already checked, records what it did in the ledger, and pushes the merge commit to `main` without force, retrying when `main` moved. It is the only thing in CLM that pushes `main`. What it keeps in a clone, the land tree, the shared target `.clm/land`, its lock, the check lock `.clm/check.lock` and failing checks' logs, is under the `.clm/` of the main worktree's CLM root, which `clm init` has the repository ignore, so a land leaves nothing untracked whatever the project's language (`land-places-ignored`). It prints `landed <sha> <kind>`, `<kind>` being `code`, `spec` or `spec review` as the gate's first line gives it, and exits 0; it exits 1 with the reason when it pushed nothing, and 2 on a git failure. Whether the branch is approved or held by a request for changes, and the signing of approvals and lands, are `land.approval`'s, as is `clm approve`, which `clm-land` re-exports. There is no after-merge review: a land that needs review lands only once approved (`yes-no-review`). `clm reconnect` pushes a `main` landed offline when it fast-forwards `origin/main`, with the local ledgers. `clm land --check-only` runs the same check command and `clm check` on the current working tree, and lands and records nothing, so a session learns the land check's verdict through a command that names no path (`land-check-command`). The check command of a land or a `--check-only` run waits for any other check of the same clone to end first (`check-runs-one-at-a-time`), so either can take as long as the checks queued before it.

## MODIFIED Design

Crate `clm-land`, called from `crates/clm`'s `land`, `approve` (re-exported from `clm-approval`) and `reconnect` subcommands. Every git call goes through `clm-git`, the remote's name taken from `REMOTE` (`git-plumbing-layer`).

**`clm land [<branch>]`**, default the current branch, refused on `main`. Each attempt, up to ten:
1. Fetch `origin` (`main`, the branch, `clm/ledger/*`) and fold the ledger. Take the head, its fingerprint and change IDs from `land.approval`. In a signed repository its key check comes first, then its hold check, then whether the fingerprint is approved under the policy at the fetched base: all before the gate, the lock, the merge and the checks.
2. Run the gate on the head against `origin/main` in the tree this attempt checks in (**Places**, below), adding `--approved` when approved. A violation prints as the gate printed it and exits 1; `gate/approval` tells the caller to ask the human for `clm approve <branch>`.
3. `git merge-tree --write-tree origin/main <head>`. A conflict, or `specs/` changed on both sides, exits 1 telling the caller to run `clm rebase`.
4. The merge commit, `git commit-tree <merged tree> -p origin/main -p <head>`, message `Merge <branch> into main`, with `Change: <id>` on a following line for a spec land that adds or modifies live changes (the first by ID), committed as the repository's git user. A head that already contains `main` is still merged with a merge commit, so a claim's tip reaches `main` only through its land (`merged-claims-released`). The commit is checked out detached into the tree, so the gate and the checks run on a commit. Then **Derived specs** (below).
5. The merged tree's code key (`ledger`). When a `checked` record names it with the same command, it asks **Readers of checked code** (below): when they select no file, only `clm check --no-detectors` runs; when they select some, `[land] check` runs as below with their selection and then `clm check --no-detectors`, and no second `checked` record is appended; otherwise **Selected tests** (below), `[land] check` through `sh -c` with `CI` unset (so a script that installs a browser only in CI doesn't) and `CARGO_TARGET_DIR` set to `<home>/.clm/land` unless the caller set it non-empty, and then `CARGO_INCREMENTAL=0` unless the caller set that non-empty (`shared-land-target`), then `clm check`, and on success a `checked` record. `<main>` is the first worktree `git worktree list --porcelain` lists and `<home>` the CLM root in it, `<main>/<prefix>` with `<prefix>` what `git rev-parse --show-prefix` prints in the CLM root, computed once; a land from a build's worktree under `.claude/worktrees/` so shares one target (`build-places`). The gate then runs again on the merge commit, since a file both sides touched can change whether it needs review, and in a signed repository `land.approval` signs the `landed` record.
6. `git push origin <merge>:refs/heads/main --force-with-lease=refs/heads/main:<the base step 1 fetched>`. A refusal isn't always `main` moving (`land-push-retry`), so it fetches `origin`'s `main` again, directly rather than through step 1's offline refusal, and judges it: the merge commit means the push went through; neither the merge commit nor the base means `main` moved and the next attempt starts, its `checked` record standing, so a retry with the same code key runs only `clm check --no-detectors`; still the base means a refusal for another reason, such as `[remote rejected] main (failure)` while other sessions push, and the same commit is pushed again with the same lease at most twice more, after fixed waits of 1 and then 2 seconds with no override, these pushes not counting as attempts. Still the base after the last is exit 2 with git's message, including the remote's lines (the push drops `--quiet` if it hides them), and a line saying the failure may be transient and that running `clm land <branch>` again is safe. When the refetch fails the push may have gone through, so it exits 2 with the push's message alone. Ten moved attempts exit 1 saying `main` keeps moving.
7. Append, in one commit (`ledger/append-all`), the `effort` records `clm effort record --branch <branch>` would append for the branch's sessions on this machine, read once before the first attempt so neither the reading nor a second ledger push lengthens the time `main` has moved with no `landed` record (`effort-accounted`; the reader's warnings print prefixed `effort: `, and when it can't read at all it warns `effort not recorded: <why>`), then `landed`: commit, branch, `land_kind` and `review` from the gate's first line, fingerprint, the step-5 code key as `code_key`, the change IDs. When `append` reports `landed` unpushed and `host` isn't `none`, it warns `the landed record isn't on origin yet: git push origin clm/ledger/<person>/<clone>` and still exits 0, since `main` has moved. Then `host`'s `branch delete <branch> --lease <head>` for an `impl/*`, `spec/*` or `propose/*` branch (a failure warns), the local branch too when it is checked out nowhere (`clm wrap-up` tidies one that is), and for `impl/*`, **Freeing a build's disk** (below).
8. Print `landed <sha> <kind>`.

**Derived specs** (`derived-specs-fingerprint`). When the head adds a change (`clm-gate`'s `added_changes` over the merge base's and the head's `ls-tree -r -z` listings, the question `gate.fingerprint/fingerprint` asks), or applies one (a change whose `change.md` parses with status `proposed` or `approved` at the base, `origin/main`'s, and in the merge commit has status `applied`, or is gone while `changes/archive/<id>/change.md` has status `done`, as `sync`'s Design defines it: `regenerate-applied-live-changes`), the IDs of the added changes whose `change.md` in the merge commit parses with status `applied` (live) or `done` (new archived), and of the applied ones, sorted, go to `sync.regenerate`'s `regenerated` (crate `clm-regenerate`, which reaches no `clm-health`: `clm/health-isolated`) without its stale-delta merge (`sync.regenerate/regenerated-tree`), run with the tree holding the merge commit as `root` and the fetched base's commit SHA as `onto`, so the scratch `specs/`, the copied `changes/` and `backlog/` and the re-apply are `clm rebase`'s own. A stop exits 1 with rule `land/derived-specs`, the lines it returned and `clm rebase`; otherwise the regenerated `specs/` and the merge commit's are compared byte for byte, a symlink by its target, over the union of their paths in byte order, a path on one side only being a difference, and the first difference exits 1 naming it. It runs before step 5, so before the `--no-detectors` run too. The fingerprint skips `specs/` on a head that adds a change, so this is what keeps an approval from covering a hand edit there. A head that applies a change and adds none keeps `specs/` in its fingerprint, which reads listings alone and can't see a status, so a sync that regenerates its `specs/` onto a `main` that changed them asks for its approval again.

**Places** (`scratch-outside-git`, `land-tree`, `fixed-land-tree`). Cargo names a workspace's outputs by its path and judges them fresh by file times, so two lands that overlap on one target can check each other's code, and a fresh path per land rebuilt everything (43 GB a day on one machine). Before step 2 an attempt computes the merged tree and its code key (`git merge-tree --write-tree` writes only objects); when its check will compile into `<home>/.clm/land`, it takes the exclusive advisory lock on `<home>/.clm/land.lock` (`land-target-lock`, `<home>/.clm/` created when missing, released by the system when a land is killed), printing `waiting for another land's check on <home>/.clm/land` on stderr once when it waits, with no time limit, and holds it until the push has gone through and the cap is applied, or the attempt ends; the append, the deletes and the print run outside it. **The cap** (`land-target-cap`): right after a push that went through, still under the lock, it sums the lengths of the regular files under `.clm/land` (no symlink followed, so a sparse file counts its length) and, above `[land] target_cap_gb` gigabytes, removes the directory and prints `cleared .clm/land (<n> GB, cap <cap> GB)`; an unreadable entry or a failed removal only warns. Incremental data and units for feature sets no land builds again are what grow there, and Cargo prunes neither, so the cap trades one cold land for a bounded directory, and each attempt takes it afresh. A merge that conflicts, a checked code key whose readers select nothing, and a caller's `CARGO_TARGET_DIR` take no lock. **The check lock** (`check-lock`): whatever the target, the run of `[land] check` itself, by a land or by `--check-only`, holds a second exclusive advisory lock, on `<home>/.clm/check.lock`, from just before the command is spawned until it exits, taken with the same helper as the land lock (`lock.rs`, generalised to take the lock file's path and the waiting line) and printing exactly `waiting for another check on <home>/.clm/check.lock` on stderr once when it waits, with no time limit; a lock file that can't be created or locked is exit 2, as the land lock's is. The lock is taken inside the helper both callers share for running `[land] check`, before the output pipe is read, and dropped when it returns, on every path. The project's tests share the host, not only the target: a test that binds a fixed local port fails in whichever of two overlapping checks starts second, for a reason that isn't its branch's. A land takes it after `land.lock`, never before, and `--check-only` takes only it, so neither can wait on the other in a cycle; `clm affected`, `clm check` and the gate run outside it. A locked attempt checks out in the land tree `<home>/.clm/land-tree` (checks of a root in a subdirectory run in `<home>/.clm/land-tree/<prefix>`): when `git worktree list --porcelain` lists it (both canonicalised) and it exists, `git checkout --quiet --force --detach <commit>` and then `git clean --quiet -fdx`; otherwise, or when either fails, it removes the path, runs `git worktree prune` and `git worktree add --quiet --detach <path> <commit>`, a failed add being exit 2. The tree stays when the attempt ends; `clm land` and `clm wrap-up` never remove it, and removing it by hand starts the next land cold. Any other attempt uses a fresh `land-*` worktree under `TMPDIR` (read through the injected environment lookup) or else `std::env::temp_dir()`, removed on every exit path, never one under `.claude/worktrees/`, and outside the repository, so no tool that refuses paths under `.git/` (Vite's `server.fs.deny`) or walks up to project files trips on it; a killed land's tree stays until the system clears it.

**Its own binary** (`land-binary-copy`). A check that rebuilds `clm` can replace the file `clm land` runs from. So before its first subcommand it copies `std::env::current_exe` into a fresh `land-bin-*` directory beside its temporary worktrees, keeping permissions, and runs the gate, `clm affected` and `clm check` from the copy, removed on every exit path; when the copy can't be made it exits 1 naming the path. The lander's binary is `main`'s rule, which the merged tree lives under. `CLM_GATE`, `CLM_CHECK` and `CLM_AFFECTED` override the three commands, run as given, so tests fake them.

**Selected tests** (`graph-test-selection`). Before `[land] check` it runs `clm affected --base <sha>`, `<sha>` the fetched base's commit (the merge commit's merge base with it, so the selection is what the branch brings), in the tree on the merge commit and under the land lock when the check holds it (the check lock covers `[land] check` alone), and writes its stdout unchanged to `selection` in a temporary directory, which `CLM_SELECTION` names. When it fails, `clm affected failed: <the first non-empty line of its stderr, or the spawn error>; the check runs every test`, and the check runs without `CLM_SELECTION`: a failed selection costs time, never a skipped test.

**Readers of checked code** (`doc-readers-marked`). `code_key` leaves the doc-only paths out, so a `checked` record says nothing of the tests that read them: a spec branch's prose can fail such a test (a retired term under `specs/`) on a tree whose code was checked. A land whose code key is checked checks the merge commit out into a temporary worktree, as an attempt with no lock does, and runs `clm affected --base <sha> --readers` there (`check.affected/affected-readers`), `<sha>` as in **Selected tests**. When it prints nothing, the attempt goes on in that worktree as before, with no lock. The gate on the head and **Derived specs** have run by then, in that worktree. When it prints a line, the attempt removes that worktree and goes on as one whose check runs: it takes the lock when the check compiles into `.clm/land`, checks the merge commit out into the land tree (a caller's `CARGO_TARGET_DIR` keeps the temporary worktree, with no lock), so the check reuses the warm target, and runs `[land] check`, so the readers' tests alone, with `CLM_SELECTION` naming a file holding that output unchanged. When it fails, it prints `clm affected failed: <reason>; the check runs every test` as **Selected tests** does and goes on the same way with `CLM_SELECTION` unset. A failing check exits 1 as any land's does.

**The check's output** (`land-check-log`). One pipe (`std::io::pipe`) carries `[land] check`'s stdout and stderr in the order written, copied to stderr and to `<home>/.clm/land-logs/<branch>.log`, the branch's slashes as directories, created and truncated first; the last 40 lines (split on `\n`) are kept in memory. It reads until the pipe closes, so a check must end what it starts. A failing check's refusal, printed last as `clm land: <why>`, is `last 40 lines of `<check>`:`, those lines and `` `<check>` fails on the merge with main; its output is at <path> ``, and the log stays; a passing check removes it. A log that can't be created warns naming the path, and the refusal then has no `; its output is at` clause. `clm check`'s output isn't logged.

**Freeing a build's disk** (`land-frees-build-target`). After the push and the append of an `impl/*` land it deletes the `target/` at `git rev-parse --show-toplevel` when that is a linked worktree whose `HEAD` is the landed branch, printing `removed <path>`; a missing one is skipped and a failed delete warns. `clm run --finish` removes the worktree itself (`orchestrator.run`).

**`--check-only`** (`land-check-command`). Given a branch as well it exits 1 (by hand: clap's `conflicts_with` would exit 2) and runs nothing. On any branch, in the CLM root (`--root`, else found from the current directory), it runs `[land] check` as step 5 does but with `CARGO_TARGET_DIR` as the caller has it, so a build compiles into its own `target/`, then `clm check` with its detectors (`CLM_CHECK` overrides it), on the working tree as it stands, output on stderr. It prints `checks pass`; otherwise exits 1 with `` `<command>` fails `` or `` `clm check` fails ``, the failure messages being a parameter of the helpers a land shares; a `clm.toml` that doesn't load is exit 1 with `config`'s message. Its check command runs under `<home>/.clm/check.lock` (**The check lock**, above), `<home>` found from the main worktree as a land finds it, so a build's or a draft's pre-land check waits for every other check on the clone, a land's included, rather than failing beside it. It reads no ledger and a working tree has no code key, so it never lets a land skip its check. It exists for a build's pre-land check (`orchestrator.run`), which Claude Code's worktree isolation refused as a script path.

**Offline** (`no-local-land-with-remote`). With `host = "none"` the base is the local `main`, there is no fetch or push, the records stay local, and it prints `landed <sha> <kind> (local)`. With any other host `main` has one copy, the remote's, so a failed step-1 fetch exits 1 with `offline: origin can't be reached; push and land when it can`. **`clm reconnect`**, for a repository that gains a remote, pushes `main` with a lease when `origin/main` is missing or an ancestor, then every local `clm/ledger/*` branch, and prints `reconnected <n> lands`; when `origin/main` has moved it pushes only the ledgers, prints `land again <branch>` for each local land (the merge commit's second parent) and exits 1.

## ADDED Requirements

### Requirement: check-lock
Every run of `[land] check`, by `clm land` or by `clm land --check-only`, whatever `CARGO_TARGET_DIR` the caller set, SHALL hold an exclusive advisory lock on `.clm/check.lock` in the CLM root of the repository's main worktree (the first worktree `git worktree list --porcelain` lists), whichever worktree of the repository it runs in, from before the command starts until it exits, releasing it on every exit path, so that no two checks of one clone run at the same time. A run that waits for the lock SHALL say so on stderr once, naming `.clm/check.lock`, and wait with no time limit. A land that also holds the lock on `.clm/land.lock` (`land-target-lock`) SHALL take it after that lock. `clm check`, `clm affected` and the gate SHALL NOT run under it, and a land that runs no `[land] check` SHALL NOT take it.

#### Scenario: overlapping check-only runs
- GIVEN two linked worktrees of one clone, a `[land] check` that appends `start <worktree>` to a log outside both, sleeps 2 seconds and appends `end <worktree>`, and a fake `CLM_CHECK` that passes
- WHEN `clm land --check-only` starts in both at once
- THEN both print `checks pass`, in the log every `start` is followed by the `end` of the same worktree before any other `start`, and the run that waited printed `waiting` naming `.clm/check.lock` on stderr

#### Scenario: a check-only run beside a land
- GIVEN a branch `impl/a` with no `checked` record, a linked worktree, and the same logging `[land] check`
- WHEN `clm land impl/a` and `clm land --check-only` in the linked worktree start at once
- THEN the land lands, the check-only run prints `checks pass`, and the two checks never interleave in the log

#### Scenario: a land with the caller's target
- GIVEN two branches `impl/a` and `impl/b`, no `checked` records, the same logging `[land] check`, and `CARGO_TARGET_DIR` set to a different directory for each land
- WHEN `clm land impl/a` and `clm land impl/b` start at once
- THEN both land and the two checks never interleave in the log

#### Scenario: released after a failing check
- GIVEN a `[land] check` that exits 1
- WHEN `clm land --check-only` runs and then a second `clm land --check-only` runs
- THEN both exit 1 naming the check command, and the second doesn't print `waiting`

#### Scenario: checked code takes no check lock
- GIVEN a branch that changes only `specs/x/SPEC.md`, a `checked` record for `origin/main`'s code key, and another process holding the lock on `.clm/check.lock`
- WHEN `clm land` runs
- THEN it lands without waiting and prints no `waiting` line

#### Serves
- capability/work-concurrently
- capability/land-safely

## MODIFIED Requirements

### Requirement: land-tree <!-- base: e1ccc61be69ea547 -->
An attempt of `clm land` that holds the lock on `.clm/land.lock` SHALL check the head and the merge commit out in `.clm/land-tree` in the CLM root of the main worktree, a detached worktree of the repository that it SHALL keep when the attempt ends. Before each checkout it SHALL make that tree exist and clean: when git lists the path as a worktree and its directory exists, `git checkout --force --detach` there and then `git clean -fdx`; otherwise, or when either fails, it SHALL remove whatever is at the path, prune git's worktree list and add the worktree afresh. Everything a land keeps in the main worktree, the land tree, `.clm/land`, `.clm/land.lock`, `.clm/check.lock` and `.clm/land-logs/`, SHALL be under that CLM root's `.clm/`, so that a repository whose `.gitignore` lists only the entries `clm init` adds (`init/init-ignores-local-settings`) shows none of it in `git status`.

#### Scenario: one tree for every land
- GIVEN two branches `impl/a` and `impl/b`, no `checked` records, and a `[land] check` that records its working directory
- WHEN `clm land impl/a` runs and then `clm land impl/b`
- THEN both checks ran in the main worktree's `.clm/land-tree`, and `git worktree list` names it afterwards, detached

#### Scenario: leftovers cleaned
- GIVEN the same branches and a `[land] check` that exits 1 when a file `left` exists in its working directory and otherwise writes it
- WHEN `clm land impl/a` runs and then `clm land impl/b`
- THEN both land

#### Scenario: tree repaired after .clm is removed
- GIVEN a land of `impl/a` that made the land tree, and the main worktree's `.clm/` then removed
- WHEN `clm land impl/b` runs
- THEN it lands and its check ran in `.clm/land-tree`

#### Scenario: stale directory replaced
- GIVEN a directory at the main worktree's `.clm/land-tree`, holding a file, that git lists no worktree for
- WHEN `clm land impl/a` runs
- THEN it lands, its check ran in `.clm/land-tree`, and the file is gone

#### Scenario: nothing untracked in a project that doesn't ignore target
- GIVEN a repository whose committed `.gitignore` lines are `clm.local.toml`, `.clm/` and `.claude/worktrees/` and nothing else, a branch `impl/a` with a passing `[land] check` that writes a file into `CARGO_TARGET_DIR`, and a branch `impl/b` whose `[land] check` exits 1
- WHEN `clm land impl/a` runs and then `clm land impl/b`
- THEN the first lands, the second exits 1, and `git status --porcelain` in the main worktree prints nothing, with no `target/` directory there
