## MODIFIED Design
It depends on `clm-model`, `clm-apply`, `clm-check` (for `format`, a violation as `clm check` prints it) and `clm-git`, and never on `clm-health`, `clm-ledger` or `clm-context` (`sync-regenerate-split`). `Tree::path` and `Tree::merged` are public for `clm-sync`'s mirror.

**The tree** (`sync/extract-through-layer`). `regenerated` extracts `onto`'s `specs/` into one temporary directory and `HEAD`'s other paths into a second with `clm-git`'s `extract_paths`, and moves the second's top-level entries into the first, so `clm_model::load` reads one tree: without the human layers, every `serves` naming an entry would be broken on both sides of `apply`'s before-and-after comparison (`apply/resulting-graph`). Only the violations under a change's own directory stop it, since only the change's own files can keep it from applying; `clm check` judges the rest.

**Order** (`reapply-order-follows-bases`). `regenerated` sorts `ids` and drops repeats itself, and picks the next change from the graph it loads for that step, before **Merge**'s reload, so a change's bases are read from its delta as committed. A change the graph doesn't hold (a `change.md` that doesn't parse) counts as having no unknown base, so ID order reaches it and its violations stop the run. A base `main` moved since is found in `onto`'s history, so a change stale only against `main` doesn't wait, and **Merge** takes it. The change picked last can still have an unknown base: a dependency the branch broke, or a base an earlier change produced before `main` moved the element.

**Stages** (`stale-delta-names-movers`, `stale-delta-shows-main`). The stages are the graphs the regenerate loads anyway. Taking the newest stage that holds a base finds a later change that restores an earlier hash at the later stage. The history walked is that of the component's `SPEC.md` as `clm-model` gives it at `onto`, without following renames, skipping a commit whose file doesn't parse. The diff has three lines of context. The merge line names the element's hash in the tree it was applied to rather than leaving it to `clm hashes`, which reads the working tree's `specs/`. The diff is the only place the author sees `main`'s new text when they rebase: updating the hashes alone would pass every check and drop that text when the branch lands.

**Merge** (`stale-delta-three-way-merge`). Each element is merged with `git merge-file` through `clm-git` on three texts: the element's text in the delta (a requirement's block as `clm-model` gives it, with its clean heading), the base's text and the element's text in the tree, each trimmed of leading and trailing blank lines. A conflict leaves the element as it is; `merge-file` failing to run is a git failure. The merged text replaces the element's text in the delta, located with `clm_model::outline`'s spans as `clm-apply` locates them, keeping the heading's slug and the surrounding blank lines. The base is replaced in place: `<key>: "<old base>"` in the frontmatter, so a flow map and a block map are both edited with the other keys untouched, and the `<!-- base: <hash> -->` comment in a requirement heading. A delta with CRLF line endings is never merged. An archived change's deltas are under `changes/archive/<id>/deltas/`, which `gate/archive-immutable` lets the branch edit. The merge takes the text, not the judgment: the merged section is in the branch's diff, `clm check` judges the result (`judged-by-check`), and on a branch that needs review the changed fingerprint asks a human to approve again (`tree-diff-fingerprint`).

**Other deltas.** An `applied` change is left alone because its bases record the text it was applied to. Only this branch's applied changes can have made such a delta stale, since one stale against `onto` itself fails `clm check` there, and the other change's author could do nothing about it until this branch lands.

**A transient `index.lock`** (`retry-index-lock`). Several sessions share one clone (`session-worktrees`, `build-places`), and Claude Code, hooks and the panel run `git` in it between a session's commands. The wrapper keys on the stderr text, not the exit code: `git rebase` exits 1 on the lock and `git add` and `git commit` 128. `merge-file`, `diff --no-index` and `clm-git`'s `fetch`, `current_branch` and `extract_paths` take no lock or use a temporary index, so they don't go through it. It lives here rather than in `clm-git` because only `clm rebase`'s two crates need it (`shared-plumbing-in-git`).
