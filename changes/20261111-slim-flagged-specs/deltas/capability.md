## MODIFIED Design
**The boundary.** For CLM the boundary is the `clm` binary (`CARGO_BIN_EXE_clm`), run in a temporary git repository whose `origin` is a bare repository beside it, so proposing, claiming, approving and landing push and fetch as they do for a person; and `clm hook`, given the hook event Claude Code would send on standard input, for `guard-sessions`. A capability that needs GitHub runs with a fake `gh` on `PATH`; `git-host`'s bare-server scenario runs with no host at all. The web app's and the panel's capabilities have boundaries of their own, below.

A scenario that starts with a skill (`/clm:propose`, `/clm:triage`, `/clm:build`) is tested from the commands the skill runs, in the order it runs them, with no Claude session. A model, the network and any paid service lie beyond the boundary and are stubbed, so every test is deterministic.

**Where the tests live.** One file per capability, `crates/clm/tests/capability/<slug>.rs` with `-` as `_`, each a module of the one integration-test target `crates/clm/tests/capability/main.rs`. The target lives in `crates/clm` because only there does cargo give a test the binary's path; the root's `paths` leave the directory to this component. The capabilities a person reaches through a browser or a pane live in two npm packages of this component's own (`capability-browser-packages`), not in `web/` or `plugin-panel/`, whose component owns every file under them (`check/paths-disjoint`): `capabilities/web/`, one Playwright spec per capability, `<slug>.spec.ts`, and `capabilities/panel/`, one vitest file per capability. Neither imports a file of `web/`, `plugin-panel/` or `crates/` by a literal path, mocks included, since `capability` can't depend on the optional `web` (`optional-nodes`); so neither is among this component's dependencies, and `ci-check.sh` runs them itself (`ci/web-checks`). Each keeps its fixtures and fakes in the package and installs with `ignore-scripts` (`unattended-commands`). Neither type-checks: the code under test is type-checked by its own component.

**The web app** (`capabilities/web/`). The boundary is a phone-sized Chromium page on the built app as it is deployed, the browser app and the Worker run by Miniflare, with the site at `/` and the app at `/app/` as the zone's routes serve them (`public-site`, `site-worker-of-its-own`). GitHub and Umami lie beyond the boundary: Miniflare's outbound hook answers the Worker from a fake GitHub of the package's own, backed by a real git repository, Umami's script is routed to a fake that records what the page tracks, and a request to any outside host the fakes don't answer fails the test. Sign-in runs the Worker's own flow, with only GitHub's side faked. Each scenario uses its own owner and repository name, since the Worker's caches outlive a test.

**The panel** (`capabilities/panel/`). The boundary is the panel's plugin directory, `plugin-panel/`, reached only through `plugin-panel/hooks/hooks.json` as Claude Code loads it, so the package adds no import edge to `plugin.panel` (`check/undeclared-imports`). The pane runs the real `clm` and `git`.

**Order and moves.** A capability is built after the rules that serve it, by the queue (`serving-rules-order-capabilities`), never by a `#### Needs` or a dependency. A rule whose build changes what a capability test observes updates that test in its own branch (`capability-tests-follow-rules`); a rule under which an entry as written no longer holds is a change to the entry, in `CAPABILITIES.md`.
