## MODIFIED Design

**The boundary.** For CLM the boundary is the `clm` binary (`CARGO_BIN_EXE_clm`), run in a temporary git repository whose `origin` is a bare repository beside it, so proposing, claiming, approving and landing push and fetch as they do for a person; and `clm hook`, given the hook event Claude Code would send on standard input, for `guard-sessions`. A capability that needs GitHub runs with a fake `gh` on `PATH` that records its arguments and answers from fixture files, as the component tests do; `git-host`'s bare-server scenario runs with no host at all. The web app's and the panel's capabilities have boundaries of their own, below.

A scenario that starts with a skill (`/clm:propose`, `/clm:triage`, `/clm:build`) is tested from the commands the skill runs, in the order it runs them, with no Claude session. A model, the network and any paid service lie beyond the boundary and are stubbed, so every test is deterministic.

**Where the tests live.** One file per capability, `crates/clm/tests/capability/<slug>.rs` with `-` as `_`, each a module of the one integration-test target `crates/clm/tests/capability/main.rs`, which holds only the `mod` lines and the shared harness (the temporary repository, its bare remote, the fakes). The target lives in `crates/clm` because only there does cargo give a test the binary's path; the root's `paths` leave the directory to this component. The tests import no crate's code: they run the binary. The three capabilities a person reaches through a browser or a pane live in two npm packages of this component's own (`capability-browser-packages`), not in `web/` or `plugin-panel/`, whose component owns every file under them (`check/paths-disjoint`):
- `capabilities/web/`: `follow-from-browser`, `review-capability-cost`, `learn-clm`, `see-site-use` and `publish-posts`, one Playwright spec per capability, `<slug>.spec.ts`.
- `capabilities/panel/`: `watch-beside-chat`, one vitest file, `watch-beside-chat.test.ts`.

Each package is private, has its own committed lockfile and a `test` script, and installs with `ignore-scripts` (`unattended-commands`), so `npm ci` and `npm test` in its directory run it. It builds the app it tests and pins its test tools to the versions `web/` resolves, so one Chromium revision is cached for both. It imports no file of `web/`, `plugin-panel/` or `crates/` by a literal path, mocks included (`capability` can't depend on the optional `web`, `optional-nodes`), and keeps its fixtures and fakes in the package. It runs no `tsc`: Playwright and vitest strip types, and the code under test is type-checked by its own component. The `clm` binary they drive is built with `cargo build -q -p clm` into the target directory `cargo metadata` names.

**The web app** (`capabilities/web/`). The boundary is a phone-sized Chromium page (a Pixel among Playwright's `devices`) on the app as it is deployed: the browser app and the Worker, run by Miniflare, the local runtime `wrangler dev` uses. The app is at `/app/` and the public site at `/` (`public-site`), two Workers on the zone (`site-worker-of-its-own`): the harness serves the site's build as static files at `/` and sends the app's paths to the app's Worker and its assets, as the zone's routes do. Playwright's `globalSetup` only builds: the app (`web/dist/`), the site (`web/site/`'s build), the Worker (a dev `worker-build`), and the `clm` binary. The build steps need `web/`'s and `web/site/`'s `node_modules`, which `ci-check.sh` installs first (`ci/web-checks`). Each spec file starts its own Miniflare in the test process, as a Playwright fixture on a free port, so its outbound-fetch hook and the test share the fake GitHub's state. Miniflare ignores `wrangler.toml`, so the package's config repeats the bindings the Worker needs, and a missing one shows as a failing test. The Worker's secrets are test values in the formats it expects (its App private key a PKCS#8 RSA key generated per run, the push keys unset).

GitHub lies beyond the boundary: the outbound hook answers every request the Worker makes from a fake GitHub of the package's own, backed by a real git repository the test builds with `git` and `clm` (a bare repository and a work tree). It answers the REST and GraphQL calls the scenarios reach and writes a ledger append to the repository as git objects and a ref update. A request it doesn't answer fails the test, naming the method and path. Each scenario uses its own owner and repository name, since the Worker's caches outlive a test. Sign-in runs the Worker's own flow: Playwright routes the browser's navigation to `github.com/login/oauth/authorize` back to the Worker's callback with that URL's `state` and a code, and the fake answers the code's exchange and `GET /user` as the first login of the invited list the build wrote, `web/dist/_clm/invited.json`.
- `follow-from-browser` needs an unsigned repository with a spec branch that needs review, and a clone of the fake's repository whose `clm.toml` sets `[land] check = "true"` and no `host`, on which `clm land` runs.
- `learn-clm` needs no sign-in: a page with no session opens `/` and the guide, with the harness's repository and fake GitHub there only because `startApp` takes them. It is built once `web/site-served-directly` is current, since before that the Worker refuses a page with no session: the queue holds it back until every rule that serves it has been built (`check.coverage/pending-report`, `serving-rules-order-capabilities`); `web`'s build moves this package's harness and specs to `/app/` (`path-ownership`).
- `publish-posts` needs no sign-in and no Worker: it builds the site from a fixture blog of its own (`BLOG_DIR`), as the site workflow builds it, serves the output as static files, and builds it again after setting a post's `draft` to `false`.
- `see-site-use` needs no sign-in and no Worker: it builds the site a second time with `UMAMI_WEBSITE_ID` set to a test ID and `SITE_OUT` a directory of its own, and serves that directory as static files, as the deployment's assets do. Umami lies beyond the boundary: Playwright routes `https://cloud.umami.is/script.js` to a fake script of the package's own that records the website ID and attributes of the tag that loaded it and defines `window.umami.track`, recording each call, which the test reads from the page. A request to any other outside host fails the test.
- `review-capability-cost` needs a fixture `CAPABILITIES.md` and a history made as a person's would be: `impl/*` branches landed with `clm land` after `clm effort record --transcripts <dir>` reads fixture Claude Code transcripts (Claude Code lies beyond the boundary).

**The panel** (`capabilities/panel/`). The boundary is the panel's plugin directory, `plugin-panel/`, loaded as Claude Code loads it: the package's fake engine reads `plugin-panel/hooks/hooks.json`, imports each module its `modules` names by the path it reads there, and calls the module's default export with its `$`. As the web package reaches the app only through its build, this one reaches the panel only through its manifest, so it adds no import edge to `plugin.panel` (`check/undeclared-imports`). The package's vitest config aliases `'claude-code'` to the fake, which supplies `atom`, `read` and `update`; a setup file defines the engine's globals `h` and `Fragment`, and classic JSX on `h` applies to files outside the package's root. The fake's `$` supplies the calls and events the module uses, a clock the test advances, a re-render on every atom change, and a renderer that turns the pane's elements into lines of text. Its `$.process.run` runs real processes, so the pane runs the real `clm` and `git`: the fake's plugin root holds no `bin/clm`, and `PATH` starts with the directory of the binary the package builds. `watch-beside-chat` needs a temporary repository with a bare remote in which a build lands (`clm land` of an `impl/*` branch, its check command `true`) while the pane is open, and the clock advanced past the pane's fetch and redraw intervals. That Claude Code itself loads the module is `ci/panel-validate`'s, not this test's.

**Order.** A capability is built after the rules that serve it: `clm pending` blocks a pending capability on each `unbuilt` requirement whose effective serves names it, on any component, `web`'s and the panel's included (`serving-rules-order-capabilities`). That order is the queue's, not a `#### Needs`, which an entry can't hold, and not a dependency, so it doesn't make this required component depend on the optional `web` (`optional-nodes`). A build that finds a capability's test can't pass because a rule it exercises is `behind` stops at that capability and records why (`requirement-blocks`).

**A rule that changes what a test sees.** A requirement of another component can change what a capability test observes at the boundary, such as the app's opening screen or a command's message. The build of that requirement updates the test's expectations, and the steps that reach them, to what the requirement states, in its own branch, since its land runs this component's tests and this component holds no requirement that could carry the move; it keeps the test's citation and every check the capability's scenarios, as `CAPABILITIES.md` states them, state, and names the fix under `## Fixes in other components` in its pull request (`path-ownership`, `capability-tests-follow-rules`). The change that adds the requirement names those tests in its text when its builder check finds them, as `web/app-at-app-path` names the harness it moves. A requirement under which a capability entry as written does not hold is a change to the entry: the change edits `CAPABILITIES.md`, the rule's build moves the tests to the entry's new text with their citations at the old version, and this component, `behind` until then, re-cites them in its own build. A build that finds an entry the change missed leaves its requirement unbuilt and files a `question` item with `blocks` naming it (`requirement-blocks`).

**Selection.** This component depends on the root, so a change anywhere in the CLI's tree selects its tests; `capabilities/web/` and `capabilities/panel/` are not among its dependencies (`web` can't be, `optional-nodes`), so `ci-check.sh` runs them beside `web/`'s and `plugin-panel/`'s suites (`ci/selected-tests`, `ci/web-checks`). A selected file under `crates/clm/tests/capability/` runs `clm`'s integration tests, and one under `capabilities/web/` or `capabilities/panel/` runs that package; the release's full run is the backstop for changes the dependant walk doesn't select.

**How many.** Coverage counts one citation per capability; that each of its scenarios has a test is the method's rule and the `spec-auditor`'s finding, not a program's.
