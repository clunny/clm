## MODIFIED Contract
`clm unreferenced [--root <dir>] [--allow <entry>]... [--entry <attribute>]...` lists the public items of a workspace's libraries that nothing outside their own library uses, one line per item, and exits 1 when it lists any, so a project can name it as one of its dead-code detectors in `clm.toml` (`dead-code-detectors`, `public-item-detector`): `command = ["clm", "unreferenced"]`, with an `--allow` pair per accepted exception and an `--entry` pair per Rust attribute that marks an item called from outside Rust beyond those the detector knows (`unreferenced-entry-attributes`). A library is a Rust package with `src/lib.rs`, whose public items are its `pub` items, or a TypeScript or Python package, whose public items are the names its entry modules export (`unreferenced-package-api`). rustc's `dead_code` lint, `knip` and `vulture` each assume or see one package; in an application workspace a public item rarely has users outside it, and this detector covers that gap. A type that a used public item names in its signature counts as used (`unreferenced-signature-carriers`). It exits 0 when it lists nothing, including in a repository with no library, and 2 when it can't read the repository, with one line `clm unreferenced: <cause>` on standard error and nothing on standard output.

`clm-unreferenced` offers `clm unreferenced` as a call (`commands-in-crate`, `commands-live-in-their-crates`): it takes the command's arguments as the command line gives them, the repository root, the environment as a lookup, which it doesn't read, and a stream each for standard output and standard error, and returns the exit status: besides those above, 2 for arguments it can't parse or a stream it can't write, and 0 for `--help`, with the help on standard output. Its arguments are `Args`, which `crates/clm`'s parser reads, `root` holding the `--root` given. `crates/clm` routes the command to it and adds nothing to what it writes.

An item marked `clm:remove-by <change-id>` is not listed (`unreferenced-skips-marked-old-paths`): it is the old path of an `expand-contract`, which nothing is meant to use once its users have moved, and `check/remove-by-markers` fails the marker once its change isn't live, so the item is skipped only while its removal is planned.

## MODIFIED Design
Crate `clm-unreferenced`, a library holding the command's call, dispatched from `crates/clm` as `clm unreferenced`; this component's build edits `crates/clm/src/main.rs`, `Cargo.toml` and `Cargo.lock` for it, as the root's Design says. `--root`'s default is the root's (`clm/root-from-cwd`), so a project without CLM's specs gets its whole workspace. Behind the call, `scan(root, allow, entry)` returns the lines the command prints, or the error line without the `clm unreferenced: ` prefix the call adds; it is public so the crate's tests can reach the scan without streams, and the Contract doesn't offer it, so no other crate calls it. It lists tracked files with `git ls-files --cached` through `clm-git` and reads them from the working tree, skipping a tracked file missing from it, as `clm survey` does, and reading a source file's bytes as UTF-8 with invalid sequences replaced. It reads only the manifests, sources and embedding files `report` lists, and never parses an embedding file. It parses Rust, TypeScript (the `typescript` language for `.ts`, `.mts`, `.cts`, `.js`, `.mjs` and `.cjs`, the `tsx` language for `.tsx` and `.jsx`) and Python with the `tree-sitter`, `tree-sitter-rust`, `tree-sitter-typescript` and `tree-sitter-python` crates at the version strings `clm-init`'s `Cargo.toml` pins, copied rather than moved to the workspace, so the workspace builds one copy of each grammar without touching `init`'s files (`tree-sitter-analysis`); it walks each syntax tree with a cursor rather than queries, so it needs no `streaming-iterator`. Each language is a module of its own (`rust.rs`, `typescript.rs`, `python.rs`) that reads a file into one shape: the names it declares and exports, with their lines, its carriers, and its mentions; `scan` then matches each language's items against mentions in that language's files, so a Python name and a TypeScript name never hide each other. It reads `Cargo.toml` and `pyproject.toml` with the workspace's `toml` and `package.json` with the workspace's `serde_json`. A file tree-sitter parses with errors is used as far as it parses, never a failure. It never runs `cargo`, `npm`, Node.js or `python`: the tracked files are the workspace, so the result is the same on every machine and needs no build.

What only a `clm` process shows, `clm check` naming `clm unreferenced` as a detector and the root found from a subdirectory, is the root's to state and prove (`clm/check-across-components`, `clm/root-from-cwd`).

**Libraries.** Each tracked `Cargo.toml` with a `[package]` table is a package rooted at its directory; a tracked file belongs to the package with the deepest root that holds it. A package is a library when it has a tracked `src/lib.rs`, named `[lib] name` when that is a string, else `package.name` with `-` replaced by `_`. Its *library files* are the module tree of `src/lib.rs` as rustc finds it (`unreferenced-library-modules`), `m.rs` and `m/mod.rs` both when both are tracked, as `public-items` spells out; a declaration carrying `#[path]`, one inside a block, or one whose file isn't tracked isn't followed. Every other `.rs` file of the package (`src/main.rs` and the modules it declares, `src/bin/`, a file no module declares) is not a library file: its items aren't listed, and its mentions count as uses from outside the library.

**Public items.** In each library file, the detector lists the items whose visibility is exactly `pub` (not `pub(crate)`, `pub(super)`, `pub(self)` or `pub(in …)`) declared directly in a module, the file's or an inline `mod { }` at any depth: `fn`, `struct`, `enum`, `union`, `trait`, `type`, `const` and `static` items, and the `fn` and `const` items of an inherent `impl` block (one without `for`) declared directly in a module. Items inside function bodies or other blocks aren't listed. A full name carries no module path: `<crate>::<name>`, or `<crate>::<Type>::<name>` for an `impl` item, where `<Type>` is the last path segment of the `impl`'s type without generic arguments, references or `dyn`. Two items with one full name are two findings, and one `--allow` entry skips both.

It skips test code, as `public-items` defines it: items, `impl`s and inline modules under a `#[cfg(…)]` that holds only when `test` is set, files opening with such a `#![cfg(…)]`, and the module tree of a `#[cfg(test)] mod m;`; `not(…)` never counts, so `cfg(not(test))` code is checked. It skips entry points called from outside Rust: an item, or an item of an `impl` block, carrying an attribute whose last path segment (`#[worker::event(fetch)]` → `event`) is `no_mangle`, `export_name`, `wasm_bindgen`, `proc_macro`, `proc_macro_derive` or `proc_macro_attribute`, or one given with `--entry`, bare or inside `unsafe(…)`, with or without arguments. `cfg_attr` isn't looked into. `pub use`, `pub mod`, macros, fields, variants and trait members aren't listed: a re-export or a module is used through the names it exposes, which are listed where they are declared.

**References.** An item is used when its name, the last segment for a method, appears as a whole word (bounded by characters other than ASCII letters, digits and `_`) in the text of any tracked `.rs` file other than its own library's files, outside plain comments as tree-sitter parses them. Strings count, so a name that a derive attribute or a macro spells as a string is used, and doc comments (`///`, `//!`, `/** */`, `/*! */`) count, so a use in another crate's doctest is a use. That file may be in another package, or among the same package's files that aren't library files. Matching by name is shallow on purpose: two items sharing a name hide each other, which can only miss dead code, never report live code, so no `use` path or type has to be resolved.

A use from outside can also reach an item through a name its library declares for it, so a library file's *carriers* count too (`unreferenced-carriers`). Outside test code, and at any depth, function bodies and blocks included, a `macro_rules!` carrying `#[macro_export]` (bare, as `#[macro_export(local_inner_macros)]`, or among other attributes) carries every whole word of its body, the whole token tree after its name with matchers and every rule included, outside plain comments, under the macro's name, so `$crate::helper()` in an exported macro carries `helper`; and a `use` declaration whose visibility is exactly `pub` carries, for each `<path> as <alias>` in it (`pub use inner::orig as renamed;`, `pub use inner::{orig as renamed}`), the path's last segment under `<alias>`, unless that segment is `self`, `super`, `crate` or `*`, or the alias is `_`. A name is *used from outside* its library when it is mentioned outside the library's files, or when one of the library's carriers carries it under a name used from outside, followed to any depth (a macro calling another exported macro, a re-export of a re-export). An item is used when its name is used from outside its own library. A carrier never makes a name used by itself: an exported macro or renamed re-export nothing outside mentions carries nothing.

A public item's *signature* is a carrier too (`unreferenced-signature-carriers`): a type another crate receives from a function it calls, or reads as a public field, is used though the caller never spells it, and `pub(crate)` on the type would make the signature a `private_interfaces` warning. So every exactly-`pub` item of a listed kind carries the whole words of its signature's types under its own name, and an `impl` block the words of its header under its type's name, as `signature-carriers` lists them. A restricted-visibility field or item carries nothing, since only the library reaches what it names. The words are matched like any mention, so a parameter `file: PlaceFile` carries `file` too, which can only miss dead code. Carrying follows to any depth with the other carriers: `blockers_view` used outside makes `BlockersView` used, its public field `root: Root` makes `Root` used, and `Root`'s public field makes `Held` used.

**TypeScript and Python packages** (`unreferenced-package-api`). Neither language has a package-private visibility, so an `export`, or a Python name without a leading `_`, is also how a package's own modules share code; listing every one would report that sharing wholesale. A package's public items are therefore the names its *entry modules* expose, each listed where it is declared, `<package>::<name>` (`@acme/core::parse`, `acme_core::parse`) at the declaration's path and line, re-exports followed within the package. The rest of the rule is Rust's: a package's *files* are its sources other than its *test files*, which count as outside like a Rust package's `tests/`; an item is used when its name is a whole word, outside plain comments, in a file of its language outside the package, or carried under a used name.

A TypeScript package is a tracked `package.json` whose `name` is a string, rooted at its directory, a file belonging to the deepest package holding it and a file under any `node_modules` to none; its sources are `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` files, and its test files `*.test.<ext>`, `*.spec.<ext>` and files under `__tests__`, `test` or `tests`. Its entry modules are what `package.json` points at (`exports` at any depth, `main`, `module`, `browser`, `types`, `typings`), as `typescript-packages` resolves them: a built path (`dist/index.js`) isn't tracked, so it is tried with its extension and first directory swapped for the source's (`src/index.ts`); with no field resolving, `src/index.<ext>` then `index.<ext>`. A package with no entry module, as this repository's `web` and `plugin-panel` are, lists nothing, and its files count as outside every other package. Re-exports are followed within the package, a `.js` specifier also tried as `.ts` since TypeScript rewrites them. A default export isn't listed, since its importers name it as they like; `export =`, `module.exports` and `exports.x` aren't read. Mentions are also read from the whole text of `.vue`, `.svelte`, `.astro`, `.html` and `.mdx` files, comments included, since those embed scripts the detector doesn't parse and a live name used only there would otherwise be reported. Every declaration carries its signature as `typescript-uses` lists, listed or not, since the type a used function returns may itself be unexposed and still name a listed one.

A Python package is a directory with a tracked `__init__.py` whose parent has none, other than `test` or `tests`, named by the directory (`src/acme_core/` → `acme_core`); a directory with `__init__.py` below it is a subpackage within it. Its sources are its `.py` and `.pyi` files at any depth, and its test files `test_*.py`, `*_test.py`, `conftest.py` and files under `tests` or `test`. Its entry module is its `__init__.py`, and its API is `__all__` when that module assigns one (list or tuple literals, `=` and `+=`), else every top-level name without a leading `_` that a `def`, `class`, assignment or import binds, `from .m import *` bringing in `m`'s API by the same rules. An imported name is listed where the module the import names binds it, followed to any depth; a name bound to a module (`from . import sub`) isn't listed, like a Rust `pub mod`. Mentions are also read from the whole text of `.ipynb` files, which hold source as JSON strings, and from the string values of `pyproject.toml`'s `[project.scripts]`, `[project.gui-scripts]`, `[project.entry-points.<group>]`, `[tool.poetry.scripts]` and `[tool.poetry.plugins.<group>]` tables, since an entry point is called by name (`acme = "acme_core.cli:main"` uses `main`). Every top-level definition carries as `python-uses` lists, listed or not, string annotations included.

**Allow-list and entries.** Each `--allow` entry is `<crate>` or `<package>`, which skips that library or package (`clm_check`, `@acme/core`, `acme_core`, compared as written; one name that is both a crate's and a Python package's skips both, and is stale only when it skips nothing in either), or an item's full name, `<crate>::<name>`, `<crate>::<Type>::<name>` or `<package>::<name>`, which skips every item with that full name. An entry that skips no finding, because it names no library or package, no public item, or only items that are used, is itself a finding, so the list can't outlive the code it excuses (`no-dead-code`). Each `--entry` value is a Rust attribute name, compared with the attribute's last path segment as written, so a value spelled as a path (`worker::event`) matches nothing. One that no exactly-`pub` item of a listed kind in a library file, or `impl` block holding one, carries outside test code, used or not, is a finding (`entry-attributes`). Entry points are skipped before the allow-list applies: an entry's staleness ignores `--allow`, and an `--allow` entry that skips only entry points skips no finding.

**Old paths marked for removal** (`unreferenced-skips-marked-old-paths`). An expand-contract's old path keeps its `clm:remove-by <change-id>` marker from the provider's first build until its last, and between them the users move off it, the last move leaving it with no user while the provider's removal waits on that move. The detector skips an item a marker holds, so that move can land. A marker holds an item when it is in a comment, plain or doc, among the comments and attributes (decorators in Python and TypeScript) directly before the item's declaration in its syntax tree, with no other declaration or statement between; one before an `impl` block holds every item of the block. In a TypeScript `export` statement the comments before the statement count. The marker is matched as `check.coverage` reads it, the text `clm:remove-by ` not preceded by a word character, then a change ID of eight digits, `-` and one or more of `a-z`, `0-9` and `-`; the detector reads it itself, since it depends on `vcs` alone and runs in projects with no specs. It doesn't ask whether the change is live: in a CLM project `check/remove-by-markers` does, and fails the check once the change is archived, done, abandoned or missing, so a marker can't outlive the removal it promises; a project without CLM's specs runs no such check, and a marker there skips its item for as long as it stays. A marked item is skipped before the allow-list applies, as an entry point is: an `--allow` entry that skips only marked items skips no finding. A marked item still carries its signature, and an `--entry` it carries still marks an item.

## ADDED Requirements

### Requirement: removal-marked
`clm unreferenced` SHALL NOT list an item that a `clm:remove-by <change-id>` marker holds, in any of its languages: a marker held in a comment, plain or doc, among the comments and attributes (decorators in Python and TypeScript) that directly precede the item's declaration in its syntax tree, with no other declaration or statement between, the comments before a TypeScript `export` statement counting for the item it declares; a marker before an `impl` block SHALL hold every item of the block. A marker SHALL be the text `clm:remove-by ` not preceded by an ASCII letter, digit or `_`, followed by a change ID: eight ASCII digits, `-`, and one or more characters of `a-z`, `0-9` and `-`. A marker inside the item's body or after it SHALL NOT hold it. It SHALL NOT read whether the change the marker names is live. Marked items SHALL be skipped before the allow-list applies, so an `--allow` entry that skips only marked items skips no finding.

#### Scenario: an old path marked for removal
- GIVEN library `a` declaring `/// The old form.` and `// clm:remove-by 20260101-a-rename` before `pub fn old()`, `// clm:remove-by 20260101-a-rename` before `impl S { pub fn m() }` with `pub struct S` used by another crate, `// clm:remove-by soon` before `pub fn not_an_id()`, `// xclm:remove-by 20260101-a-rename` before `pub fn glued()`, `pub fn inside() { // clm:remove-by 20260101-a-rename }`, and `pub fn after()` declared after `old` with no comment of its own, none of them named elsewhere
- WHEN `clm unreferenced` runs
- THEN it reports `a::not_an_id`, `a::glued`, `a::inside` and `a::after`, and not `a::old` or `a::S::m`

#### Scenario: marked in TypeScript and Python
- GIVEN TypeScript package `@acme/core` whose entry module holds `// clm:remove-by 20260101-a-rename` before `export function old()` and an unmarked `export function g()`, and Python package `acme_core` whose `__init__.py` holds `# clm:remove-by 20260101-a-rename` before `@decorator` and `def old_py(): ...`, none of them used outside its package
- WHEN `clm unreferenced` runs
- THEN it reports `@acme/core::g`, and not `@acme/core::old` or `acme_core::old_py`

#### Scenario: an allowance for a marked item
- GIVEN library `a` with `// clm:remove-by 20260101-a-rename` before an unused `pub fn old()`
- WHEN `clm unreferenced --allow a::old` runs
- THEN it prints `clm.toml: allow a::old skips no finding` and exits 1
