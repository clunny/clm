## MODIFIED Design
Thin wrappers over `std::process::Command`, with no git library. One `Error` type: `Failed { command, status, stderr }`, `Spawn { command, source }`, `TimedOut { command, limit }` and the variants below (`Unreadable`, `StillOnDisk`), printed as `<command>: <stderr or status>`, or `<command>: timed out after <limit>` with the limit in `Duration`'s debug form (`10s`, `250ms`). Callers map it into their own errors, `Failure` or a type of their own; none matches every variant by name, so a new variant breaks none of them. `StillOnDisk { path }`, displayed `<path>: still on disk`, is `remove_worktree`'s when git succeeded but the directory remains and it couldn't remove what was left either. The crate has no dependency on the rest of the workspace, so every component can depend on it, and it stays out of the wasm builds (`web.worker` never shells out), which is why a crate that builds for wasm (`orchestrator`) uses `REMOTE` and `now()` only behind the feature that brings in `clm-git`.

`REMOTE` is a `pub const REMOTE: &str`, and `fetch` passes it rather than spelling the name, so the name is written once in the workspace's code. `pub fn now() -> u64` reads `SystemTime::now()` and returns 0 when the clock is before 1970; callers that need finer time, such as `orchestrator`'s claim IDs, or a formatted date, such as `ledger`'s records, keep their own. `Failure` is `#[derive(Debug)] pub enum Failure { Refused(String), Git(String) }`, with `Display` printing the string either variant holds, `From<Error>` giving `Git(e.to_string())`, and `exit_code(&self) -> u8` giving 1 for `Refused` and 2 for `Git`; it implements `std::error::Error`.

`run` and `run_within` share one body that takes an optional limit; `run` passes none and waits. With a limit, stdout and stderr are each drained on a detached thread (not a scoped one) and stdin written on a third, from an owned copy of the bytes since the thread may outlive the call, and the caller polls `try_wait` every few milliseconds until the command exits or the limit passes. On exit it joins the readers and returns as `run` does. When the limit passes it calls `kill` and `wait` on the child, so it is reaped, and returns `TimedOut` without joining the readers: a process the command started, such as a credential helper, may still hold the pipes open, and the readers end when it closes them. Only the child is killed, not a process group, since `git` and `gh` are run directly and the portable `std` API kills one process. A zero limit starts nothing and returns `TimedOut`. A limit is a `Duration`, not a deadline, so callers sharing a budget pass what remains of it.

`run_within` is a function beside `run` rather than a `timeout` field of `Options`, since `Options` is built by struct literal in other crates (`bounded-runs`).

The scan test lists the workspace's crates from `Cargo.toml`, keeps those whose own `Cargo.toml` lists `clm-git`, reads each one's `src/` tree, and fails naming the file and line of any `Command::new("git")` or `Command::new("gh")`, so a wrapper that comes back is caught where it appears, not by review.

`extract_tree` and `extract_paths` both read the whole of `rev` into a temporary index (`git read-tree <rev>` with `GIT_INDEX_FILE` set), so checkout reads `rev`'s `.gitattributes` from that index even when the paths asked for don't include them, then check entries out with `checkout-index` and the temporary directory as the work tree: `extract_tree` every entry (`--all`), `extract_paths` only the entries under `paths`, listed from the temporary index (`ls-files -z --full-name` with literal, top-relative pathspecs) and fed to `checkout-index --stdin -z`. Not `git checkout <rev> -- <paths>`: it runs the repository's `post-checkout` hook, and `checkout-index` runs none. `extract_paths` checks each path's form first, and errors naming a path the listing matched no entry for, since `ls-files` matching nothing is not a git error.

**Tracked files.** `tracked_files(root: &Path) -> Result<Vec<PathBuf>, Error>` and `tracked_matching(root: &Path, globs: &[String]) -> Result<Vec<PathBuf>, Error>`, `globs` being a component's `paths` as the model holds them. `tracked_files(root)` runs `git ls-files -z --cached --deduplicate` in `root`; `tracked_matching(root, globs)` runs the same with `--` and one pathspec `:(glob)<glob>` per glob, so a component's `paths` (`**`, `*`, `?` as in its frontmatter) match by git's own glob rules, and returns nothing without running git when `globs` is empty: a component with no `paths` owns no file, not every file. Both split the output on NUL and return each name as a `PathBuf` relative to `root`, in git's order (sorted). `--deduplicate` lists a file the index holds at several merge stages, during a conflict, once. On Unix the path is built from git's bytes with `OsStr::from_bytes`, so a name that isn't UTF-8 comes back exactly and a caller can hand it back to git (`check-attr --stdin -z`); elsewhere it is converted lossily, which CLM accepts since it runs on Linux and macOS. `--deduplicate` needs git 2.31 or later. An error is `run`'s, naming the whole `ls-files` command; callers pass it on as they map any other `Error`. `init`'s `clm survey` and `check`'s `clm size` both list a component's files through these, so they agree on which files a component owns (`tracked-files-in-git-layer`). `check`'s coverage scan, which also lists untracked files, and `sync`'s queries of single paths and merge stages are other questions and keep their own `run` calls.

**Reading a commit** (`tree-blobs`, `common-dir`). Used by `view.repo`'s `--at` reader (`view-at-rev`). `tree_blobs(root: &Path, commit: &str, keep: &dyn Fn(&str) -> bool) -> Result<Vec<(String, Vec<u8>)>, Error>` runs `git ls-tree -r -z --full-tree <commit>` and then, with the IDs of the blobs whose path `keep` accepts on stdin, one `git cat-file --batch`, both with `GIT_NO_LAZY_FETCH=1` so a partial clone never fetches a missing object, and both through `run`. It returns each kept blob's path, relative to the top of the repository whatever directory `root` is, and its bytes as stored (no `core.autocrlf`, `ident` or filter driver is applied: unlike `extract_paths`, it reads objects, not a checkout), in the listing's order. It skips gitlinks (submodules), symbolic links (mode `120000`) and paths that aren't UTF-8 before asking `keep`. A batch answer that isn't `<oid> blob <size>` followed by that many bytes, such as `<oid> missing`, returns `Error::Unreadable { command, why }`, a variant displayed `<command>: <why>` with `why` naming the path and the answer; no caller matches every variant by name. `common_dir(root: &Path) -> Result<PathBuf, Error>` runs `git rev-parse --path-format=absolute --git-common-dir`: the main checkout's `.git` from any worktree of the clone.

**Removing a worktree** (`remove-worktree`). A build can leave an ignored directory without its owner's write permission, for instance by unpacking an archive; `git status` still reads the worktree as clean, but `git worktree remove` unregisters the worktree and then can't delete what that directory holds. `remove_worktree(root: &Path, path: &Path) -> Result<(), Error>` runs `git worktree unlock <path>` first, ignoring its failure, since Claude Code locks the worktrees it makes and unlocking one that isn't locked fails; then gives the owner read, write and execute permission on `path` and every directory under it that lacks them, setting a directory's permission before it reads its entries so one its owner can't list is still walked, walking with `std::fs::symlink_metadata` and never following or changing a symbolic link, so nothing outside `path` changes; then runs `git worktree remove <path>` through `git`, without `--force`, so a worktree git refuses (one holding an initialised submodule, or a file that isn't ignored) is refused. The walk is best effort: what it can't change is left for git to report. **What git leaves behind.** `git worktree remove` deletes the directory first and unregisters the worktree whether or not that worked, so when a process adds a file while git is deleting (a build's subagent that the agent harness hasn't ended yet, when the build loop finishes the run on its report), git fails with `Directory not empty`, the worktree is no longer one, and no later `git worktree remove` or `clm wrap-up` finds the directory again: it used to be the human's to delete by hand, which isn't theirs to do (`build-loop-in-clm`). So when `path` still exists after git ran, and git listed a worktree at `path` before the call and lists none there after it, the function removes what is left itself with `std::fs::remove_dir_all`, which follows no symbolic link, after the same permission walk, and tries again with a short pause while `path` still exists, for at most 5 seconds from the first try. Git has by then judged the worktree removable and deleted what it tracked, so what is left is what git itself was deleting, and nothing is discarded that git wasn't already discarding. The two listings are the guard: a worktree git refused is still listed, so it is never touched, and a path git never listed as a worktree is never removed, whatever the caller passed. 5 seconds is a constant, not a setting (`yagni`): it has to outlast a process that is ending, not one that is working, and it bounds how long `clm run --finish` and `clm wrap-up` take on a directory nothing can remove. Once `path` is gone the function returns `Ok`, also when git had failed; when it remains, it returns git's error when git failed and `StillOnDisk` when git succeeded. Not taken: `--force`, which removes a worktree with uncommitted work and still fails on a directory being written into; the loop keeping the paths that were left in its file and trying again at each step, which is state and a second removal for a case the retry covers; and `clm wrap-up` sweeping `.claude/worktrees/` for directories git doesn't list, which could remove a directory the agent harness is still making. It lives here, not in `clm-run`, so `clm wrap-up`, which depends on `clm-git` and not on `clm-run`, removes a worktree as `clm run --finish` does (`reuse-first`). It is file-system work beside the git call, and lives in this crate because a worktree is git's: the two callers need nothing else from one another. Each caller prints its own `left` line from the error, since the words are the command's, not the layer's; what is still left after this is what the session's user can't remove at all, such as a file owned by another user, or what git refused.

## MODIFIED Requirements

### Requirement: remove-worktree <!-- base: ff9f14fb8aa93e76 -->
`remove_worktree(root: &Path, path: &Path) -> Result<(), Error>` SHALL remove the linked worktree at `path` whole, ignored files included: it SHALL unlock it, ignoring the failure for a worktree that isn't locked; give the owner read, write and execute permission on `path` and on every directory under it that lacks them, setting a directory's permission before it reads its entries; and then run `git worktree remove <path>` through `git`, without `--force`. When `path` still exists after that, whether `git worktree remove` failed or succeeded, and git listed a worktree at `path` before the call and lists none there after it, it SHALL remove what is left of the directory itself, giving the owner the same permissions first, and SHALL try again while `path` still exists, for at most 5 seconds from its first try, so a directory a process was still writing into goes once the writing stops; it SHALL return `Ok` once `path` is gone, also when `git worktree remove` had failed. It SHALL never follow or change a symbolic link, so nothing outside `path` is removed and no permission outside `path` changes. It SHALL remove nothing itself while git still lists a worktree at `path`, or when git listed none there before the call. When `path` still exists at the end, it SHALL return `git`'s error when `git worktree remove` failed, and `Error::StillOnDisk`, whose display holds the path and `still on disk`, when it succeeded. It SHALL NOT judge whether the worktree has uncommitted changes, which is its caller's question.

#### Scenario: unwritable directory removed
- GIVEN a repository with a locked linked worktree `w` holding an ignored directory `cache/` with a file in it, `cache/` without its owner's write permission
- WHEN `remove_worktree(root, w)` runs
- THEN it returns `Ok`, `w` is gone from disk and `git worktree list` doesn't name it

#### Scenario: symbolic link not followed
- GIVEN a linked worktree `w` holding an ignored symbolic link `out` to a directory `d` outside `w` that holds a file and lacks its owner's write permission
- WHEN `remove_worktree(root, w)` runs
- THEN `w` is gone, and `d` and its file still exist with `d`'s permissions unchanged

#### Scenario: git refuses
- GIVEN a linked worktree `w` holding an untracked file that isn't ignored
- WHEN `remove_worktree(root, w)` runs
- THEN it returns an error whose display holds `git worktree remove`, and `w` and the file are still there

#### Scenario: git leaves the directory
- GIVEN a linked worktree `w`, and a `git` first on `PATH` whose `worktree remove` runs the real one, then makes `w` again holding a file and an ignored symbolic link `out` to a directory `d` outside `w` that holds a file, and exits 1 as git does when it can't delete a directory, running every other command as the real one
- WHEN `remove_worktree(root, w)` runs
- THEN it returns `Ok`, `w` is gone from disk, `git worktree list` doesn't name it, and `d` and its file still exist

#### Scenario: removable only later
- GIVEN a linked worktree `w` whose parent directory lacks its owner's write permission, so neither git nor anyone can delete `w`, until one second after the call starts, when the test gives the permission back
- WHEN `remove_worktree(root, w)` runs
- THEN it returns `Ok`, and `w` is gone from disk and `git worktree list` doesn't name it

#### Scenario: never removable
- GIVEN a linked worktree `w` whose parent directory lacks its owner's write permission throughout
- WHEN `remove_worktree(root, w)` runs
- THEN it returns, within 10 seconds, an error whose display holds `git worktree remove`, `w` still exists, and `git worktree list` doesn't name it

#### Scenario: not a worktree
- GIVEN a repository and a directory `d` holding a file, which git lists no worktree at
- WHEN `remove_worktree(root, d)` runs
- THEN it returns an error whose display holds `git worktree remove`, and `d` and its file are still there
