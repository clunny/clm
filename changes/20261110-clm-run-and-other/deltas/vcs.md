## MODIFIED Contract
The one place CLM shells out to `git` and to GitHub's CLI, `gh` (`git-plumbing-layer`, `reuse-first`). Crate `clm-git` offers `git(root, args)` and `gh(root, args)`, which run the command in `root` and return its trimmed stdout, or an error carrying the command, its exit status and its stderr; `fetch(root)` (`git fetch origin`, tried again after a failure as `fetch_retrying` tries it, returning the last run's error: `fetch-tries-again`); `fetch_retrying(root, args)`, a fetch of `origin` tried again after a failure, which tells being offline from a fetch git refused (`fetch-retries`); `is_ancestor(root, a, b)`; `current_branch(root)` (`None` on a detached `HEAD`); `worktrees(root)` (each worktree's path, branch and whether it is locked, from `git worktree list --porcelain`); `extract_tree(root, rev)`, which checks a revision's tree out into a temporary directory with a temporary index, leaving the working tree alone; `extract_paths(root, rev, paths)`, which does the same for only the files under `paths` (each a file or directory, relative to the top of the tree), so a caller that needs `specs/` doesn't write the whole repository. Both write each file as `git checkout` of `rev` would write it into this repository's working tree: line endings, `ident` and filter drivers (smudge) are applied from `rev`'s attributes and the repository's configuration, and `export-ignore` and `export-subst` are ignored, so hashes read from an extracted tree equal those read from a checkout of the same revision (`extract-as-checkout`). `tracked_files(root)` and `tracked_matching(root, globs)` give the files the index holds under `root`, all of them or those a component's `paths` globs match, each once (`tracked-files`). `run(root, program, args, Options { stdin, env })` is the raw form the others are built on: `program` is whatever program the caller names (`git`, `gh` or any other), `stdin` optional bytes to feed it, `env` variables to set (`GIT_INDEX_FILE`, `GIT_AUTHOR_DATE`, a `GH_TOKEN`), and it returns stdout as bytes untrimmed, so callers that pipe `git check-attr --stdin -z`, run with a temporary index or run a host CLI without a wrapper of its own have one place to go. `run_within(root, program, args, options, limit)` is `run` with a time limit: a command still running when `limit` runs out is killed and the call returns a timed-out error naming the command and the limit (`bounded-runs`), so a caller that must answer in time, such as the release guard, needs no thread of its own and leaves no process behind. Every program is resolved on `PATH`, so a test puts a fake `gh`, `az` or `git` first on `PATH` and the layer runs it. Every crate that lists `clm-git` as a dependency runs no `git` or `gh` itself; a test in this crate fails when one does. A crate comes under the scan by adding the dependency and gaining its own `git-through-layer` requirement. `tree_blobs(root, commit, keep)` reads a commit's files from the local objects in memory, writing nothing, with one `git ls-tree` and one `git cat-file --batch`, and `common_dir(root)` gives the clone's common git directory as an absolute path, shared by every worktree (`tree-blobs`, `common-dir`). `remove_worktree(root, path)` removes a linked worktree whole, ignored files included, also when a build left a directory in it its owner can't write, the one removal `clm run --finish`, `clm wrap-up` and `clm runner` share (`remove-worktree`); whether the worktree is clean enough to remove is the caller's question. `git_isolated(dir, args)` is `git` run as though the environment named no repository: every variable `git rev-parse --local-env-vars` prints (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the rest) is removed from the command's environment, so a command that makes or works in a repository other than the caller's clone, such as `git init --bare`, finds it from `dir` alone and doesn't follow, or get refused by, the variables that name the clone (`git-isolated`). Every other git command the crate runs, through `git`, `run`, `run_within` or any function built on them, runs as `git_isolated` does when its `root` lies outside the work tree the calling process's environment names, so a plain copy CLM writes elsewhere is no repository to git and a temporary worktree is its own checkout, whatever `GIT_DIR` and `GIT_WORK_TREE` name; inside that work tree the environment is honoured (`git-follows-its-clone`).

It also owns the plumbing that the crates which shell out would otherwise each copy (`shared-plumbing-in-git`): `REMOTE`, the name of the remote every command fetches from and pushes to (`"origin"`, the one `fetch` fetches); `now()`, the current time in whole seconds since the Unix epoch; and `Failure`, the error of a command that either refused (`Refused(why)`, exit 1) or failed in git (`Git(message)`, exit 2). `Failure` converts from this crate's `Error` with `?` (as `Git`), displays its message alone, and gives its exit code with `exit_code()`. A crate whose errors are exactly these two, with no conversions from other crates' errors, uses `Failure` as its `Error`, so `crates/clm` can map them to an exit code in one place; a crate that needs a third kind, or `?` from another crate's error type, keeps its own type.

## ADDED Requirements

### Requirement: fetch-tries-again
`fetch(root)` SHALL run `git fetch origin` in `root` and, when it fails, run it again at most twice more, with the waits `fetch_retrying` makes (`fetch-retries`). It SHALL return success at the first run that succeeds and, when the last run fails, that run's error, running no `git ls-remote`, so `clm rebase`, `clm verify`, the ledger's compaction and `clm intake`, which fetch through it, go on after a fetch that lost a race with another process of the same clone over a remote-tracking ref. Its retries SHALL be `fetch_retrying`'s loop, not a second copy of it.

#### Scenario: a plain fetch that loses a ref race
- GIVEN a clone whose `origin` is a bare repository with a branch `b` the clone hasn't fetched, and an executable `git` first on `PATH` that, for the first `fetch` naming `origin`, prints `error: cannot lock ref 'refs/remotes/origin/main'` on stderr and exits 1, and runs the real `git` for every other call
- WHEN `fetch(root)` runs
- THEN it returns success after at least 1 second, `refs/remotes/origin/b` exists, and the fake ran `fetch` twice

#### Scenario: a plain fetch that keeps failing
- GIVEN the same, with a `git` that fails every `fetch` naming `origin` that way
- WHEN `fetch(root)` runs
- THEN it returns an error whose display holds `cannot lock ref`, after at least 3 seconds, and the fake ran `fetch` three times and `ls-remote` never

#### Serves
- capability/work-concurrently
