---
title: "Each build compiles into its own worktree's target; a per-clone cap of places bounds how many run"
date: 2026-10-27
status: accepted
---

Every build compiles into its own worktree's `target/`, its check command included: `clm run`'s prompt names no `CARGO_TARGET_DIR`, and nothing is written to a shared `<main>/target/build`. How many builds and drafts run at once on a clone is bounded instead by `max_builds` (default 3), a setting each clone can set for itself in `clm.local.toml` (`local-settings`). A build or draft holds a *place*, the file `<git common dir>/clm/builds/<name>` in the clone's git common directory, from when `clm run` or `clm draft` starts it until it lands, is finished with `--finish`, or its claim lapses. `clm next` prints at most the free places; `clm run` and `clm draft` exit 3 naming the cap when none is free, claiming nothing. Lands keep sharing `<main>/target/land`, one at a time per clone under a lock, and run their subcommands from a copy of their own binary. A landed build's worktree goes at once: `clm land` deletes its `target/`, and the orchestrating session's `clm run --finish <node>` removes the worktree.

**The probe.** An earlier design had every build share one target directory, `<main>/target/build`, on the assumption that cargo keeps each worktree's workspace crates apart there by their path. It doesn't. Cargo names a workspace crate's outputs by its path relative to the workspace, so every worktree of the repository writes the same files, and it decides freshness by comparing file times. On 2026-10-27 one binary crate was built from two copies at different paths, A then B, into one target directory; B's sources were older than A's build. Running B's binary ran A's code, and cargo reported B `Fresh`. So in a shared `target/build` a build whose untouched sources are older than another build's last compile tests the other build's code and can pass on it. Two lands overlapping on `target/land` can do the same: land A checks out, land B compiles, then A's compile finds A's files older than B's outputs. And a check that rebuilds `clm` into the directory `clm land` runs from replaced land's own binary, so land failed with `No such file or directory` after its checks had passed.

**Why a count, not leased shared directories.** The first proposal leased N shared directories, `target/build-<slot>`, reusing each slot's compiled dependencies. A slot handed to a worktree created before the slot's last use, as a resumed build's is, still serves that use's outputs as fresh, so leasing only narrows the window. Each build compiling into its own `target/` is correct by construction. It costs speed: every build compiles its dependencies cold, so a wave of builds is slower than with the shared directory.

**Why a count, not free space.** On this machine the WSL host's disk fills at about 150 GB used while `df` inside the distribution still reports free space, so a free-space threshold can't guard it, and it would need a size estimate per build. A count bounds disk at roughly `max_builds` worktrees' `target/` (13-20 GB each here) plus `target/land`: about 60 GB with the default 3.

**Places.** A place is a file, not a branch or a record, because it is one clone's local state: the cap counts this clone's builds only, and other clones and machines have their own. Nothing shared depends on it, so `git-is-truth` holds; deleting every place loses only the count, which the next commands rebuild from what is running. It lives in the git common directory, which every worktree of the clone shares, because builds and the orchestrating session run in Claude Code worktrees that come and go: a place taken in one is seen from all, it works for a bare repository with linked worktrees, and nothing has to find the main worktree. A place counts until its branch lands, or its claim lapses and it was taken longer ago than the expiry, so a session that dies never holds a place for more than the claim's expiry; `clm checkpoint` deletes places that no longer count. Taking, renaming and freeing one happen under a file lock, `<git common dir>/clm/builds.lock`, so two commands started at once can't both take the last place. `clm checkpoint` judges places with the default expiry before it removes any branch; a session that ran builds with a longer expiry may see one freed early, which only lets one more build start. `clm next` takes none: it prints only as many nodes as are free, and a session launching them takes them through `clm run`. A draft's place is named by its change ID, which `clm draft` therefore chooses itself from the date and its first claimed item, avoiding any ID a change, a `spec/*`, `autosync/spec/*` or `propose/*` ref, or a place already holds, rather than the drafting session choosing it later: the skill has to know what to finish whatever the draft's closing line says. Until it has claimed, the draft holds a provisional place named with its process ID, never reused, which it renames under the lock.

**Cleanup on land.** A build runs `clm land` from inside its own worktree, which it can't remove, but it can delete that worktree's `target/` once its push succeeds: most of the worktree's disk, freed the moment the work is on `main`. Never the main worktree's, which holds `target/land` and the human's own builds. The orchestrating session then runs `clm run --finish <node>` (or `clm draft --finish <change>`) whenever a subagent returns, landed or not: it frees the place and, once the branch has landed, removes the clean worktree under `.claude/worktrees/` that has it checked out, unlocking it first as `clm checkpoint` does. Running it through `clm` keeps the git calls in the CLI, which a worktree-isolated session may run where it may not run git on another worktree. A build that stopped keeps its claim and pushed work, so a retry resumes it. `clm checkpoint` remains the backstop.

**Lands.** `target/land` stays shared, sparing each land a cold compile, because lands are what other work waits on. The probe's failure needs two lands to interleave, so a land whose check will compile there holds an exclusive lock on `<main>/target/land.lock` from before it creates the tree it checks until its check ends; every file it checks is then newer than the previous land's outputs. A land that waits says so. A land whose code was already checked compiles nothing there and takes no lock, so spec lands don't queue behind code lands. Before running any subcommand `clm land` copies its own binary into its temporary directory and runs the gate and `clm check` from the copy, so a check that rebuilds `clm` can't remove it.

**Upgrading.** The cap applies from the moment the installed `clm` holds it, so it is rebuilt from `main` after this lands. A clone's existing `target/build` is no longer written and can be deleted by hand.
