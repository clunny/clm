---
title: "A runner on the human's own machine builds from git headless; hosted sandboxes are declined"
date: 2026-10-27
status: accepted
---

Refines `builds-in-subagents`, whose "No headless path" left remote runners to design a headless launch of their own. `clm runner --permission-mode <mode>` (`orchestrator.runner`) runs on a machine the human owns, in a clone of the repository, and builds what `clm next` lists: `clm run <node>` prepares each build, the runner starts `claude -p` in a worktree for it, and `clm run --finish <node>` tidies it when the session exits. The interactive path doesn't change: `implement` still builds in worktree subagents of the human's session.

**Pulls from git, nothing dispatches.** The backlog item imagined `web` dispatching ready work to runners connected to a control plane. A dispatcher would own state (which runner has which job) outside git (`git-is-truth`), and runners would depend on the optional `web` (`web-optional`). They don't need one: `clm next`, the claims on `origin` and the clone's places already decide who builds what, and `clm land` serialises the lands. A runner is one more builder polling the queue, so it keeps no state and stopping it loses nothing. `web` already shows the claims it makes.

**Permissions are the human's choice.** The old headless launch used `dontAsk` plus an allowlist CLM shipped, and `builds-in-subagents` dropped it because the list kept growing and every adopting repository would need its own. The runner instead takes `--permission-mode` as a required option and passes it to `claude` unchanged, with no default and no allowlist: the human decides what an unattended session on their machine may do, as they decide their own session's mode for `implement`, and the machine's Claude Code settings apply as in any session. A mode is required rather than defaulted so nobody runs unattended builds under a mode they didn't pick. Headless, a call the settings don't allow is denied, not asked about, so short of `bypassPermissions` a build gets past its first step only when the machine's or repository's settings allow at least `git`, `clm` and the check command; which way the human goes is their setup, and the Contract says so. The runner's worktrees are named `agent-runner-<node>` so the tidy-ups that serve subagents' `agent-*` worktrees (`clm run --finish`, `clm checkpoint`) serve them unchanged.

**Protected writes become human items.** Nobody answers a headless session's prompts, so Claude Code denies a write to a protected path and the guard's `ask` decisions. The runner tells the session to treat a denial as a step only the human can take: leave the requirement unbuilt with a `human` item that blocks it (`requirement-blocks`) and build the rest. The node then settles and the runner doesn't retry it; the human builds the blocked requirement from their own session after deleting the item. A queue state that kept such nodes away from runners in advance (`interactive-tasks`) was rejected again: it matched paths in spec text, over-flagged, and was removed with the headless launch. The same denial is why a runner can never approve or review (`approval-policy`).

**Credentials never leave the machine.** Anthropic's Claude Code terms (read 2026-10-22) require an unmodified `claude`, each user authenticating with their own credentials, and no third party collecting, storing or intermediating Claude.ai credentials or session tokens. The runner runs the machine's own `claude` with the runner's environment unchanged: it reads, stores, passes and sets no credential. Pro and Max limits assume ordinary individual use, so a subscription-signed machine should run with `max_builds = 1`; that is the human's setting, since CLM can't tell how the machine is signed in without reading its credentials.

**Subprocesses, not library calls.** The runner drives `clm next`, `clm run` and `clm run --finish` through their Contracts, so the claim, resume, prompt, places and cleanup stay where they are and a runner's build is exactly the build `implement` launches. No other node's Contract changes.

**Hosted sandboxes are declined** (`20261030-hosted-sandbox-runners`). Running builds in sandboxes CLM operates (Cloudflare Sandbox SDK, E2B, Daytona, Modal, Claude Managed Agents) would need: Anthropic's written confirmation before any subscription-backed hosting, encrypted key storage, per-customer spend caps, an egress allowlist, a GitHub App minting short-lived per-repository tokens without label write, and an audit log of them. Under the re-founding's "stop the growth" and YAGNI no capability asks for it, so it is accepted as out of scope rather than kept as a backlog item. A capability for hosted builds, not a backlog item, would bring it back, and its design would start from this list.

**Alternatives.** A runner daemon connected outbound to a control plane, like a GitHub Actions self-hosted runner, was the item's first shape; rejected for the dispatcher's state above. Restoring `clm run`'s own `claude -p` launch behind a setting brings back two launch paths in one command; a separate node keeps the launch, the only part that is new, apart from the preparation both paths share. A default of `bypassPermissions` would be convenient, but would make the most permissive mode the one nobody chose.
