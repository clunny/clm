---
title: "The build loop is a clm stepper the session carries out, continuous and resumable, one per clone"
date: 2026-11-12
status: accepted
---

`/clm:build` runs the clone's build loop through `clm build` (`orchestrator.loop`). `clm` decides every step: what to launch next and in what order, on which model, how to handle a run's return (resume, rebuild, escalate), when to fold review drafts, archive complete changes and run `clm verify`. It prints the actions, and the session carries them out with the agent harness's subagents and reports what comes back. The loop is continuous: it waits for new work when it runs out, until the human asks it to drain or stop, in the chat or with the panel's buttons. Its state is in git and in a loop file beside the build places, so a crash, a cleared context or a new session resumes it. Everything that needs the human waits in the loop's queue, shown by `clm view queue` and the panel's Queue tab, until it is resolved.

**Why.** An audit on 2026-11-12 found the queue's foundations sound and the loop that drove them wrong, all from one cause: its rules lived in a 22.5 KB skill a model followed, against `agent-harness-adapters`. Return handling was precedence rules in prose, several of them patches over the session getting it wrong (the old `build-waiting-builds`, `build-stops-landed-builds`, `build-unclosed-builds`). The loop's state lived only in the context, which compaction loses. Free places sat idle until one of the session's own builds returned. Drafts went before builds whatever their priority. The approval of review drafts waited for the whole drain to end.

**Through the other commands' Contracts.** The loop runs `clm next`, `clm triage`, `clm run`, `clm draft`, `clm wrap-up`, `clm verify` and `clm land` as subprocesses and reads their output as their Contracts state it, as `clm runner` does, rather than calling their libraries, so every rule stays with its command and the loop's build edits no other component's files (`path-ownership`). A draft whose session ended is continued with `clm draft --resume` on the branch it pushed. The session reports an approval with `clm build approved <batch>`, and `clm land` judges it, so the loop reads no ledger.

**Recompute the plan, don't keep a queue.** Each step computes the plan afresh from `origin/main`, the places and the loop file, which holds only what git can't (the lease, the runs, the history, the drafted items, the fold list, the conditions, the stop request). An explicit queue in the file was rejected: it goes stale whenever another clone lands, claims or files an item, so it needs recomputing and reconciling anyway. A step costs a fetch and a read of the tree, about a second, which a loop waiting on runs of many minutes doesn't notice. Each step stores the plan it acted on in the loop file, and `clm view queue` renders that stored plan, so the panel and the loop never disagree (`views-rendered-by-clm`).

**What belongs to whom.** The human set the rule: what belongs to the AI is in the loop, and what belongs to the human is not. The loop escalates when it must, and every escalation waits in sight. A component or draft that stops twice in a row for the same cause becomes a `question` item the loop files and lands itself, on a `loop/<slug>` branch, so the queue holds the component back until the human answers (`requirement-blocks`). Conditions that clear themselves (a usage limit) or that the human clears (a full disk) stay in the loop file and the queue while they hold. Approving a fold batch is still asked in the conversation, since `clm approve` must be the human's yes through the guard. GitHub intake and upgrade migrations stay the human's (`/clm:triage`, `/clm:upgrade`); a red `clm verify` waits for the human to take it in (`slow-tests-after-land`).

**Continuous, so no wrap-up.** What `clm wrap-up` does that changes nothing of the human's (removing landed work, freeing stale places) runs at every step, and what it reports joins the human's queue, so the loop never needs to wrap up; one summary ends a drain or a stop. `clm wrap-up` stays for the other skills. The watch offer at the end of a drain (`next-wait`) goes: `clm build wait` replaces `clm next --wait`, waking on everything a step would launch, drafts included, while runs are still going.

**One loop per clone, under a lease.** A second session's `/clm:build` sees a live lease and shows the queue; a lapsed lease (15 minutes, outlasting the wait's interval) is adopted, and the runs it lists are orphans the next step relaunches on their branches. `--take-over` is the human's word that the other session is gone; an orphan whose branch still moved within the lease is held until it stays still, so two subagents never push over one branch.

**The session's one judgement.** Reading why a run stopped (a usage limit, a full disk, a failing check, running out of context) needs a model, so the session passes it as `--cause`. `clm` keeps the counts and decides: resume what stopped from outside the work, rebuild on the session's model what went wrong in it, escalate what keeps stopping. The criteria are `resume-sound-builds`', now code, its amendment included: when the same limit or full disk stops runs again, they are resumed one at a time and nothing new launches until they have returned. A rebuilt run that stops again for the cause that rebuilt it is escalated rather than rebuilt again.

**Priority across drafts and builds.** Drafts and builds share the places and launch in one list by priority; at equal priority a draft goes first, since a bug's spec fix can make its component pending. The review drafts are folded once no draft is running, not once every build has returned.

**Dropped after a spike.** A shared compile cache saves nothing a build notices: a fresh worktree compiles this workspace from nothing in 19 s (16 s warm) since `debug = 0`. Holding a component while a spec branch naming it is in flight would have touched 2% of builds over 9 days (6 of 370), each for 4 to 19 minutes; the repeated builds come from specs written after the build started.

**Alternatives.** `clm runner` as the loop brings back headless sessions for attended builds, which `builds-in-subagents` dropped. The panel's hooks module driving the loop puts rules in the agent harness. Keeping the skill as the scheduler and moving only its state and retries into `clm` leaves the prose state machine that produced the defects. `clm runner` keeps its own loop for now (`backlog/runner-loop-on-the-stepper`).
