---
title: "A branch that adds a change is fingerprinted by its authored files; clm land verifies that specs/ is derived"
date: 2026-10-28
status: accepted
---

An approval is pinned to the branch's fingerprint, the hash of the tree entries the branch changes (`tree-diff-fingerprint`, `per-writer-ledgers`). On a branch that adds a change, `specs/` is derived: `main`'s `specs/` with the change's deltas and assets applied, regenerated by `clm sync` and never merged (`regenerate-dont-merge`, `regenerate-applied-specs`, `keep-main-specs-on-spec-branches`). When another change landed on `main` touching the same `SPEC.md`, `clm sync` regenerated the file, its blob changed on both sides, and the fingerprint changed with it, though nothing the human had read (`## Intent`, `## Significant`, the decisions, the deltas) had moved. Each such land on a busy `main` cost a human round trip to approve the same intent again; one change took two. `tree-diff-fingerprint` and `regenerate-applied-specs` had accepted that cost as "a fresh look", but the look is at `main`'s other change, reviewed at its own tier, in a file the reviewer never reads as such (`humans-review-intent`).

So `fingerprint_of` skips every path under `specs/` when the head adds a change: it holds a `changes/<id>/change.md` the merge base lacks, or a `changes/archive/<id>/change.md` the merge base lacks while lacking the live file too. An archive move (the live file at the base, the archived one at the head) adds none, and nor does a branch that adds no change: an `impl/*` branch's `Activate` commit and a finish branch's `status:` line are authored edits under `specs/`, and stay hashed. The rule reads paths only, so `fingerprint_of` is still a pure function of two listings, which `clm fingerprint`, `clm ledger verify` and the `web` Worker already hold.

Skipping `specs/` would be unsafe on its own: until now the fingerprint was the one deterministic thing stopping a hand edit under `specs/` from landing on an approved branch, by lapsing the approval on any edit. `clm land` takes that over (`land/derived-specs`): when the head adds a change it regenerates `specs/` from `origin/main`'s with the added changes' deltas and assets in a scratch directory, exactly as `clm sync` does, and refuses a merged tree whose `specs/` differs, naming the path and `clm sync`, before any check runs. The approval covers the authored files; the lander proves the derived ones follow from them (`deterministic-enforcement`).

What it keeps: `stale-delta-three-way-merge`. A delta `clm sync` merges is authored text committed on the branch, so the merge still changes the fingerprint and the human approves text nobody has read in that form. Only a sync that leaves every authored file alone keeps the approval.

What it costs: every spec branch's fingerprint changes once, so an approval recorded before this lands has to be given again, as after `tree-diff-fingerprint`; and `clm ledger verify`, which recomputes a signed HARD land's fingerprint from its parents, reports earlier HARD spec lands of a signed repository as `ledger/unapproved-land` from then on. No transition accepts both definitions, for the reason `tree-diff-fingerprint` gave. Each land of a branch that adds a change pays one regenerate and one comparison.

Alternatives considered:
- **Fingerprint `specs/` by element** (the changed requirement's old and new hashes), which an unrelated requirement landing in the same file leaves alone. It needs both sides' contents and a parser inside the fingerprint; the Worker would fetch blobs it has no need of today.
- **Carry the approval forward in `clm sync`** when only regenerated files changed. The record would be the author's clone's, which `approval = "other"` refuses, and nobody confirmed it at the guard's prompt.
- **Regenerate at land instead of refusing.** The landed tree would differ from the head the gate rated and the author pushed; `gate/up-to-date` already sends the author to `clm sync`, and this does the same. Taken later for a head behind `main` in `specs/` alone, once concurrent spec lands starved each other (`land-regenerates-behind-specs`).
- **Pin the approval to the deltas' hashes alone**, ignoring the other authored files. Decisions, backlog edits and `change.md` are what the human reads; they stay in.
