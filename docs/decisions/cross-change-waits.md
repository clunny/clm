---
title: "A task waits for another live change's unbuilt work on the nodes its node depends on, derived by the queue"
date: 2026-10-22
status: superseded
superseded_by: node-reconciliation
---

`apply-in-spec-pr` puts every applied change's requirements in `specs/` before any of them is built. A node's spec can then hold text from several live changes, and whichever change builds the node first builds all of it, including text that relies on another change's work elsewhere. `20261022-task-status`'s `orchestrator` task built `orchestrator/run` with `20261022-web-ui`'s prompt text naming the `human` backlog kind, while web-ui's `model` task, which makes the parser accept it, was unbuilt. The launch prompt then told sessions to write items `clm check` rejected (`backlog-kind-human-rejected`). `change-order` couldn't help: it orders whole changes, and a task's `waits_for` names only tasks of its own change.

A task of change `C` on node `X` now also waits while another queued change `D` has deltas for `X` and for a node `Y` in `X`'s `depends_on`, and `D`'s tasks on both are unfinished (no plan, no such task, or not `done`). It waits for `D`'s `plan`, or for those tasks. A `D` that reaches `C` through `after` or `prefer_after` entries, directly or through other changes, is skipped: it is ordered after `C`.

- **Derived by the queue, not written to `plan.md`.** The fact depends on other changes' state, which moves: an unplanned change has no tasks to name, and finishing one releases the wait. Derived each time the queue is read, it's always current and needs no re-plan. `check/plan-matches-change` is unchanged. Writing it to `plan.md` (or both) would go stale, or record one fact twice (`regenerate-dont-merge`).
- **One hop of `depends_on`**, as `waits_for`. The text a node's requirements rely on is in its dependencies' contracts (`spine-scoped-context`).
- **Coarse on purpose.** It can't tell which of `D`'s requirements on `X` rely on which dependency, so it waits for all of `D`'s unfinished work there. It may over-wait; it never lets the bug through.
- **No loops.** Waits only point at nodes `X` depends on, and the node graph has no cycles, so two changes can't wait for each other.
- **The declared order wins** (2026-10-23, `20261023-cross-waits-follow-order`). At first only `after` skipped `D`. A `prefer_after` pointing the other way then fought the wait: `20261023-priorities` preferred nine changes, yet their `orchestrator` tasks cross-waited on its `plan`, which its preferences held back, so most of the queue stalled behind one held item. `check/change-order` already counts `prefer_after` as ordering two changes, so the queue now skips `D` for the same reach. The ordered-first change's plan leaves the later change's text on `X` to that change's own task, as it already must for `after`; the later change's task on `X` still waits for the earlier one's dependency work, so the protection holds in the declared direction. This relies on the plan for the ordered-first change, as `after` always did; nothing checks it deterministically yet.
- **Hard.** A wait can last while `D` is blocked on a human. `--ignore-preference` doesn't lift it, because the task would otherwise build text that relies on missing work. The reason shows in `clm claim`'s refusal and in `queue_from_refs`.

Rejected: declaring the waits by hand in `plan.md` (`waits_for: ["<change>/<node>"]`), which relies on whoever plans to notice the overlap, and the "preference yields" rule of `prefer_after`, which would let exactly this bug through when `D` stalls. Skipping a `D` that prefers `C` is not that rule: it never lets `D`'s preference yield into building `C`'s node early, it only stops `C` waiting on work that `D` declared comes after it. Also rejected for the stall: exempting the work a preferred change waits for from the preference (the exemption `20261023-priorities` specifies) alone, which unblocks the stall but leaves the two rules pointing opposite ways: work would run in the order the waits set, not the order the author declared.
