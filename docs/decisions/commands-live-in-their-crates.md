---
title: "A command belongs to the crate whose requirements state it: its arguments, what it prints and its exit status"
date: 2026-11-15
status: accepted
---

On `main` at `4f96740b`, 872 of the 1,049 tests in the top-level files of `crates/clm/tests/` proved a requirement of another component, and 725 of those ran the `clm` binary. They sat in the root's files because Cargo gives a built binary only to its own package's tests. No crate offered a call that took a command's arguments and streams: each returned lines or a result, and `crates/clm/src/main.rs` chose the stream, the `clm <command>:` prefix and the exit status, in about 1,850 of its 2,824 lines. So the code that met a component's requirement was partly the root's, edited by every build as wiring, and its proof was wholly the root's. `path-ownership` carried a clause for it, "a file that cites the component" (`own-files-at-the-gate`), and the mutation pass couldn't run such a test in the package it mutated (`mutation-after-land`).

So each crate owns its commands. It defines the command's arguments and offers the command as a call that takes them as the command line gives them, the repository root, the environment as a lookup and a stream each for standard output and standard error, and returns the exit status. `crates/clm` parses with those definitions, applies what holds for every command, loads the settings a crate is passed and routes. A test of a component's requirement calls the component's own crate, in the component's own files.

**The arguments are defined in the crate, not in `crates/clm`.** A component that adds an option must be able to prove it in its own files once the clause is gone; with the definitions in the root, a test of the option could only be the root's. It also lets each moved test keep its arguments and its assertions: only the helper that ran the binary changes.

**The environment of a command's children.** The lookup a call takes reaches only code that reads through it. `git`, `gh` and `claude` are started with the process's environment, and many of the moved tests gave the binary a `PATH` holding a stand-in for one of them, a `TMPDIR` or a `GIT_` variable. A moved test sets those on its own process for the length of the call, which is safe because the Rust tests run one per process (`ci/nextest-runner`). Threading an environment through every call of `clm-git`, 383 call sites in the crates' sources, was not taken: it changes every crate's code for what only tests need.

**A command stated below the crate that offers it.** `view` states what `clm status` and `clm view` print and `check.coverage` what `clm pending` and `clm coverage` print, but `clm-view-repo` and `clm-check` offer those commands and lie above them. Their tests assert the text their own crate returns, and the offering crate's `commands-in-crate` proves that the call writes it unchanged, with its stream and exit status. `clm approve` is offered by `clm-approval`, since `land.approval`'s requirements state it.

**Tests move, none is dropped.** `changes/20261115-commands-in-their-crates/moved-tests.txt` is the inventory, made by a script from the markers: 882 lines, one per test and component it cites. A build moves each test under its own name, and a test that cites two components or the root is never deleted by the first build to reach it. A test that observes something only a process has stays, with a `deferred` item that blocks `clm/routes-only`.

**What stays the root's.** The commands whose behaviour the root's own requirements state (`clm contribution`, `clm upgrade`, `clm verify`, `clm machine`, `clm agent-harness`, `clm build`, `clm fingerprint`), what holds for every command, and the proof that a routed command prints and exits as its call does. The root measured 174,665 code tokens before this; about 60,000 remain after it, still over its budget of 40,000, most of it `dev-install` and the scans of source and guide text that the plan's phase 5 takes.

**Tests that need no binary** (`ci`, `plugin`, `plugin.agents`, `plugin.panel`: 144 tests that read workflows, scripts and plugin files) move to directories of their own in the root package, as the capability suite has, since they need only a package to run in (`20261115-tests-in-their-own-files`), in directories that share no name with a top-level test file.

Rejected:
- **Leaving the tests in place and moving their ownership**, with a directory or a `tests` glob per component under `crates/clm/tests/`. No code moves and the clause still goes, but every component's proof still depends on the root's binary and `main.rs` keeps other components' behaviour (`components-own-their-tests` rejected it for this repository).
- **Asserting on what the libraries return today.** The moved tests would stop proving the stream and the exit status, which the requirements state.
- **Argument definitions kept in `crates/clm`**, with a plain request type per crate: a new option couldn't be tested by its owner.
- **A shared crate for the call's stream and environment types.** Standard writers and a lookup function need none.

**A scenario only a process can show is the root's (2026-11-15, by the human).** The first builds left four tests in the root's files with a `question` item each pair: two of `config`'s scenarios run `clm check` and `clm unreferenced`, another component's commands, and two of `check.unreferenced`'s need `clm` started as a detector's child process and the root found from a subdirectory. Each states several components working together through the product, or the root's own root-finding, and a test of the whole product belongs to the component that holds the entry point (`components-own-their-tests`). So such a scenario moves, word for word, into a requirement of the root, which keeps the binary and proves it as it stands. Moving it to the command's component was not taken: that crate can start no `clm` process either. Rewording it for the crate's call was not taken: the test would stop observing what the scenario says. A build that meets such a test still leaves it and files an item that blocks `clm/routes-only`, since only a spec change moves a scenario: a `deferred` item, not a `question`, since this answer stands for the whole class and a question would show as waiting on the human. One spec change takes them all when the build run has drained.

**A mixed scenario is split at the clause (2026-11-17, by the human).** `20261117-scenarios-only-a-process-shows` moved the scenarios the first builds left. Ten of them were mixed: they state what the component made and, in a last clause, that another command accepts it, as "all seven files exist ... and `clm check` exits 0" does. Such a scenario is split: the component keeps it without the clause and proves that in its own crate, and the clause becomes the root's scenario in the same words. Moving it whole was not taken: the root would then state what `clm init` writes a second time, or `init` would have no scenario and no test of its own for it, and three of `init`'s requirements were already proven only from the root's file. A scenario that is wholly another component's command moves whole. Where the component's half is something its crate offers and nothing stated, as the findings `clm-ledger` gives `clm check` on `main`, the component's requirement states that half, so its own tests prove the code that lives in it. The root's requirements are grouped by what the root does (`clm/init-result-accepted`, `clm/check-across-components`, `clm/land-as-a-process`), and a scenario an existing requirement of the root already covers folds there (`clm/root-from-cwd`, `clm/old-command-names-retired`). Folding `init`'s into the `adopt-clm` capability test was not taken: that test shows none of the cases, and a capability test cites only its entry.

**The crate names its own command (2026-11-17, by the human).** `sync/warnings-name-the-command` barred `clm-sync` from holding a string that names `clm rebase`, proven by a scan of its source, so that the root could print each warning under the name the command was run by while the old `clm sync` still ran. With the command a call of `clm-sync` that writes everything it prints, the bar made the root pass the word `rebase` in as an argument. The old name no longer runs, so the bar and its scan are cut, with the human's yes since a scenario goes: the call writes `clm rebase: <warning>` itself, and `clm/rebase-warnings-prefixed` is removed, its scenario moved to `sync`.

**A clause the command's crate can show is that crate's (2026-11-17, by the human).** The fixes that moved tests into their components' crates left 26 in another component's files, nearly all asserting what only `clm status`, `clm view` and `clm pending` do, or `clm-check`'s narrowing of the pending list: the exit status, argument errors, the default width, and what the commands read from git and the settings. `view` and `check.coverage` stated them, and their crates lie below the ones that offer the commands. The answer of 2026-11-15 sent such a clause to the root because the command's crate could start no `clm` process either. Here the crate needs none, so the clause goes to the component whose crate does it, in the same words: `view.repo` states what the three commands read and how they exit, `check` the refusal of a component the graph doesn't hold, and `view` keeps what its library draws for the checkout, size report and claims it is handed (`20261117-clauses-only-a-command-shows`). The root was not taken: it is over its budget, and it would prove by running the binary what a crate decides. One clause stays the root's, a scenario of `clm/routes-only`: `clm-view-repo` is handed the budgets, so that `clm status` marks a component by `clm.toml`'s budget is a join only the binary shows. The same holds the other way: how the line naming a commit renders was stated by `view.repo` and drawn by `clm-view`, so `view` states it and `view.repo` says what the command reads for it.

**The same line through the web app and through `clm land` (2026-11-17, by the human).** Three items still held markers citing a component other than their file's owner, 66 in all (`20261117-tests-sit-with-the-component-they-cite`).

- *The browser tests are `web`'s.* Eighteen markers in `web/e2e/` cited `web.views` and `web.client-live`. Every requirement they cited is also proven in its own component's files, with the Worker faked; the browser tests show the same views through the built app, under `web`'s entry file, stylesheet, routes and service worker: viewport widths, computed colours, what is in the window, the real service worker. `web` holds the app's entry point as the root holds the binary's, so what only the built app in a browser shows is `web`'s, stated in five requirements grouped by what the app shows (`web/cost-views-in-the-browser`, `review-`, `graph-`, `backlog-` and `push-in-the-browser`), and the tests are re-cited where they stand. Giving the tests to `web.views` with a `tests` glob was not taken: they run `web`'s entry and stylesheet, which a component's own tests may not (`components-own-their-tests`). Leaving them uncited was not taken: the clauses only the browser shows would be stated by a component that can't prove them. The cost is that a view change which alters what a browser test shows takes two builds, as a command's does for the root's process tests.
- *A clause whose code is the view's or the Worker's goes to it.* `web.views`' `api.test.ts` cited `web` for what its own request module does (the retry on 401, the copy kept for offline use, `fresh`, a JSON body), which no requirement stated in full: `web.views/worker-requests` states it. The Worker's `sign_in.rs` cited `web/invited-users` for what the Worker decides: `web.worker/invited-sign-in` states it, and `web` keeps what its build and its `wrangler.toml` do.
- *A test of `web`'s files is `web`'s.* Five markers sat on Rust tests in the Worker's crate that read `web/wrangler.toml` and `web/.npmrc`. They are ported to `web`'s own test files. Two of them asserted only what `web/src/wrangler.test.ts` already asserts, and are deleted with the human's yes; their assertions it didn't make (the Worker's name, the assets directory) join the tests there. A `tests` glob giving the two Rust files to `web` was not taken: `web`'s tests would stay in the Worker's package for good.
- *What `clm land` does with an approval is `land`'s.* `land.approval`'s `approval-policy`, `approval-from-base`, `changes-requested-holds` and `signed-land` read "WHEN `clm land` runs" in every scenario, and their 25 tests land a branch from `land`'s crate, which `clm-approval` can't depend on. The four move to `land`, and the tests are re-cited where they stand. The deciding code stays in `clm-approval`, so `land.approval` states what its calls answer (`approvals-counted`, `policy-at-base`, `request-refusal`, `key-and-signing`) and proves it in its own crate, as `ledger` came to state the findings it gives `clm check`. Moving the requirements alone was not taken: that code would then be proven only from another package, where the mutation pass can't judge it.

**What only the process holds stays the root's to print (2026-11-17, by the human; `20261117-phase-4-s-move-is-over`).** `clm/routes-only` said the root prints nothing of its own for a routed command, and asked `--help` of every command `clm --help` lists. Two things didn't fit. The parser's own `help` takes command names and no `--help`. And the root still prints an error of its own when the process can't read its standard input or its current directory, which a call is handed and can't read for itself. The requirement now says both. Fitting the code to the text was not taken: it would hand a standard-input stream to every crate's call for one command's use.
