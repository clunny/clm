---
title: "clm sync rebases another live change's delta that this branch's apply made stale"
date: 2026-10-28
status: accepted
---

A spec branch that applies a change rewrites the sections its deltas modify. A `proposed` or `approved` change elsewhere, on `main` or beside it on the branch, whose delta modifies the same section recorded the old hash as its base, so on the branch that delta is stale (`hash-based-staleness`), and `clm check` fails the branch on it (`apply/stale-base`). Nothing could fix that but editing the other change's delta on this branch: its own author can't rebase it onto text that hasn't landed, and `clm sync` merged a stale delta three-way only for the changes the branch adds, against `main` (`stale-delta-three-way-merge`). On `spec/20261027-clm-serve-2` the session did that merge by hand with a script, twice.

So after regenerating, `clm sync` merges the stale deltas of every live `proposed` or `approved` change it didn't regenerate against the regenerated tree, with the same three-way merge, the same `merged` line and a commit of its own, `Merge <movers> into <change>`, naming the regenerated changes that moved the elements; what doesn't merge cleanly stops the run with the same report, naming those changes. An `applied` change's bases differ from the tree by nature and an archived change is history, so neither is read.

Editing another change's delta on this branch is what the hand merge did. The merged text is in the branch's diff and `clm check` judges it. A merged delta is authored text, so on a branch that needs review (`yes-no-review`) the fingerprint changes and a human approves the merged text again (`derived-specs-fingerprint`).

Alternatives considered:
- **Leave the other delta stale and let `clm check` ignore a stale base that this branch caused.** The branch would land with a delta that applies the old section over the new one when its change is applied, dropping this branch's text (`stale-delta-shows-main`).
- **Have the other change's author rebase after this branch lands.** Until then this branch fails `clm check` and can't land; the author would be rebasing onto text they can't see.
- **Merge only the deltas on `main`, not a `proposed` change the branch adds.** A proposed change beside an applied one on the same branch is stale the same way, and the fold flow (`clm draft --fold`, `yes-no-review`) puts several changes on one branch.

**Taking a merge back** (amended by `20261121-wave-3-sync-by-the-rule`). A merge whose movers name a change, and a hand resolution of one, set the delta's base to a hash only this branch's tree has. The next `clm rebase` loses that tree. When `main` has moved that element since, `git rebase` keeps `main`'s side of `specs/` and drops the earlier `Re-apply` commit. When the branch has taken its edit back, nothing produces the hash again. Either way the delta is left on a base with no text, and the report could only say to compare by hand. So before the merge, each element of a delta whose base is unknown is taken back to the base it had before the newest commit on the branch that set it, and the merge then runs again from a base a stage or `onto`'s history has. The commit is found by the base the element records, never by its message, so the program's `Merge` commits and a person's hand resolution are read alike. The take-back works per element, as the merge writes: the element's block is merged three-way (now, in that commit, before it) and only its own base key is set, so a base edited by hand on another element of the shared frontmatter line doesn't block it. An element is judged when its change is reached in order, against the tree that change is judged on: in a regenerate, the tree after the changes applied before it, as the order reads a base; in the merge of other changes' deltas, the regenerated tree. So a base the report asked the author to set, the element's hash after an earlier change on the branch, is current there and the author's resolution stays; judged before the order, against `onto` alone, it would read as unknown, be taken back and conflict again on every run. An element whose base is current, or found in a stage or `onto`'s history, is never taken back, so an unchanged rebase writes nothing.

Considered:
- **Searching `HEAD`'s history for the base.** Rejected: the rebase drops the `Re-apply` commit that held it.
- **Starting another change's delta again from `onto`'s copy.** Rejected: it discards the branch's own edits to it, a hand resolution among them, and has no copy for a change the branch adds.
- **Taking back the whole file, or only commits whose subject reads `Merge … into …`.** Rejected: a hand-set base on the same frontmatter line makes a whole-file take-back conflict, and a subject would make a hand resolution a trap that rests on a person's choice of words.
- **Judging every element before the changes are ordered.** Rejected: the only tree then is `onto`'s, so a base the report itself asked the author to set reads as unknown and is taken back on every run.
- **Reverting the merges before `git rebase` replays them.** Not taken: it would also avoid a replay conflict when two branches merge into one change, but it moves the work into `sync`'s rebase loop for a case that `clm rebase` already reports.

What stays a hand job: a hand resolution is taken back with the rest, so when its cause changes and the merge conflicts again, the author resolves it again; and an element whose take-back itself conflicts keeps its base and is reported as today.
