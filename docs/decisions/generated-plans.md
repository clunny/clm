Refines `plan-per-change`. Every field of a task (node, requirements, waits_for, context) follows from the change's deltas, the node graph and `clm context`, so `clm plan` writes them and `clm check` verifies them. Claude adds notes on approach in the body, which nothing parses, and may add to a task's `waits_for` another task of the change that its code needs first (`code-order-waits`). Re-planning a stale plan is re-running `clm plan`.

Staleness is not a `clm check` rule: a spec change merging would then break `main` for every pending plan it touches, and the spec PR couldn't re-plan without becoming `mixed`. Instead a stale task leaves `clm next`, `plan` reappears there, and the gate blocks marking a stale task done.

The queue is uniform: a change's `plan`, its tasks and its `finish` are all items that `clm next` lists and `clm claim` claims, so one loop drives the whole implement flow.
