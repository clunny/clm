---
title: "A test renamed in its own file that cites everything it cited is not a deleted test"
date: 2026-11-18
status: accepted
---

`cuts-are-what-a-program-lists` had `clm land` refuse a renamed test, on the reasoning that a build keeps a test's name. The first build to meet it (`impl/host`, renaming two tests whose names stated an exit status the requirement had changed) could not keep a true name: a code branch can't add a line to a `deleted-tests.txt`, so the only ways through were a spec branch for a rename or a name that says something false. It took the false name and a comment explaining it.

**What counts as a rename** (`check.coverage/test-lists`). A test `deleted_tests` would return is matched instead, one for one, with a marker-holding test at the head of the same file whose bare name no test at the base carries, with a marker or without, and whose markers cite every requirement the gone test's cited, versions left out. A matched test is renamed, not gone. The pairing renames as many gone tests as can be paired, taking them in the order `deleted_tests` lists them, so the order of a file's tests never leaves a rename reported as gone. (Amended by `20261119-a-test-that-gains`: the first wording counted only marker-holding base tests' names, so a test the base held with no marker could gain one and stand for a deleted test; and it paired greedily in line order. Amended by `20261119-an-uncited-test-renamed`: a test the base held with no marker that leaves its file's names takes one of the file's new names before a citing test does, since it could have become any of them; so the tests renamed in a file number no more than its new tests, marker or not, less its unmarked tests gone from the head. Before that, an unmarked test renamed as it gained a marker could stand for a deleted test. Amended by `20261119-a-cited-test-deleted`: a name's renames in a file number no more than how many fewer tests of that name, marker or not, its head holds, so a test that keeps its name and loses its last marker is not renamed; and the head's citing tests of a name leave out, per file, those its unmarked tests of that name that left could have become, so a cited test deleted beside an uncited namesake that gains a marker is gone.)

**Why that loses nothing a removal yes protects.** The check is about names already: a build may rewrite a test's body under its old name, keeping its markers, and the land has never refused it. A new name in the same file with at least the same citations gives no more room than that. Whether the test still proves what it cites is the judge audit's and the mutation pass's question, as it is for a test edited in place.

**What is still gone.** A test renamed and moved to another file in one branch, one renamed that cites fewer requirements, one whose new name some test at the base already carries, cited or not, every gone test beyond the new names its file gains once its unmarked tests that left have each taken one, one whose name its file still carries as often as before, and a cited test of a name whose unmarked namesake in its file, or in the file it moved to, may have gained a marker in its place. Each of these errs toward refusing: the build keeps the test, or the change lists it.

Considered:
- **A rename recorded by the build, such as a commit trailer.** Rejected: it is the session's word where a program can check the same thing from the two trees.
- **Matching a new name anywhere in the tree.** Rejected: the case met was a rename in place, and a match across files would let any test elsewhere that cites the same requirement stand for a deleted one.
- **Comparing the test's body.** Rejected: a rename that comes with a change to what the test asserts, the case that met the rule, would never match.
