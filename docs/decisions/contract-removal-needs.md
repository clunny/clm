---
title: "A requirement that removes contract another node uses needs that node's move off it; a build never edits the node it would break"
date: 2026-10-26
status: accepted
---

`20261024-node-builds-as-subagents` removed the queue's `interactive` state and `clm next --interactive` in one change. `orchestrator`'s build had to delete the variant to build its own requirements, so it edited `view`'s crate and tests, outside its `paths`, to keep the workspace building, and it left `plugin`'s `implement` skill calling the removed flag until `plugin` was rebuilt. `expand-contract` covers this case only with two changes, the second left unapplied until the first is built. Nothing told the author when that was needed, and nothing told the build what to do when it hadn't been done.

**At propose time.** When a change removes or renames something in a node's Contract that another node's code uses (a flag, a state, a field, a library call), the requirement that removes it carries a `#### Needs` naming the requirements of each such node that move it off the old contract (`requirement-needs`). The queue then orders the work with no second change: the provider builds everything else and settles, the dependants build against a contract that still holds the old path and move off it, and that releases the removal, which the provider's next build makes. Each build stays inside its own node. A need may point against `depends_on` (`orchestrator`'s *need against the node graph*), which is exactly this case. A `REMOVED` requirement can't carry a `Needs`, so when the removed text is a whole requirement whose code another node uses, the change states the removal as an added or modified requirement of the provider (such as "SHALL NOT offer `--interactive`") with the `Needs`, or splits into the two changes `expand-contract` describes. `propose`'s builder check asks for these needs as it asks for the others.

**At build time.** A build never edits another node's code or tests to absorb its own node's removal, except for the compile-only and test-fixture fixes the removal forces, named in its page (`architecture/path-ownership`; see the amendment below). When building a requirement would break code or tests of another node because that node still uses what the requirement removes, beyond such a fix, the build keeps the old path working and does not build that requirement. It adds a `question` backlog item with `blocks` naming the requirement, saying which node uses what, so a spec PR gives the requirement the `Needs` it lacked and the dependant a requirement to move off, and deletes the item (`requirement-blocks`). For an `obsolete` requirement, which no item can block, the build removes its markers and tests as usual and keeps the code the other node still uses, since that code still serves a current requirement (`no-dead-code`), and adds the item without `blocks`. The item's `nodes` name both nodes. The kept code carries no `clm:remove-by` marker, since the removing change may archive before the item is settled. The spec PR that settles the item says when the code goes.

**Why not edit the dependant.** It would usually be safe, since a dependant waits while the node it depends on has work, but not always: a `--fix` claim ignores the queue, and a need can hold a node back without `depends_on`. It also builds a node from a context that doesn't hold that node's spec (`spine-scoped-context`), and it hides from the human that the spec asked for something its other nodes still contradict. The root's dispatch files stay the one place several nodes' builds edit (`crates/clm/src/main.rs`, `Cargo.toml`, `Cargo.lock`).

Refines `expand-contract` (one change can carry both halves when the halves are requirements on different nodes) and `requirement-needs`.

Rejected:
- **A check that flags a change removing contract from a node another node depends on.** Whether a dependant uses the removed part is a fact about code, not about the spec graph, so the check would fire on every unrelated removal from a provider, or need code analysis per language.
- **Letting the build make the smallest edit in the dependant.** What the `orchestrator` build did; see above.
- **Always two changes.** Two spec reviews and a later apply for what one change and the queue already order.

(Amended 2026-10-29, `20261029-refounding`: the human allowed, at the re-founding's second touchpoint, the compile-only and test-fixture fixes a removal forces in other nodes' code, such as a `match` arm on a removed enum variant, named in the build's page (`path-ownership`). `Needs` can't order a required node after an optional one, nor a variant's removal after another crate's exhaustive `match`. A dependant that still uses what is removed is still never edited to absorb it.)

(Amended 2026-10-31, `20261031-a-build-cannot-delete`: for an `obsolete` requirement the item the build adds is `kind: deferred`, not a question, and says the kept code goes once the other node no longer uses it. The provider's build that removes the code deletes the item with a `Resolves: backlog/<slug>` trailer, with no spec PR (`deferred-work-resolves-in-code`). The item with `blocks` for a requirement left unbuilt stays a question.)

(Amended 2026-11-01, `20261101-a-contract-step-from`: a removal that can't carry its `Needs`, a whole requirement removed or a required node waiting on an optional one, is split into the two changes `expand-contract` describes, and the branch adds a `kind: deferred` item that names the contract change and what it waits on (`contract-step-deferred`).)

(Amended 2026-11-04, `20261104-rename-adds-then-removes`: a rename is an adding requirement, which needs nothing, and a removing one, which needs each user's move, in one change, so the needs form no cycle (`rename-adds-then-removes`).)

(Amended 2026-11-04, `20261104-clm-run-allows-compile`: the compile-only and test-fixture fixes a build may make in other components cover what an addition to its Contract forces too, such as a struct literal that must name an added field, set to the value under which the provider behaves as before (`forced-fixes-cover-additions`).)
