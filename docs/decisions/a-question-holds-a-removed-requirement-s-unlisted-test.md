---
title: "A question holds a removed requirement whose test nobody may delete or re-cite"
date: 2026-11-19
status: accepted
---

A build deletes a removed requirement's test only when an approved `deleted-tests.txt` names it (`land/deleted-tests-approved`), and otherwise re-cites it to the requirement that now states what it proves. When none does and no list names it, because the change that removed the requirement forgot the line, the build can do neither: deleting it is a cut, which needs the human's yes (`removal-needs-a-yes`). It was told to leave the test and file a `question`, but `model/parse-backlog` rejected a `blocks` entry naming a requirement the spec no longer holds, so the question held nothing back. The requirement stayed `obsolete` and ready, the queue offered its component after every build that changed nothing, and the removing change never archived.

**A `question` may block a requirement an applied change removed.** The model accepts a `blocks` entry naming a requirement a live change with `status: applied` or `implementing` lists under `REMOVED Requirements`, and a capability such a change lists under `removes_capabilities`. `clm pending` already prints an item's block on any line, so the obsolete line waits for the human like any blocked requirement, and the queue no longer offers it. The human's answer is a spec change that lists the test in a `deleted-tests.txt` or states what it proves, and resolves the question.

**The code the held-back test runs stays, with no `clm:remove-by` marker.** The obsolete line stays pending and blocked, and the removing change can't be archived while the test cites the requirement, so the pending line is the record `no-dead-code` asks for: once the answer lands, the line's next build removes the test or re-cites it and removes the code no other requirement needs.

**Only once the removal is applied.** A change not yet applied that removes a requirement an item blocks still fails `clm apply` (`apply/resulting-graph`), so the branch that removes a requirement still edits the items that block it: an old question about building the requirement must not survive to hold its removal back. Once the change is archived the entry names nothing and is rejected as before; the change can't be archived while the test the question holds back still cites the requirement.

**Why it doesn't contradict `a-removed-requirement-s-tests-elsewhere-are-listed`.** That decision rejected a question blocking an obsolete line for a test in another component's file, since every such test can be found when the change is designed, and `check/obsolete-tests-elsewhere` makes the change list it. A test in the requirement's own files may still be re-cited, which only the build can judge against the new text, so no check at design time can tell a forgotten line from a test the build will keep. The question is for that edge, a line the change should have carried, and for the places the check doesn't reach (no `wiring`, a `wiring` or unowned file), where the owner's build files it for another component's removed requirement too. It blocks every line of the requirement: one requirement, one wait, released by one answer.

**A removed capability follows the same placement as a removed requirement.** Its test in a file another component owns, once the root sets `wiring`, is pending on that component, the line on `capability` waits for it, and `check/obsolete-tests-elsewhere` holds the change to list it, as `a-removed-requirement-s-tests-elsewhere-are-listed` does for a requirement. The owner's prompt says nothing of code for it, since a capability's tests are all it has. This amends `removed-capabilities-build-out`, whose line was never blocked and sat on one component. Without a `capability` component the placement stays on each marker file's owner, as before, and `check/obsolete-tests-elsewhere` reads the root, which then builds the capability tests, as the capability's component: a test in another component's file is pending on that owner and must be listed, as a removed component's test is.

Considered:
- **A check that every test of a removed requirement in its own files is listed.** Rejected: it would take the re-cite from the build, which is the right answer whenever the behaviour stays stated, and make every removal list tests that stay.
- **A list of tests to re-cite, written by the change.** Rejected for now: it is new machinery for a forgotten line, which the question covers with what exists (`yagni`, `reuse-first`).
- **Accepting a block on a removed requirement whatever the change's status.** Rejected: a stale item would survive a removal unseen and hold its obsolete line back.
