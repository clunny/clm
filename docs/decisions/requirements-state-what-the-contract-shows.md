---
title: "A requirement states what the component's Contract shows, and nothing of how the code is laid out"
date: 2026-11-18
status: accepted
---

Measured on 2026-11-18, 371 of the 891 requirements in the components stated only behaviour. The rest named a function or type (352 by a reader's count, 128 by a program that counts only names the component's own Contract doesn't hold), a field only source shows (55), where a test sits (73) or where code lives (78), had a file's text as their subject (176), or stated only an absence (55). And 214 sentences of a Contract or Design stated an exit, a message, a refusal or a failure path that no requirement of the component states, 87 of them asserted by a test that cites a requirement which doesn't say it. Four such sentences were found one at a time in `check.affected` and `check`, each by a review of a build and each mended by a spec branch and a build of its own.

**The rule.** A requirement states what someone outside its component can observe: a command's arguments, output, exit status and effect on files and git; a file format's keys; or what a call the component's Contract offers returns for what it is given. It names no function, type or field the Contract doesn't offer, no test and no place where code or tests sit, and its subject is never a file's text. Another component's behaviour is named by its requirement's ID, not by the function that carries it.

**A requirement about a file's text** stays in three cases: an entry of `ARCHITECTURE.md` names it under `#### Enforced by`, which makes it a structural check, held once and not once per component; it states a value a program puts into a prompt (`prompt-text-is-source`); or it states a value this repository's own settings file holds, such as its `clm.toml`'s `[verify]` table (amended by `20261119-wave-1-by-the-rule`: a spec branch can't set `clm.toml`, so each of this repository's settings is a requirement of `config` that its build makes, `own-files-at-the-gate`, and without the requirement nothing states the setting or orders the build that switches it on). Any other is a proposed cut, which the human reads (`removal-needs-a-yes`).

**The Contract and the Design.** A Contract may summarise what the component's commands print and how they exit, since a dependant's build receives the Contract and not the requirements (`ancestor-scoped-context`); each such statement is also a requirement's. A Design says how the component works and states no exit, message or refusal. A sentence of either that states behaviour no requirement states is mended one of three ways: it is relied on, so a scenario states it and its test cites it; a requirement already states it, so the sentence goes from the Design; or nothing relies on it, or it contradicts a requirement, so it is a proposed cut.

**How it is applied.** One pass per component: one delta that holds every reword, regroup, move, newly stated scenario and cut, and one build. A pass keeps a scenario's name when it rewords or moves it, so a program can list what a branch removes by name, and its change names every SHALL sentence a requirement loses, though no requirement or scenario goes. A test may reach the behaviour through any public call of its crate: the rule is about a requirement's wording. The rule reaches every project in the guide's spec-format page (`method-in-the-plugin`). It is a principle: a program counts what it can see of it, as advice (the names a Contract doesn't hold, the words that place a test, the exit statuses a Design states, the tests that cite nothing), and whether a requirement states behaviour is a reader's judgement.

Considered:
- **No code names at all, every requirement worded through a command.** Rejected: it rewrites about 350 requirements, and `vcs`, `model` and the ledger's fold hold behaviour no command shows. A library component's calls are what its dependants observe.
- **Working one fault class across every component.** Rejected: each component would be built four to six times, nearly every build a re-cite.
- **A program that re-cites a requirement whose scenarios are unchanged.** Rejected: it makes a requirement current by rewriting its marker, the route `markers-count-in-tests` closed, and no program can tell a shortened statement from a widened one.
- **Failing `clm check` on a test that cites nothing.** Rejected as a gate: it pushes a helper's unit test to cite a requirement that doesn't say what the test asserts, which is the fault this decision mends. The count is advice.

**What wave 1 settled** (2026-11-19, with the human, `20261119-wave-1-by-the-rule`):
- **A per-crate scan of source for retired words is cut** (`says-component`, held by 14 components): its subject is a file's text and `plain-terms` names only the root's two checks. The sentences and scenarios that state the messages stay. Each wave lists its components' scans under that yes.
- **One check holds `git-plumbing-layer`.** `vcs/one-git-layer` reads every crate, whether or not it lists `clm-git`, its build script and its test modules, and names the crates that start any other program. Each later wave cuts from its components' `git-through-layer` the copied sentence and scenario under the yes given here, and keeps what is the component's own.
- **A clause that is the root's code waits for the root's wave**, where both sides move on one branch: until then the component's requirement keeps it, so it is never stated nowhere.
- **Two sentences of `config` stay outside the three cases, by name.** `config/settings-guide-covers-keys`, a rule over a guide page's text, waits for the root's wave, where the root's eleven scans of guide pages are settled as one class; and `config/build-setup-here` keeps the sentence that its test holds a `clm:reads` marker, since nothing else has a land that adds a `package.json` run it. Neither is a precedent: each is cut or restated when a program holds what it guards.
- **A requirement states the intended behaviour where the code falls short of it, and its build mends the code.** `rename/replay` keeps "exactly", though the code compared regular files alone; writing the code's narrower comparison into the requirement would have been a cut nobody was asked about.
- **A change's list reaches the build that deletes.** `orchestrator.run/pending-prompt` names a listed test under a requirement that stays, as it did under one that is removed; before it, a build was told only to re-cite such a test.

**What was settled after wave 1** (2026-11-20, with the human, `20261120-the-plan-ends-with-phase-5`). Wave 1 made its nine components 16% larger in spec tokens, two thirds of it scenarios: 496 became 631 for about 60 newly stated clauses.
- **The rule is for a spec that is true, not a smaller one.** A pass states what the code shows at its component's boundary, the handling of odd input included. `clm land` refuses the loss of a test only when the test cites a requirement, and `no-dead-code` removes code no requirement asks for, so a behaviour left unstated can be removed by any build unseen. A rule that a clause is stated only when something named relies on it was considered and rejected for that reason: a case such as a clock stepped back is most likely there because something broke once, and a build that isn't told of it can't know.
- **No clause for input that can't reach the code.** A reading the system never gives, or an argument no caller can pass, is left unstated: the clause protects nothing and its wording still has to be right. `machine/machine-report` had stated what a memory total of 0 and a disk total of 0 are judged as; the first never reaches the judge, since a total of 0 from the system is no reading, and the second only with no space free.
- **A clause written from the code is checked against the intent.** Of each one the pass asks whether the code or the requirement is right; where the code does a thing by accident the requirement states what is meant and its build mends the code, as `rename/replay` did.
- **One scenario for a clause.** A newly stated clause gets one scenario, its cases listed inside it, and none that shows what another scenario of the requirement already shows. The test behind each case stays.
