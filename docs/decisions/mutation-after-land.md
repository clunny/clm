---
title: "After a land, a project's mutation command says whether new tests notice a change to the code, and a requirement whose tests notice none reads as not built"
date: 2026-11-14
status: accepted
---

A marker in a test that passed says the test ran. It doesn't say the test would fail if the code were wrong: CLM's own capability test for `prove-by-tests` got `current` from an empty test function. Builds were told to break each key rule by hand and see a test fail, which nothing recorded.

`clm verify` now runs a mutation pass after a check that passed, when the project sets `[verify] mutate`. CLM names no tool, as for `[land] check`: the command reads a plan and writes one verdict per requirement, `killed`, `survived <n>` or `not-judged`. Here it is a script that runs `cargo-mutants` and StrykerJS. The pass appends a `mutated` ledger record, and for each survivor lands a `bug` item naming the requirement under `unproven`; coverage reads a requirement so named, at its current version, as `unbuilt`, until a build deletes the item: by mending the test, which the next pass then judges as a changed test, or by finding it sound, which settles it, since an unchanged test is not judged twice.

**Which requirements.** One whose citing test was added, or changed in more than its markers, since the last pass. The plan said "changed or re-cited", and mutating "the changed code of its component". A requirement that was only re-cited has no changed test and often no changed code, and its tests are the ones an earlier pass saw. Judging it against a sample of its component's mutants misjudges sound tests: on 2026-11-14, 17 mutants of `clm-coverage`, run against every test citing it, were noticed by the tests of seven of its ten requirements in 18% to 88% of cases and by those of three in 0 to 6%, among them a test that only builds the crate for another target. So the changed code carries the verdict, the 20 further mutants from the rest of the component are a second chance for a new test whose requirement needed no new code, and a re-cite alone is not judged.

**What it doesn't reach.** Tests written before the pass (`backlog/tests-written-before-the-mutation-pass-were-never-judged`), requirements proven only by browser tests, which the script reports `not-judged`, and a new sound test of code the lands didn't change that 20 mutants miss, which costs one build's look.

**Why the verdict is a backlog item.** Verify pushes nothing to `main`, and coverage is computed from the tree alone in the CLI, in `clm view --at` and in the Worker. An item is a file in the tree, so every reader sees the verdict with no ledger, and adding an item lands on checks. Verify lands it itself through `clm land`; the route a red slow test takes, waiting for a person to take it in, would have a person judge a test.

**Cost.** Nothing at a land: the pass runs after the `verified` record is written and outside the check lock, with a `CLM_SLOT` of its own, one past the build places, so its tests may overlap a land's check as a build's do (`tests-run-concurrently`). Measured here, a mutant costs about 1 second with a crate's own tests and 10 to 18 with the root's CLI tests; a typical build's diff holds 5 to 15 mutants; a pass over 20 lands is 30 to 60 minutes of one core.

Rejected:
- **CLM calling `cargo-mutants` itself.** CLM knows no language's tools (`reuse-first` is the project's to apply to its own language).
- **Coverage reading the ledger's `mutated` records.** Every caller of the coverage would have to fold the ledger, the Worker included.
- **A new state word, `unproven`.** Every view matches the states exhaustively; `unbuilt` already means "not counted as built".

**The first real run (2026-11-14, `20261114-proof-switched-on`).** `.github/scripts/mutate.sh` had only ever run against fakes of its tools. Run with `cargo-mutants` 27.1.0 and StrykerJS 10.1.1 on two lands, it judged nothing and exited 0: nextest refused its filter, `binary(=<package>::<target>)`, which names a binary ID, and StrykerJS refused `--vitest.configFile`, which it takes only from a configuration file. With the filter corrected, the pass over the two requirements of one `check.coverage` land took 30 seconds for 26 mutants and gave both `killed`, with one mutant missed. StrykerJS then failed on TypeScript 7.0.2, which lacks a function it calls when it finds a `tsconfig.json`, and past that ran no test.

Three things follow. A tool that fails is not a verdict: the script exits non-zero, the pass records nothing and the requirements stay due, since a `not-judged` on record is never looked at again while its test is unchanged. The tools are proven where they run: before the plan the script judges a fixture of its own with each tool, and a wrong verdict fails the pass. A test in the suite that ran the real tools was rejected, since it would add their run to every land that selects it (`land-checks-stay-fast`). And this repository sets `[verify] mutate` only by `config/verify-here`, which needs `ci/mutate-script`, so the pass can't be switched on before the script works.

The tracefile the pass leaves for `clm health` is `.clm/verify-build/lcov.info`, the copy in the place `clm verify` keeps from run to run, with every path relative to the repository root: `clm health` strips only the root of its own checkout, so the absolute paths `cargo llvm-cov` writes under the verify tree were dropped without a word in any other checkout.

**Where the first pass starts (2026-11-14, `20261114-migrations-with-templates`).** With no `mutated` record, a pass started from its own verification's `since`. The first real pass here covered 17 lands, failed on a fault of the script and recorded nothing, as it must. The next verification's `since` was that commit, so its pass covered 2 lands, and the tests of the 17 were never due again; they were judged by hand instead, 51 of 53 `killed` and none surviving. A pass with no record to start from now starts at the last commit before `clm.toml` set `[verify] mutate`, read from git alone, so a pass that fails loses nothing however many verifications pass meanwhile. A project that sets `mutate` in its first commit has every cited requirement judged once. Starting from the oldest `verified` record was rejected: it would judge every test a project wrote before it switched the pass on, which `backlog/tests-written-before-the-mutation-pass-were-never-judged` leaves as a decision of its own.

**Only mutants the tests run (2026-11-16, `20261116-the-mutation-pass-judges`).** The 20 further mutants were the first 20 of the component's files in `cargo mutants --list` order, and the diff's were all of the changed code, whatever the requirement's tests ran. For a requirement whose tests reach only part of its component, those are mutants no citing test could notice: `config/unreferenced-detector`, whose rule is data in `clm.toml`, was filed unproven on 20 mutants of `Display` impls and getters its tests never run, while the one function they do run, `detectors()`, had its mutant caught. So `mutate.sh` first runs the block's tests alone under `cargo llvm-cov nextest` and tries only mutants with a line of their span among the lines run, and StrykerJS counts its `NoCoverage` mutants as not tried. A requirement whose tests run lines of its files but none a mutant changes, as when its rule lives in a data or text file, is not judged. One whose tests run no line of its files at all is still `unproven`, its untried mutants counted as survived: that is the empty test this decision began with, and it must stay caught (narrowed on 2026-11-17, below, for tests in a file that reads the repository's files). The whole-suite tracefile wasn't used: it says which lines any test runs, not which the citing tests do, and the previous pass's may be stale or missing. The cost is one instrumented run of each Rust block's tests.

**A pass keeps what it reached, runs requirements at once, and has a limit (2026-11-16, `20261116-a-mutation-pass-that-stops`).** "A tool that fails is not a verdict" holds per requirement, no longer per pass. On 2026-11-15 and 2026-11-16 four passes failed, three on a test that needed a git repository and one on a hang, and each recorded nothing, so every retry started a day's requirements again from the first; a pass of 219 requirements then ran over two hours, one requirement after another, on a 24-core machine with a load of 0.5, with nothing to bound it. Now the script writes each verdict as it reaches it, and however a pass ends (a failure, the `[verify] mutate_minutes` limit, or a stop request) `clm verify` records the verdicts written and names the due requirements it didn't reach under the record's `left`, which the next pass judges first, with the diff from where they first became due. A requirement whose block failed is left, never `not-judged`, so the reason above still holds. A record of what is left was taken over making each requirement due since the record that last judged it, which needs no new field but would make `clm ledger compact` keep, for every requirement, the newest record that judged it, and would take a diff per distinct commit. The script judges up to `[verify] mutate_jobs` requirements at once, cut down to one per 2 GiB of available memory, since memory, not cores, is the limit, and a fixed number would swap beside the build loop's builds; each gets a build directory and a slot of its own, the slots running on past the pass's first, one past the build places. `cargo mutants --jobs` was not taken: it multiplies the memory of requirements at once, and is to be measured first. This repository sets `mutate_jobs = 6` and `mutate_minutes = 60`; both default to one at a time and no limit.

**A test that reads the repository's files is not an empty test (2026-11-17, `20261117-the-mutation-pass-files`).** `clm/doc-readers-marked` was filed `unproven` twice, and both times a build found its tests sound. Its rule is data, the `clm:reads` markers in test files of half a dozen crates, and its tests run `clm-affected`'s `readers`, none of the root's code, so the script took them for an empty test and counted every mutant survived. The plan now names, on `reads` lines, the globs of the `clm:reads` markers in the files holding a requirement's citing tests, and a block that holds one and whose tests run no line of its code with a mutant is not judged. An empty test in a file that reads nothing is still `unproven`. The marker was taken as the signal because it already declares that a test reads the repository's own files; `verify` reads it with `check.affected`'s parser, so any project's command gets it. Not judging every requirement whose tests carry a marker was rejected, since most such tests also run their code and are judged well; so was not judging tests that run only other components' code, which is the misplaced test the pass should report. The markers are read per file, as the land's readers are, so an empty test escapes in any file that carries one, the shared `cli.rs` files among them: that narrows the promise of 2026-11-16 and joins what the pass doesn't reach. Reading only markers inside a test's own span was rejected, since every marker is written once at a file's head.
