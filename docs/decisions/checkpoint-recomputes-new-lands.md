---
title: "The checkpoint recomputes whether each land since this clone last looked needed review, from a local mark, and a land the gate can't rate is a finding"
date: 2026-10-28
status: accepted
---

**What the audit recomputes.** `clm ledger verify` judges a signed land by the kind and the `review` bool its `landed` record states, which the lander writes (`signed-ledger-records`, `yes-no-review`). A lander who records a change that needed review as one that didn't, or as `code`, skips the approval audit; the signature makes the lie attributable, but nothing would report it. So `clm ledger verify --review` recomputes each signed land's kind and review as `clm land` computed them, the gate on the merge commit against its first parent, read from git objects with no checkout per land (`gate/evaluate-at`), and reports `ledger/understated-land` when the recomputed one ranks above the recorded one (`code` = `spec` < `spec review` < `mixed`). A land recomputed as needing review is audited for a counted approval as one recorded so is. Only understatement is reported: an over-stated land asked for more review than the diff needed, which hides nothing.

**Where it runs.** The checkpoint, `clm wrap-up`, passes `--review`, and a human can run it any time; `clm check` on `main` doesn't. Recomputing loads `specs/` at two revisions for each signed spec land, so a check that ran it would pay that for the whole history on every run, growing with every land, and it may not remember what an earlier run verified: no check reads a cache (`git-is-truth`). The checkpoint ends every session (`checkpoint-before-done`), so an understated land is reported within a session of landing, and `wrap-up incomplete` makes a session look at it. The rest of the audit, which reads records and one tree listing per land, stays in `clm check`.

**The mark.** Recomputing every signed land back to the oldest at every checkpoint, with nothing remembered, is a cost that grows with every land, paid at the end of every session. So `clm wrap-up` keeps a *review mark*, the local ref `refs/clm/tiers-verified`: the newest commit on `origin/main`'s first-parent chain up to which this clone has recomputed every signed land and found nothing to report. A checkpoint recomputes only the lands after the mark (`clm ledger verify --review --since <mark>`), runs the audit without `--review` over the whole chain, and then moves the mark to the first parent of the oldest land that got a `ledger/understated-land` or `ledger/unrated-land` finding, or to `origin/main` when none did. A clean land is recomputed once per clone; a finding is reported at every checkpoint until a human acts on it, and only the lands from it on are recomputed meanwhile. A fresh clone's first checkpoint, and a checkpoint after the mark was deleted or `main` rewritten, is the full pass.

**A finding, not a failure.** `clm ledger verify --review` reports a gate error on one land, such as a committed file the current gate can't read, as `ledger/unrated-land`, naming the land and the gate's message, judges that land by its record and goes on; only a git failure outside the gate fails the run. The audit's job is to name lands a human should look at. A land the current gate can't rate is such a land, so it is a finding with the gate's message, like an understated one, and it holds the mark as one does. Failing the run instead would hide every land after it, at every checkpoint, and give no way out short of fixing the gate, since nothing can change a land that is on `main`.

**Why this doesn't bend `git-is-truth`.** The invariant allows a cache derived only from git that can be deleted and rebuilt with nothing lost, provided no check, gate or approval reads it. The mark is derived from this clone's own earlier runs of the audit; nothing lands, approves or passes `clm check` on it; `clm check`'s own run of `verify`, without `--review`, reads no mark; and the full audit stays one command, `clm ledger verify --review` with no `--since`, which reads none either. Deleting the mark (`git update-ref -d refs/clm/tiers-verified`) costs one full pass. The guarantee is that every land is recomputed by the first checkpoint on each clone after it, so a lie is reported within a session; a land this clone has already found clean isn't found clean again at every session's end.

**A ref, not a file.** The build places are files under `<git common dir>/clm/` (`build-places`); the mark is a commit, and git keeps a commit better than a file does: `git update-ref` refuses a value that isn't one, `git rev-parse --verify` reads it, `git fetch --prune` leaves it alone, and every worktree of the clone shares it. `per-writer-ledgers` rejected custom refs for shared state because no host shows or fetches them, which is exactly right for a mark one clone keeps for itself.

**Rules drift.** A land is recomputed with the gate of the `clm` that runs the audit, not the one that landed. A later gate that rates some past diff higher reports an honest land as understated; the land's record and signature are unchanged, and the report names both ratings, so a human can tell drift from a lie. With the mark, such a land is reported only when this clone recomputes it: a clone whose mark is past it never sees the report, a fresh clone sees it on its first checkpoint. A way to acknowledge a report is still open; until then a human who has judged a report moves the mark past it by hand (`git update-ref refs/clm/tiers-verified <commit>`), on that clone.

Rejected:
- **Recomputing in every `clm check` on `main`.** Its cost grows with history, without bound, on the most frequent check.
- **A cache of verified lands that `clm check` reads.** It would make a check depend on state outside git (`git-is-truth`); deleting it would change nothing but the time, but a check may not read it even so.
- **A `verified` ledger record that later runs trust.** It moves the trust to whoever wrote the record, which is the problem the recomputation solves. A local mark that only this clone reads moves no trust: another clone recomputes for itself, and the full audit reads nothing.
- **A temporary worktree per land, running `clm gate` in it.** It checks out the whole tree for each land, where the gate reads only a few files and `specs/` at two revisions.
- **Bounding by time or by count.** Lands in the last N days, or the newest N lands, don't give the guarantee: this repository lands hundreds of branches in a week, so a window either covers most of the history or lets a land go unrecomputed when a session lands more than it holds.
- **Moving the mark past a finding.** It would report each finding once per clone and then go quiet, which is an acknowledgement nobody gave.
- **A file in `<git common dir>/clm/`.** It would work, but a damaged or hand-edited file needs a parse and a rule for what a bad value means; a ref can only hold a commit.
