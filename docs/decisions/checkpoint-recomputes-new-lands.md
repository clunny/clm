---
title: "The checkpoint recomputes the tiers of the lands since this clone last looked, from a local mark, and a land the gate can't rate is a finding"
date: 2026-10-28
status: accepted
---

`recomputed-land-tiers` put the tier recomputation in `clm checkpoint`, which ends every session, so that an understated land is reported within a session of landing while `clm check` on `main` stays one walk of the chain. It left the checkpoint recomputing every signed land back to the oldest, every run, with nothing remembered: a cost that grows with every land, paid at the end of every session. And a gate error on any one land, such as a committed file the current gate can't read, failed the whole run (exit 2) at every checkpoint until a human stepped in, with the lands after it unverified.

Now `clm checkpoint` keeps a *tier mark*, the local ref `refs/clm/tiers-verified`: the newest commit on `origin/main`'s first-parent chain up to which this clone has recomputed every signed land's tier and found nothing to report. A checkpoint recomputes only the lands after the mark (`clm ledger verify --tiers --since <mark>`), runs the audit without tiers over the whole chain as before, and then moves the mark to the first parent of the oldest land that got a `ledger/understated-land` or `ledger/unrated-land` finding, or to `origin/main` when none did. A clean land is recomputed once per clone; a finding is reported at every checkpoint until a human acts on it, and only the lands from it on are recomputed meanwhile. A fresh clone's first checkpoint, and a checkpoint after the mark was deleted or `main` rewritten, is the full pass. And `clm ledger verify --tiers` reports a gate error on one land as `ledger/unrated-land`, naming the land and the gate's message, judges that land by its recorded tier and goes on; only a git failure outside the gate fails the run.

**Why this doesn't bend `git-is-truth`.** The invariant allows a cache derived only from git that can be deleted and rebuilt with nothing lost, provided no check, gate or approval reads it. The mark is derived from this clone's own earlier runs of the audit; nothing lands, approves or passes `clm check` on it; `clm check`'s own run of `verify`, without `--tiers`, reads no mark; and the full audit stays one command, `clm ledger verify --tiers` with no `--since`, which reads none either. Deleting the mark (`git update-ref -d refs/clm/tiers-verified`) costs one full pass. What the checkpoint guarantees is unchanged: every land is recomputed by the first checkpoint on each clone after it. The guarantee of `recomputed-land-tiers`, that a lie is reported within a session, holds as it did; what changes is that a land this clone has already found clean isn't found clean again at every session's end.

**A ref, not a file.** The build places are files under `<git common dir>/clm/` (`build-places`); the mark is a commit, and git keeps a commit better than a file does: `git update-ref` refuses a value that isn't one, `git rev-parse --verify` reads it, `git fetch --prune` leaves it alone, and every worktree of the clone shares it. `per-writer-ledgers` rejected custom refs for shared state because no host shows or fetches them, which is exactly right for a mark one clone keeps for itself.

**A finding, not a failure.** The audit's job is to name lands a human should look at. A land the current gate can't rate is such a land, so it is a finding with the gate's message, like an understated one, and it holds the mark as one does. Failing the run instead hid every land after it and gave no way out short of fixing the gate, since nothing can change a land that is on `main`.

**Rules drift.** `recomputed-land-tiers` noted that a later gate rating a past diff higher reports an honest land as understated. With the mark, such a land is reported only when this clone recomputes it: a clone whose mark is past it never sees the report, a fresh clone sees it on its first checkpoint. A way to acknowledge a report is still open; until then a human who has judged a report moves the mark past it by hand (`git update-ref refs/clm/tiers-verified <commit>`), on that clone.

Rejected:
- **Bounding by time or by count.** Lands in the last N days, or the newest N lands, don't give the guarantee: this repository lands hundreds of branches in a week, so a window either covers most of the history or lets a land go unrecomputed when a session lands more than it holds.
- **A `verified` ledger record.** Rejected in `recomputed-land-tiers`: it moves the trust to whoever wrote the record. A local mark that only this clone reads moves no trust: another clone recomputes for itself, and the full audit reads nothing.
- **Moving the mark past a finding.** It would report each finding once per clone and then go quiet, which is an acknowledgement nobody gave.
- **A file in `<git common dir>/clm/`.** It would work, but a damaged or hand-edited file needs a parse and a rule for what a bad value means; a ref can only hold a commit.
