---
title: "Lands and checks take a clone's locks in a set order: P1 first, then already-checked lands, by priority and then arrival"
date: 2026-11-08
status: accepted
---

`clm land` and `clm land --check-only` wait on two advisory locks, `.clm/land.lock` and `.clm/check.lock` (`land-target-lock`, `check-runs-one-at-a-time`). An operating system wakes a lock's waiters in no stated order, so a land that came first could be passed over, and a spec or docs land whose check runs a handful of reader tests waited behind a full build and test run. Each lock has a queue in front of it (`land/lock-queue`): waiters take tickets, and a ticket carries a lane and a priority. A land whose code key is already checked, whose check runs only the tests that read the files it changed (**Readers of checked code**), takes a ticket in the cheap lane; every other run takes an ordinary one. A land's ticket carries the land's priority, from `orchestrator`'s `land_priority` (`orchestrator/land-priority`): the effective priority of the component an `impl/*` branch builds, the `priority` of each change a branch adds, and the `priority` of each backlog item it resolves, `P5` otherwise. The turn goes to `P1` tickets first, a cheap one before an expensive one; then to the cheap lane, highest priority first; then to the rest, highest priority first; arrival order breaks ties. After six cheap-lane turns in a row below `P1` while an ordinary ticket waits and no `P1` ticket does, that ticket goes next, so a stream of spec lands can't starve a build's land.

**Why tickets locked by their owner.** A ticket is live while its run's process holds an advisory lock on it, which the system drops however the process dies. Nothing reads a process ID, so a reused ID can't keep a dead ticket alive, and the queue needs no cleanup beyond what the next reader does. The lock itself still provides exclusion: the queue only orders, so a run that skips it (an older `clm` on the same clone) loses its place in the order but never overlaps another check.

**Why "already checked" is the lane's test.** It is known before the lock and depends on no toolchain: the merged tree's code passed the project's check, and only the tests that read what the land changed run. It is the case the human asked for (2026-11-08). Other signals were weighed and left out:
- *Past check times from the ledger.* Neutral across toolchains, but `checked` records hold no duration today. Once `slow-land-checks-go-unnoticed` has the ledger record check times, a short measured check could join the lane.
- *Size of the `clm affected` selection.* For unchecked code it is computed in the shared land tree, under the lock, so it isn't known when the land queues. In a compiled project, a small selection still pays for the build, so it doesn't make a land cheap.
- *Small code lands, such as a build of one component.* Not asked for, and with no measured time they can't be told apart from slow ones.

**Why a fixed cap.** No project has asked to tune it (`yagni`). It keeps a burst of spec lands moving while a waiting build lands within a few short checks. It is six, the number the human asked for, and applies only below `P1`.

**Why priority orders the queue, `P1` first.** The human asked that higher-priority work jump the queue too (2026-11-08). Below `P1` the cheap lane still goes first, since a short check delays an urgent land little and spares many waits; `P1` work goes ahead even of that, as the human decided. Here priority can hold work back, which `priority-orders-nodes` rules out for readiness: a steady stream of `P1` lands keeps every other land waiting, with no bound, and below `P1` a stream of higher-priority lands keeps a `P5` one waiting. The human chose this order over a guaranteed turn for low-priority lands. Few slots exist at the top (`priority-caps`), a land queue holds at most a clone's builds and drafts, and it drains whenever lands stop arriving, so the wait is bounded in practice though not by a rule. `priority-orders-nodes` still holds for what it governs: priority never makes a component ready or keeps one from being built. A priority that can't be computed is `P5` with a warning, since the order is never worth failing a land for. The priority is derived when the land queues, from what the branch and the base already hold, so no branch or record has to carry it.

**Why our own queue** (`reuse-first`). No standard tool offers an ordered lock between processes. `flock(2)` and `fcntl` locks, and Rust's `File::lock`, which the clone's locks already use, promise no order among waiters. The lock crates (`fs4`, `fd-lock`, `file-lock`, `named-lock`) wrap those same calls and promise none either. POSIX named semaphores and System V semaphores have no stated order and outlive a killed holder unless it cleans up. The queue keeps the platform's lock for exclusion and adds only the ordering: a counter, ticket files and polling, a few dozen lines in `lock.rs`.

**Alternatives.**
- *Tickets judged live by process ID.* Rejected: IDs are reused, and a check of another process's liveness differs by platform.
- *One queue for both locks.* Rejected: `--check-only` and `verify` take only the check lock, and a land takes the land lock first, so each lock needs its own order.
- *Batching the waiting lands into one check* (`queued-lands-each-run-a-full-check`). Left in the backlog: that work builds on this ordered queue.
