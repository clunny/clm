---
title: "Three routes onto main: spec, code for one component, and light; a branch's name is a claim, never a rule"
date: 2026-11-21
status: accepted
---

A branch reached `main` by eleven routes: a spec branch that needs review, one that lands on checks, a queued build, a fix under `clm claim --fix`, a small code change with no claim, a docs-only branch, test plumbing under a trailer, a rename branch, an archive branch, an outside contribution and the release's push. Several rules chose among them by the branch's name. Only a branch named `impl/<component>` was held to one component's files, so a fix or a small change under another name could change any component's files: since 2026-11-14, 16 code branches landed under names other than `impl/`, 3 of them changing several components' files. `clm land` deleted only `impl/*`, `spec/*` and `propose/*` branches, refused a local `impl/*` or `spec/*` branch `origin` doesn't hold while landing any other name from the clone, and exempted every `spec/*` branch from the deleted-tests check. The gate, which says it reads no branch name, read one for the advice on a `mixed` line. A branch holding only backlog items, an archive move or nothing read `code`. And a scenario added to an existing requirement took a spec branch and then a build, with the requirement pending between them.

The human agreed the routes on 2026-11-21, in `20261121-wave-3-land-by-the-rule`, after the code of `gate` and `land` was read. Each takes effect from that change's builds on; until the build that carries it lands, the rule is as it was.

1. **Spec.** A branch with no code file is a spec branch, and a program decides whether it needs review (`yes-no-review`, `gate/needs-review`). A backlog-only branch, an archive move and an empty diff read `spec` and need nothing. Docs-only, archive, rename and outside contributions are this route. No rules version changes for it: `code` and `spec` with no review rank alike.
2. **Code for one component.** Every code branch, whatever its name, changes one component's files, plus the root's wiring, files no component owns and a capability test that component serves and the branch only modifies. The gate reads the component from the files (`gate/own-files`, `own-files-at-the-gate`) once the root names `wiring`. A fix, a small change and test plumbing are this one route; a claim holds a place in the queue.
3. **Light.** Spec and code together stay `mixed` and refused, except a branch whose spec part is one change it applies and archives `done`, whose deltas only add scenarios to existing requirements of one component, cutting nothing and needing no review, whose code is that component's, and which leaves those requirements current (`gate/light`). It needs no approval and lands on checks. The gate's rules become version 7, under which alone such a branch is `light`.
4. **Every landed branch is deleted.** `clm land` deletes from `origin` any branch it lands that `origin` holds, leased on `origin`'s tip as the land's fetch read it, through `host`'s delete, which refuses `main` and `clm/*` (`land/landed-branch-cleanup`, `host/branch-delete-call`). The head a land takes reads no name (`land.approval/branch-head`): the local branch when `origin` doesn't hold the branch or its tip is the local branch or an ancestor of it, `origin`'s tip when there is no local branch, and a refusal, with advice, for a local branch behind `origin`'s copy or diverged from it.
5. **The release's push** of its version bump stays the one named exception to `clm land` pushing `main` (`land-locally`).

Names stay as claims: `impl/<component>` and `spec/<id>` tell other sessions and `clm proposals` what is taken, and `clm land` holds each to what its files show (`land/build-holds-own-files`, `land/spec-branch-holds-spec-paths`). No rule rests on a name alone, but `spec/<id>` is the one place a name decides what may land beyond whose work the files show: a branch under it lands only when the gate reads `spec`, so a `light` branch that any other name would land on checks is refused there. Outside contributions land under that name through `/clm:contribution`, and a light branch needs no review, so without the rule an outsider's code could land unread (`outside-contributions-are-intent`, `spec-branches-hold-spec-paths`).

**What the direction of 2026-11-18 got wrong.** It was agreed before the code was read.
- It counted eight routes; there were eleven.
- It said a claim would only hold a place in the queue. A branch named `impl/<component>` is still held to its claim: the component the gate reads says whose work a branch is, and is not the claim's test, since a build may modify a capability test its component serves, a file another component owns, and so `clm land` keeps `foreign_files` for that component as the test.
- It took docs-only and archive branches to be the spec route already. A branch with no code file read `code`.
- It wrote light as "one scenario with its test and code". The change can't stay live, since `clm rebase` archives only on `impl/*` branches and a light land must leave nothing for a later build; so it rides the branch archived `done`. Nor can the ledger record a new land kind: every reader of `land_kind` would meet an unknown word, and exhaustive matches on it would break other components' compiles.
- It didn't see that deleting every landed branch makes `host`'s refusal of `main` and `clm/*` the only guard against deleting them, so `host` joined this change and `land` needs that requirement.
- It didn't see what the `spec/*` exemption from the deleted-tests check was for: a replayed rename, whose rewritten markers `rename/replay` vouches for.

**Corrections the session made while drafting** (2026-11-21):
- A light land is recorded as kind `code` with a field `light: true` (`ledger/landed-record-fields`), so an older `clm` reads it as a code land and, auditing with `--review`, says it can't rate it, never that it is understated. The field breaks struct literals of the `landed` record, so `ledger/landed-constructor` landed first and every literal outside `clm-ledger` moved onto it.
- `clm land` keeps holding `impl/<component>` by `foreign_files(component)`, as before, a file outside the CLM root included; the gate admits such a file, which is no component's.
- `host` moved into this change from `20261121-wave-3-host-by-the-rule`, so that `land` can need `host/branch-delete-call`.
- Deleted tests are judged for every branch but a replayed rename, where the routes were first worded "every branch whose kind is not `spec`": an approval-only `clm.toml` edit reads `spec`, and a spec path such as `docs/t.test.ts` can hold a test (`cuts-are-what-a-program-lists`).
- A branch named `spec/<id>` lands only when the gate reads `spec`, which refuses `light` there: an outside contribution lands as `spec/<id>` through `/clm:contribution`, and a light branch needs no review, so allowing it would let an outsider's code land on checks (`outside-contributions-are-intent`).

**Corrections of the second round** (2026-11-21 and 2026-11-22, after the branch's second builder check and its architecture audit):
- *Which head lands.* The first draft refused a local branch ahead of `origin`'s copy whatever its name, which would have refused every early-pushed draft and broken a test of `land`'s that `land.approval`'s build may not edit. A land now takes the local branch when `origin`'s tip is it or an ancestor of it, and refuses only a local branch behind `origin`'s copy or diverged from it; the delete is leased on `origin`'s tip, which the landed merge contains.
- *The approval order kept beside the old.* `Body::approved` keeps leaving `clears` out, so an approval built the old way clears by time and no approval clears nothing between `ledger`'s build and its writers' builds; `Body::with_clears` writes the field, and `clm approve` and the web app's approve move to it in their own builds.
- *Old calls go by a requirement, not a marker.* `land.approval` keeps its old head and hold calls beside the new until `clm land` moves; `land.approval/old-calls-gone`, which needs `land`'s requirements, removes them, so the change stays live until then. A `clm:remove-by` marker would have failed `clm check` on whichever build archived the change first (`contract-removal-needs`). Once built and dropped from the Contract, the requirement stated only an absence, and `20261122-old-calls-gone-is-cut` cut it with its test.
- *A new public call is proven from its crate's own tests.* An earlier report that a build adding a public call another component adopts later can't land alone was mistaken: the unreferenced-items detector counts a use in the crate's own tracked tests.

**What it costs.** One evaluation of the gate took 0.05 s for a one-commit code diff here, 0.2 s for a spec branch whose cuts load both spec graphs. Route 2 adds one load of the merge base's graph for a code branch when the root names `wiring`; light adds one `git grep` for the touched requirements, only for a branch whose spec part is one archived change and one component's `SPEC.md`. `clm land` calls the gate's library once before its lock, for the kind its own rules read.

Considered and rejected:
- **The gate reading a branch name** to decide whether ownership applies, as it read one for its advice: the gate stays a function of two trees and one flag (`spec-branches-hold-spec-paths`).
- **`clm land` comparing a branch's name with the component the gate reads.** An `impl/a` that only modifies a capability test `a` serves reads `capability` and lands today; it must keep landing.
- **A new land kind `light` in the ledger**, for the reasons above.
- **A light branch whose change stays live**, archived later by `clm rebase`: only an `impl/*` branch archives, a name read, and a live change would leave the requirement for a later build.
- **Blocking a file outside the CLM root at the gate.** It is no component's; the claim's test on `impl/<component>` still refuses it.
- **`clm land` deleting only claim branches**, as before: a rule resting on a name, and a landed branch is done; the lease keeps one that moved since.
- **Light on a branch named `spec/<id>`**, for outside contributions.
