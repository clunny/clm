---
title: "The unit of building is the node: its code is brought up to its whole spec, ordered by the node graph alone"
date: 2026-10-23
status: accepted
---

A change is the unit of intent: a human approves it, and `clm apply` folds its text into `specs/` (`apply-in-spec-pr`). Until now the change was also the unit of building: one plan per change, one task per change per node, a `finish` item, and tasks that recorded the bundle hash they were built on. But `specs/` on `main` holds every applied change's text for a node at once, so a task on a node either built other changes' text by accident or had to be told, change by change, which text was its own. Every ordering rule CLM grew came from reconciling those two units: `after` and `prefer_after` (`change-order`), the demand that every overlap be ordered, cross-change waits derived from shared nodes (`cross-change-waits`), code-order waits within and across changes, plan staleness and re-plans, `gate/task-done-fresh`, and priority inheritance. Each was right locally. Together they fixed order at propose time from arrival rather than need, held work for weeks behind changes that didn't need it, re-planned a change after almost every other change that touched its nodes, and failed finished PRs because `main` had moved under them.

Now the unit of building is the node. A build session brings a node's code up to the spec on `main`, all of it, highest priority first. The queue is derived each time it is read from three things that are all committed: the node graph, the test markers with their versions (`versioned-markers`), and the backlog items that block requirements (`requirement-blocks`).

- **Order is the graph.** A node is ready when it has pending work no item blocks, whatever the state of the nodes it depends on: only a requirement's `Needs` holds work back (`needs-alone-order`, which on 2026-10-29 replaced the rule first written here, that a node waited until every node it depended on was settled). The graph has no cycles, so nothing waits for itself, and no cross-change wait can point the wrong way. A dependency that is waiting is unsettled, so the wait reaches down the graph without naming it.
- **Nothing is planned.** The queue reads no `plan.md` or task file, and there is no `finish`. (A change run by hand may keep a `plan.md` as notes, as the re-founding does; nothing parses it.) What is left to build is read from the markers, so a merged PR is progress whatever it leaves, and a spec that moves under a build adds pending text instead of invalidating work.
- **Parallelism is the frontier of the graph.** Every ready node runs at once, each in its own worktree on `impl/<node>`, claimed by lease as before. Node `paths` are disjoint, so two sessions rarely edit the same file (since 2026-10-29, only through a removal's forced fix in another node, `architecture/path-ownership`). A node too hot to keep up is a reason to split it in the architecture, which is pressure in the right direction.
- **Changes carry priority and progress.** A pending requirement takes the priority of the live change that added, modified or removed it (`priority-orders-nodes`). A change is complete when its requirements are current and nothing cites one it removed, and `clm sync` archives it (`archive-on-sync`).
- **A build is scoped to a node, whatever intent its text came from.** One PR may carry text from several changes. Humans review intent in spec PRs, not code (`humans-review-intent`), so the mixing costs no review. Progress per change is read from its requirements.

Supersedes `plan-per-change`, `generated-plans`, `change-order`, `cross-change-waits`, `cross-change-code-order-waits`, `code-order-waits`, `task-status-files` and `report-block-cycles`. Refines `priority-caps` (the caps stay; the between-changes ordering goes), `blocked-by-backlog` and `task-deletes-fixed-items` (items block requirements, and the build that fixes an item deletes it), `lease-claims` and `merged-claims-released` (the claim is `impl/<node>`), and `interactive-tasks` (the test runs over a node's pending requirements).

Rejected:
- **Keeping change-scoped tasks and pruning the waits** to requirement-level dependencies declared by the author. Smaller, but a task still builds other changes' text by accident, so staleness and re-plans stay, and the author has to know the code's wiring.
- **A task per requirement.** Finer than the paths that keep parallel sessions apart, and many more PRs for the same code.
- **Design-only changes making a node pending.** A node is pending on requirements only; a Design edit alone builds nothing, as `archive-in-spec-pr` already treats it. Reopen if Design edits that should drive refactors turn out common.

(Amended 2026-11-12, `20261112-components-own-their-tests`: builds no longer share files through a removal's forced fix in another node; they do only under `path-ownership`'s remaining exceptions (`coupled-changes-sequence`).)
