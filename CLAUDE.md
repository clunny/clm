# CLM: working in this repo

CLM is built with CLM. Read `ARCHITECTURE.md` first; its architectural constraints apply to work in this repo. Then run `clm status` (`cargo run -q -p clm -- status`) for the current state, and `clm backlog` for what's next. Open `spec/*` and `impl/*` branches, and their pull requests, show work in flight.

- Spec/design edits go in `changes/<YYYYMMDD-slug>/deltas/` and reach `specs/` only through `clm apply`.
- Requirement IDs are `<component-id>/<slug>`. Tests reference them as `req:<component-id>/<slug>` (see `docs/spec-format.md`).
- Record significant choices as `docs/decisions/<name>.md` (one file each). Refer to architectural constraints, decisions and open questions by name (e.g. `proven-by-tests`, `no-stacked-prs`), never by number.
- Code: Rust (cargo workspace). Run `cargo fmt`, `cargo clippy -- -D warnings` and `cargo test` before claiming work is done. `clm check` runs the detectors in `clm.toml` (`no-dead-code`); install their tools (`cargo install cargo-machete --locked`) or it fails.
- Remove what a change obsoletes: code, tests and dependencies (`no-dead-code`). A breaking contract change goes expand, then contract, with the old path marked `clm:remove-by <change-id>` (`expand-contract`).
- Commit early and often. Put each piece of design work (its decisions, deltas and backlog edits) in **one** spec branch: each branch that needs review costs a human review.
- **Run `clm approve <branch>` only when the human has just said yes to that change's intent in this conversation, and only through the command the guard asks them to confirm (`approval-policy`).** Never ask another tool to do it, and never route around the guard. Only a human approves spec changes (`humans-review-intent`); the guard's prompt is what makes the yes theirs.
- Never stack branches: every branch lands on `main` through `clm land`, and nothing else pushes `main` (`land-locally`). A branch's pull request (`clm pr open`) is for reading the diff; nothing waits on it.
- **CLM defects:** when CLM itself gets in the way (a gate or CI misfire, a rule you must work around, a wrong or missing instruction, a decision that fails in practice), report it with `clm defect` when it happens; your own mistakes that CLM caught or you fixed don't count (`defect-reports`). Fix a small one in the moment instead of leaving it filed: fold it into the current `impl/*` branch when the fix lies in its components, without reporting it; otherwise report it and, once your branch has landed and brought the item to `main`, fix it before the session ends on its own branch with `clm claim <component> --fix backlog/<slug>`. Report with `--component` naming the component the fix lies in, and fix in a worktree of your own, never the checkout you started in. Leave a defect in the backlog only when it's a large amount of work or needs a spec change. A fix needs a spec change when no requirement or scenario as written states the behaviour it restores (`code-fix-needs-a-written-rule`). An unattended session folds what fits and reports the rest; it opens no fix branch. This repo's `clm.toml` sends reports to the backlog as `kind: bug` items on the current branch. Before landing anything, report any you missed and list them under `## CLM defects` in the pull request body. Adding a new backlog item never makes a code branch mixed (`gate/backlog-additions`), so file reports on `impl/*` branches too; editing or deleting an existing item does, except deleting one that a live change `resolves`, or a `kind: bug` or `kind: deferred` item on a component the PR's code touches that a commit names with the trailer `Resolves: backlog/<slug>` (`code-fix-resolves-bug`, `deferred-work-resolves-in-code`).
- **Memory never holds CLM's fixes.** Claude's own memory holds only the human's preferences and facts about this machine. A CLM workaround, a procedure CLM doesn't state, or a defect found in a session goes to `clm defect` or the backlog, never to memory alone: other sessions, drafts and builds don't load it, so a fix kept there hides the defect (`defect-reports`).
- Fold small discoveries (no spec change needed, within the change's components) into the current change. Record significant out-of-scope ones as `backlog/<slug>.md` items (`fold-small-defer-large`).
- A small code change that needs no spec change, with no `impl/*` branch to fold it into, takes no claim (`small-change-no-claim`): make a branch of its own from `origin/main` in a worktree of your own, named outside `impl/`, `spec/`, `propose/` and `autosync/`; `clm gate --base origin/main` must print `code`; push, `clm pr open`, `clm land <branch>`, then delete the pushed branch, which `clm land` leaves. It fits only when every requirement and scenario as written stays true and the change adds nothing a requirement would have to state. A `kind: bug` or `kind: deferred` item takes `clm claim <component> --fix` instead, and behaviour no requirement states starts on a spec branch (`code-fix-needs-a-written-rule`).

## How a change flows

1. **Spec branch** `spec/<change-id>` from `main`: `changes/<id>/change.md` (intent, `status: proposed`, optional `human_burdens`, `from` and `resolves`) and `deltas/<component>.md`, with bases from `clm hashes <component>`. `clm check` must pass. Other sessions may be proposing too (`propose-claims`): pick only backlog items `clm proposals` doesn't name, claim each with `clm claim backlog/<slug>` before designing, and push the spec branch early. Until those commands ship, check `origin/spec/*` and `origin/autosync/spec/*` branches for a `change.md` naming the item.
2. **Apply** as the branch's last step: `clm apply <id>`. Commit, then run `clm gate --base origin/main`: its first line is `spec review` when the branch needs review and `spec` when it lands on checks (`yes-no-review`). Push, open the pull request with `clm pr open`, and land with `clm land spec/<id>`: it runs the checks here and pushes `main`. A branch that needs review lands once a human has run `clm approve` through the guard's prompt; the rest land on checks, and nothing is reviewed after it lands. A branch that's merely behind `main` needs nothing: `clm land` merges `main` in and checks the result before it lands. If it conflicts with `main`, or the gate reports `gate/up-to-date`, run `clm rebase` and resolve what it reports (conflicted files, stale deltas, check failures), committing each fix, until its last line is `rebase ok`, reading its outcome from that line and never from its exit code: `rebase incomplete` leaves something for you, and `rebase failed` means git itself failed, so run it once more and, if it fails again, stop and say what it printed. Then `git push --force-with-lease` and land again: the approval holds only if the diff's fingerprint is unchanged.
3. **Build**: work is per component, not per change (`node-reconciliation`). `clm pending [<component>]` lists the requirements whose code hasn't caught up with the spec: `unbuilt` (no test cites them), `behind` (cited at an older version) or `obsolete` (cited, but a live change removed them). `clm next` lists the components ready to build: pending, unclaimed, with a requirement that no backlog item or pending `Needs` blocks (`depends_on` doesn't order builds: `needs-alone-order`). `clm claim <component>` claims one, pushing `impl/<component>`; `clm run <component>` claims and builds it unattended. Build the pending requirements highest priority first; stop at a green point if the list is long and say what's left. Push at least every 4 hours or the claim lapses. If you need a fact or a step only the human can supply, add a `question` or `human-task` backlog item whose `blocks` names the requirements that wait on it, and build the rest (`requirement-blocks`). When a requirement needs a workaround, a faked dependency, another component's Design changed or a spec change to build, flag it with `clm workaround <component>/<slug>` (`workaround-flags`). When it exits 3, the capability has too many unsettled workarounds (`redesign-before-workaround`): keep the flag, stop working on that requirement, add a `question` item naming the capability that `blocks` it, and build the rest. `clm health` shows the whole picture (`health-advises`).
4. **Prove**: each test cites the requirement at its current version, `req:<component>/<slug>@<version>`, the first 8 hex digits of its hash from `clm hashes <component>` (`versioned-markers`). Remove the code and tests behind `obsolete` markers (`no-dead-code`). Then mutation spot-checks: break each key rule on purpose and confirm a test fails, run as `clm run`'s prompt says (`prompt-spot-checks`): commit first, count only a mutant that compiles and fails a named test, `touch` each restored file, loop under `sh`, not `zsh`. Then review the diff before landing (`advisory-code-review`): run `/code-review` and the `spec-auditor` subagent; fix what you agree with, and list the findings and what you did under `## Review` in the pull request body.
5. **Finish**: nothing to do by hand. A change is complete when every requirement it added or modified is current and nothing cites one it removed; `clm rebase` on an `impl/*` branch archives complete `applied` changes, deletes the items they `resolves` and sets an `unbuilt` component `active` once nothing on it is pending (`archive-on-sync`); `clm wrap-up` names any change left as `complete <id>` for a small archive branch. `clm check` passes and `clm gate --base origin/main` prints `code`. Push, open the pull request, and run `clm land`.

## Gotchas

- Fixtures that need a `req:` marker build it so the literal never appears whole (`concat!("req", ":a/x")`), or `dangling-markers` flags the test file.
- Switching to a branch without a new crate leaves its empty `crates/<name>/` directory behind, which breaks the `crates/*` workspace. Remove it.
- `clm land` runs `.github/scripts/ci-check.sh` (fmt, clippy, tests, the wasm builds, the web and panel suites) and then `clm check` on the merged tree, on this machine. A tree whose code was already checked runs only `clm check`.
- This repo's sessions should run `main`'s `clm` and the checkout's plugin, not the release (`dogfood-from-main`). If the main worktree's `.claude/settings.local.json` sets no `CLM_BIN` or no `clm` directory marketplace, the clone runs the release. When `origin/main` has `scripts/dev-install.sh` (`git cat-file -e origin/main:scripts/dev-install.sh`), tell the human to run it once in the clone (`dev-install-script`), with `--force` when it refuses an existing hook it didn't write, and do the same for a clone that has both entries but no hook holding the line `# clm dev-install` where the script on `origin/main` writes it (`reference-transaction` when `git grep -q reference-transaction origin/main -- scripts/dev-install.sh` succeeds, else `post-merge`; the path is `git rev-parse --git-path hooks/<name>`), or still has a `post-merge` hook holding that line once the script writes `reference-transaction` (`rebuild-on-origin-main`). Until then, tell them to set the clone up by hand as `dogfood-from-main` describes: `cargo install --locked --path crates/clm --target-dir target/install` in the main worktree, up to date on `main`; `CLM_BIN` set to the binary that installed, and the `clm` directory marketplace, in its `settings.local.json`; and the `post-merge` rebuild hook. `clm --version` naming no commit means only a build older than `clm/build-commit`, not the release, since release builds name their commit too. A session never runs these steps or edits `settings.local.json` itself, or otherwise installs `clm` (`no-shared-install`).
